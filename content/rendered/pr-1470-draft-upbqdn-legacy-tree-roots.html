#Terminology

The key words "MUST", "MUST NOT", "SHOULD", and "MAY" in this document are to be interpreted as described in BCP 14 [1] when, and only when, they appear in all capitals.

The term "network upgrade" in this document is to be interpreted as described in ZIP 200. [2]

"Legacy protocol" means the P2P network protocol specified in ZIP 204. [3] uint8, uint32, and CompactSize are as defined there.

The tree roots of a block are its Sapling, Orchard, and Ironwood note commitment tree roots, that is, the roots of those trees after the block's note commitments are appended. [8] [5]

#Abstract

This ZIP adds a service bit and two messages, gettreeroots and treeroots, to the legacy protocol. With them a node obtains the tree roots of a range of blocks from a peer. The node does not trust the peer: it checks each block's roots against the commitments in the headers of that block and its successor. A node syncing from checkpoints can then maintain its chain history tree without computing the Sapling, Orchard, and Ironwood note commitment trees.

#Motivation

A node needs every block's tree roots. They are committed to by the chain history tree [4], and are the anchors that later spends reference. Computing them requires updating the note commitment trees, which is most of the cost of committing blocks with many shielded outputs. During checkpoint sync, the node needs the trees only for their roots.

The roots are small and are authenticated by block headers, so any peer can supply them. The draft version 2 P2P protocol has a get-tree-roots request for this purpose. [11] This ZIP specifies the equivalent for the legacy protocol.

#Privacy Implications

Requests reveal the heights a node is syncing, as getheaders and getdata already do.

#Non-requirements

This ZIP does not provide note commitment tree frontiers, Sprout roots, or historical tree states. A node that uses supplied roots instead of updating its trees cannot update them again until it obtains authenticated frontiers by other means, which this ZIP does not specify.

#Specification

#Service bit

NODE_TREE_ROOTS (bit 3) in the services field of a version message signals that the node answers gettreeroots. A node MUST NOT send gettreeroots to a peer that did not set this bit in its version message.

#gettreeroots

Command:

gettreeroots

Direction:

Both

Payload:

Size

Field

Description

4

start_height

Height of the first block (uint32).

32

final_hash

Hash of the last block in the range.

4

count

Number of blocks, from 1 to 4000 (uint32).

Requests the tree roots of the blocks at heights start_height to end, where end = start_height + count - 1, computed without wrapping. final_hash is in the internal byte order used for hashPrevBlock. [10] A node MUST reject a gettreeroots message whose count is 0 or greater than 4000.

Both

Field

Description

varies

n

Number of entries, present only if result is 0 (CompactSize).

varies

entries

n entries, present only if result is 0.

Each entry has the following format:

Size

Field

Description

32

sapling_root

Sapling note commitment tree root.

32

orchard_root

Orchard note commitment tree root.

32

ironwood_root

Ironwood note commitment tree root.

1

has_auth_data_root

0 or 1 (uint8).

0 or 32

auth_data_root

Authorizing data root of the next block, present only if has_auth_data_root is 1.

sapling_root, orchard_root, and ironwood_root are encoded as anchorSapling, anchorOrchard, and anchorIronwood respectively. [9] [5] auth_data_root is a hashAuthDataRoot value as defined in ZIP 244. [6]

A node MUST reject a treeroots message whose result or has_auth_data_root is neither 0 nor 1, whose n is greater than 4000, or that contains a non-canonical root encoding.

#Answering requests

A node that advertises NODE_TREE_ROOTS SHOULD answer each gettreeroots with a treeroots, sending a refusal when it does not serve the request, for example because it is busy or lacks the data. It MUST NOT send more than one treeroots per gettreeroots, nor a treeroots that was not requested.

A node MUST NOT send entries unless its best chain has a block at height end with hash final_hash. Entry i, for 0 <= i < n where 1 <= n <= count, MUST hold the tree roots of the block at height start_height + i on that chain. auth_data_root MUST be present if and only if the next block, at height start_height + i + 1, is at or after NU5 activation; it is then that block's hashAuthDataRoot.

Computing auth_data_root requires the next block's authorizing data, so a node SHOULD bound the block data it reads per request, sending fewer than count entries if needed.

#Sending requests

A node MUST NOT send gettreeroots on a connection while an earlier gettreeroots on that connection is unanswered. A node that stops waiting for an answer MUST NOT send another gettreeroots on that connection, since a late answer cannot be matched to its request.

A node MUST ignore a treeroots received while no gettreeroots is outstanding on that connection, MUST reject one with more than count entries, and MUST treat one with no entries as a refusal.

#Verifying roots

Before using the entry for the block B at height h, a node MUST have authenticated B and the header at height h + 1 on its chain, for example by checkpoint verification, and MUST check that:

  1. the root of each pool whose network upgrade (Sapling, NU5, or NU6.3 respectively) is not active at height h is the root of its empty tree;

  2. if h is at or after Sapling activation and before Heartwood activation, sapling_root equals the hashFinalSaplingRoot field of B's header;

  3. if h + 1 is at or after Heartwood activation, the header at height h + 1 commits to the hashChainHistoryRoot of the chain history tree after appending B, computed as specified in ZIP 221 and ZIP 258 with the supplied roots as B's tree roots, or to all zero bytes if that header's block activates Heartwood. [4] [7] If that header's commitment is hashBlockCommitments, the node MUST compute it with auth_data_root as hashAuthDataRoot, and MUST reject the entry if auth_data_root is absent. [6]

A node MUST NOT use an entry that fails these checks, and MAY disconnect the peer that sent it.

auth_data_root does not authenticate the next block's transactions. A node MUST check that block's authorizing data root against a verified auth_data_root; if they differ, the block is invalid, not the entry.

#Rationale

The final block hash anchors the requested range, including when the answer is a prefix.

Refusals let a requester try another peer at once instead of waiting for a timeout.

From NU5, a header commits to the history tree of the preceding blocks together with its own block's hashAuthDataRoot. [6] Supplying that digest lets a node verify an entry without the next block's authorizing data, and tell an invalid entry from an invalid block.

4000 entries with auth_data_root take 516,004 bytes, within ZIP 204's 2 MiB message limit.

#Security Considerations

The request does not anchor the successor at height end + 1. A peer whose chain diverges there can supply an entry for height end that fails check 3 and be penalized.

Root authentication does not ensure availability. A node that has stopped updating its trees depends on peers serving roots until it obtains frontiers.

#Deployment

This ZIP changes no consensus rules or existing messages. Bit 3 is also proposed for this capability by the version 2 draft [11]; its allocation requires agreement with that draft and the ZIP Editors.
