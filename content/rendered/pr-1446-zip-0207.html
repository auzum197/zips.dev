#Abstract

This proposal specifies a mechanism to support funding streams, distributed from a portion of the block subsidy for a specified range of block heights.

This is intended as a means of implementing the Zcash Development Fund, using the funding stream definitions specified in ZIP 214 [19]. It should be read in conjunction with ZIP 1014 [25], which describes the high-level requirements for that fund.

Revision 2 preserves the approximate duration and value of each address period when NU7 reduces the target block spacing to 25 seconds.

#Motivation

Motivation for the Zcash Development Fund is considered in ZIP 1014 [25].

This ZIP 207 was originally proposed for the Blossom network upgrade, as a means of splitting the original Founders’ Reward into several streams. It was then withdrawn when such splitting was judged to be unnecessary at the consensus level. Since the capabilities of the funding stream mechanism match the requirements for the Zcash Development Fund, the ZIP was reintroduced for that purpose in the Canopy upgrade in order to reuse specification, analysis, and implementation effort.

As of NU6, ZIP 1015 [26] directs part of the block subsidy to a reserve, the distribution of which is to be determined via a future ZIP. ZIP 2001 [27] modified this ZIP to augment the funding stream mechanism with a common mechanism to implement this proposal. ZIP 271 [24] specifies a one-time disbursement from this reserve at NU6.1 activation, which is deducted from the Deferred Development Fund Chain Value Pool Balance.

#Requirements

The primary requirement of this ZIP is to provide a mechanism for specifying the funding streams that are used in ZIP 214 [19] to implement the Zcash Development Fund. It should be sufficiently expressive to handle both the main three "slices" (BP, ZF, and MG) defined in ZIP 1014 [25], and also (with additional funding stream definitions) the "direct grant option" described in that ZIP.

As for the original Founders’ Reward, a mechanism is provided to allow addresses for a given funding stream to be changed on a roughly-monthly basis, so that keys that are not yet needed may be kept off-line as a security measure.

#Specification

#Revisions

  • Revision 0: The initial version of this specification, as agreed upon by the Zcash community in ZIP 1014 [25].

  • Revision 1: Adds the Deferred Development Fund Chain Value Pool Balance as a potential recipient of funding stream outputs, as agreed upon by the Zcash community in ZIP 1015 [26] and specified in ZIP 2001 [27].

  • Revision 2: Extends the remaining address period at NU7 activation and subsequent address periods in proportion to the change in target block spacing specified in ZIP 218 [20], and permits transparent P2PKH addresses per ZIP 2008 [28].

#Funding streams

A funding stream is defined by a block subsidy fraction (represented as a numerator and a denominator), a start height (inclusive), an end height (exclusive), and a sequence of recipients as defined below.

By defining the issuance as a proportion of the total block subsidy, rather than absolute zatoshis, this ZIP dovetails with any changes to both block target spacing and issuance-per-block rates. Such a change occurred at the Blossom network upgrade, for example. [15]

An active funding stream at a given block height is defined as a funding stream for which the block height is less than its end height, but not less than its start height.

The value of each funding stream is paid to one of a pre-defined set of recipients, depending on the block height.

As of Revision 0, each recipient MUST be the string encoding of a transparent P2SH address or Sapling address (as specified in [6] or [7]).

As of Revision 1, each recipient identifier MUST be either the string encoding of a transparent P2SH address or Sapling address (as specified in [6] or [7]) or the identifier 𝖣 𝖤 𝖥 𝖤 𝖱 𝖱 𝖤 𝖣 _ 𝖯 𝖮 𝖮 𝖫 . The latter, added in the NU6 network upgrade [22], indicates that the value is to be paid to a reserve to be used for development funding, the distribution of which is to be determined via a future ZIP.

As of Revision 2, each recipient identifier MUST be either the string encoding of a transparent P2PKH or P2SH address or of a Sapling address (as specified in [6] or [7]) or the identifier 𝖣 𝖤 𝖥 𝖤 𝖱 𝖱 𝖤 𝖣 _ 𝖯 𝖮 𝖮 𝖫 .

#Consensus rules

Prior to activation of the Canopy network upgrade, the existing consensus rule for payment of the original Founders’ Reward is enforced. [11]

Once the Canopy network upgrade activates:

  1. The existing consensus rule for payment of the Founders’ Reward [11] is no longer active. (This would be the case under the preexisting consensus rules for Mainnet, but not for Testnet.)

  2. The coinbase transaction in each block MUST contain at least one output per active funding stream that pays the stream's value in the prescribed way to the stream's recipient address for the block's height.

  3. The recipient 𝖿 𝗌 . 𝖱 𝖾 𝖼 𝗂 𝗉 𝗂 𝖾 𝗇 𝗍 ( 𝗁 𝖾 𝗂 𝗀 𝗁 𝗍 ) of a funding stream 𝖿 𝗌 at block height 𝗁 𝖾 𝗂 𝗀 𝗁 𝗍 is as defined in Funding streams.

  4. The "prescribed way" to pay a transparent P2SH address is to use a standard P2SH script of the form OP_HASH160 RedeemScriptHash OP_EQUAL as the scriptPubKey [29], where RedeemScriptHash is the 20-byte script hash in the raw encoding of the address [6].

    As of Revision 2, the "prescribed way" to pay a transparent P2PKH address is to use OP_DUP OP_HASH160 <keyHash> OP_EQUALVERIFY OP_CHECKSIG as the output's scriptPubKey, where <keyHash> is the direct push of the 20-byte public-key hash decoded from the recipient's Base58Check address. No other script encoding satisfies this funding-stream payment rule.

  5. The "prescribed way" to pay a Sapling address is as defined in [18]. That is, all Sapling outputs in coinbase transactions (including, but not limited to, outputs for funding streams) MUST have valid note commitments when recovered using a 32-byte array of zeroes as the outgoing viewing key. In this case the note plaintext lead byte MUST be 𝟎 𝐱 𝟎𝟐 , as specified in [17].

Once the NU6 network upgrade activates:

  • Rule 2 above is replaced by: In each block with coinbase transaction 𝖼 𝖻 at block height 𝗁 𝖾 𝗂 𝗀 𝗁 𝗍 , for each funding stream 𝖿 𝗌 active at that block height with a recipient identifier other than 𝖣 𝖤 𝖥 𝖤 𝖱 𝖱 𝖤 𝖣 _ 𝖯 𝖮 𝖮 𝖫 given by 𝖿 𝗌 . 𝖱 𝖾 𝖼 𝗂 𝗉 𝗂 𝖾 𝗇 𝗍 ( 𝗁 𝖾 𝗂 𝗀 𝗁 𝗍 ) , 𝖼 𝖻 MUST contain at least one output that pays 𝖿 𝗌 . 𝖵 𝖺 𝗅 𝗎 𝖾 ( 𝗁 𝖾 𝗂 𝗀 𝗁 𝗍 ) zatoshi in the prescribed way to the address represented by that recipient identifier, distinct from the outputs counted for every other such funding stream and for the lockbox disbursement outputs required by ZIP 271 [24].

Note: The outputs required by rule 2 before NU6 activation are likewise distinct for each funding stream. In particular, a single output cannot be counted for two active funding streams that have the same recipient and the same value.

Rule 5 has subsequently been clarified as follows:

  • The "prescribed way" to pay a Sapling or Orchard address is as defined in [18], using the post-Heartwood consensus rules specified for shielded outputs of coinbase transactions in [8]. A Sapling address is paid by a Sapling-pool output. An Orchard address is paid by an Orchard-pool output before NU6.3 activation, and by an Ironwood-pool output from NU6.3 activation onward, since coinbase transactions can then contain no Orchard-pool component [18].

Note: The recipient identifiers permitted above do not include Orchard addresses; the "prescribed way" to pay an Orchard address is defined in anticipation of a future change. Up to and including NU7 there have been no funding streams defined with a shielded payment address as a recipient. That might change in future, so implementations are encouraged to support Sapling and Orchard addresses as recipients, as permitted by [18].

These rules are reproduced in [12].

#Deployment

This proposal was initially deployed with Canopy. [21]

Changes to support deferred funding streams were deployed with NU6. [22]

Revision 2 is intended to activate with NU7 as specified in ZIP 259 [23].

#Backward compatibility

This proposal intentionally creates what is known as a "bilateral consensus rule change". Use of this mechanism requires that all network participants upgrade their software to a compatible version within the upgrade window. Older software will treat post-upgrade blocks as invalid, and will follow any pre-upgrade consensus branch that persists.
