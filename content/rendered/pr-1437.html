#Terminology

The key words "MUST", "MUST NOT", and "SHOULD" in this document are to be interpreted as described in BCP 14 1 when, and only when, they appear in all capitals.

The terms "block chain", "consensus branch", and "network upgrade" follow ZIP 200. 2 The character § refers to sections of the Zcash Protocol Specification. 3

"Block target spacing" means the interval between blocks targeted by the difficulty adjustment algorithm. Actual block intervals vary.

The "25-second baseline" means the rules after NU7, including ZIP 218's 25-second target spacing and ZIP 237's subsidy definitions. 4 5

A "stale block" is a valid mined block that does not remain on the selected chain. This document reports "stale blocks per accepted block" separately from the fraction of all mined blocks that become stale.

"Reach 90%" means the time for a block to reach 90% of the specified node sample. "Effective old-tip mining time" means the accumulated mining work spent on the old tip, expressed as seconds of the whole network's mining power.

MB means 1,000,000 bytes.

#Abstract

This proposal reduces block target spacing from 25 to 20 seconds in a network upgrade after NU7. It builds on ZIP 218 without changing its action limits or block size limit. 4 6

The change reduces the expected wait for a first confirmation by 20%. With unchanged per-block limits, it increases maximum transaction throughput by 25%. Nodes and wallets must process 25% more blocks per unit time, increasing worst-case block processing time and sync cost. It adjusts the difficulty averaging window, issuance parameters, and duration-based node defaults to the new spacing. Shorter inclusion intervals can expose finer transaction timing information.

#Motivation

A 20-second target reduces the expected wait for a first confirmation by five seconds. With unchanged per-block limits, it increases maximum transaction throughput by 25%. The additional blocks increase worst-case block processing time and sync cost per unit time. This proposal evaluates that incremental trade-off from ZIP 218's baseline.

#Privacy Implications

ZIP 218 identifies timing and anchor-depth privacy effects. 4 Shorter blocks give observers finer timing information without changing what individual shielded transactions reveal.

A three-block anchor depth spans an expected 60 seconds instead of 75. A rollback past the anchor invalidates the transaction. A replacement spending the same notes exposes the same nullifiers, linking the two transactions. Ordinary stale-block measurements do not bound rollback depth.

#Requirements

  • Reduce target spacing from 25 to 20 seconds after NU7.
  • Preserve approximately the difficulty averaging duration and issuance schedule, including partial halving intervals, subject to integer rounding.
  • Preserve historical consensus rules and integrate the transition with ZIP 237 and active funding-stream schedules.

For example, at halving index 3 the scheduled subsidy changes from 26,041,666 zatoshi to 20,833,333 zatoshi. Flooring 26,041,666×4/5 would incorrectly produce 20,833,332 zatoshi.

#Action limits

This proposal does not change ZIP 218's action limits, global shielded budget, or block size limit. Implementations MUST continue to enforce them.

#Minimum difficulty blocks on Testnet

Retain ZIP 218's 450-second elapsed-time threshold after this upgrade. A block qualifies only if its timestamp is strictly more than 450 seconds after the preceding block's timestamp. In that case its nBits MUST equal 𝖳𝗈𝖢𝗈𝗆𝗉𝖺𝖼𝗍(𝖯𝗈𝖶𝖫𝗂𝗆𝗂𝗍), following ZIP 218.

At and after A20, this fixed threshold replaces the expression 18⋅𝖯𝗈𝖶𝖳𝖺𝗋𝗀𝖾𝗍𝖲𝗉𝖺𝖼𝗂𝗇𝗀(h). Thus 450 seconds does not qualify, while 451 seconds does. This rule does not affect Mainnet. Existing timestamp-validity bounds and local-clock tolerances remain unchanged. The Testnet minimum-difficulty exception remains subject to those rules.

#Transaction expiry

Wallets SHOULD increase the default expiry delta from 120 to 150 blocks. Choose the default using the transaction's target height, which is the next block height after the chain tip. Use 150 when that height is at or above A20; otherwise retain the prior default. Compute expiry relative to the target height as specified by ZIP 218. Wallets SHOULD preserve an explicit user-configured delta across activation.

#Rationale

#Capacity and resource costs

With unchanged per-block limits, nodes and wallets must process 25% more blocks per unit time. If per-block processing time remains unchanged, the worst-case proportion of time spent processing blocks increases by 25%. Syncing blocks produced during a given time offline also requires 25% more work. Maximum two-action Orchard throughput rises from 6.6 to 8.25 transactions per second. ZIP 218's compact-field model rises from approximately 169.10 to 211.38 MB/day; it excludes serialization and transport overhead. 4

This figure describes worst-case compact sync bandwidth when blocks fill the shielded action budget. It does not establish a daily download requirement for every wallet.

Ironwood wallet bandwidth constrains the choice of its per-block action limit. This draft retains ZIP 218's limit; it does not increase that limit to obtain more throughput. Shorter target spacing still increases the maximum number of actions per day by 25%. Retaining the per-block limit therefore does not preserve the existing daily bandwidth bound.

Open design item: evaluate a lower Ironwood per-block action limit against a wallet bandwidth budget. Account for the private information retrieval (PIR) query design and measure its download costs before selecting a limit. The compact-field estimate alone does not establish those query costs.

#Stale blocks and effective propagation time

Following ZIP 218's propagation analysis, we estimate stale blocks per accepted block as the work-weighted time miners remain on the old tip divided by target spacing: ϕ=τeff/T. 4 8

The Zebra-only devnet data accompanying the propagation report contains 621 block hashes at heights of at least 400 with bodies of at least 1,990,000 bytes. This near-full-block sample has a mean reach-90% time of 1.55994 seconds. 8

The mixed-client experiment uses 80 geographically distributed nodes: 40 run Zakura and 40 run Zebra. TODO: identify the mixed-run dataset and report its reach-90% measurement. The 1.56-second input below comes from the Zebra-only sample and has not been established for the mixed run.

Effective old-tip mining time accumulates the mining work still spent on the old tip during propagation. For example, half the network mining the old tip for one second contributes 0.5 effective seconds.

If dissemination rises linearly from 0% to 90% over 1.56 seconds, the old-tip mining share falls from 100% to 10%. Its average is 55%, giving:

τeff≈1.56×0.55=0.858 seconds.

At 20 seconds, this gives ϕ≈0.858/20=4.29%. It assumes nodes represent mining work and omits any material tail after reaching 90%. Remaining old-tip mining after that percentile adds to the effective time.

Under Poisson discovery, the chance of another block anywhere within 1.56 seconds is 1−e−1.56/20≈7.50%. That includes blocks found by miners who already received the new tip. The effective-time model counts only old-tip work. Its probability of at least one competitor is 1−e−0.858/20≈4.20%, distinct from the expected count of 4.29%.

ZIP 218 reports a 3.26% propagation-based estimate at 25 seconds. 4 Holding that effective delay fixed gives 4.08% at 20 seconds. The near-full-block filter gives 4.29% under the same model. The difference reflects the sample filter, rather than a different scaling rule.

#Difficulty averaging duration

ZIP 218's 102-block window at 25 seconds spans an expected 2,550 seconds. The equivalent count at 20 seconds is 127.5 blocks. This proposal rounds up to 128, giving 2,560 seconds, about 0.39% longer. A 127-block window would give 2,540 seconds. Keeping 102 blocks would shorten the duration to 2,040 seconds.

This proposal preserves the averaging duration because mining hash rate can vary. Reducing that duration would change the DAA's response to hash rate changes as well as changing block target spacing.

#Issuance and schedule continuity

The interval change preserves its expected duration:

6,300,000×20=5,040,000×25 seconds.

The halving formula retains progress through the 25-second era. Scaling the unrounded scheduled subsidy by 4/5 preserves the expected issuance rate before rounding. Integer rounding changes the realized schedule.

The NSM fraction changes from 1375/1010 to 1100/1010, also a factor of 4/5. ZIP 237's ceiling and evolving balance mean this does not establish exact equality of reissuance per unit of wall-clock time.

Open specification item: amend the funding-stream end heights and address period calculations in ZIPs 207 and 214 for a second spacing transition. 9 10 Preserve fractional progress through the active address period and define integer-boundary rounding. Keep ended streams ended and ensure recipient lists cover every extended period. The deployment height and schedule amendments must be settled together; changing NU7 constants retroactively is invalid.
