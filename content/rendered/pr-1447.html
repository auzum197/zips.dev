#Terminology

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", and "MAY" in this document are to be interpreted as described in BCP 14 1 when, and only when, they appear in all capitals.

The character § is used when referring to sections of the Zcash Protocol Specification. 2

The terms "Mainnet" and "Testnet" are to be interpreted as described in § 3.12 ‘Mainnet and Testnet’. 3

The terms "best valid block chain" and "block height" are to be interpreted as described in § 3.3 ‘The Block Chain’ 4, and the term "coinbase transaction" as described in § 3.11 ‘Coinbase Transactions’. 5

The term "network upgrade" is to be interpreted as described in ZIP 200. 6

The terms "coinbase bundle", "nMinerSignals", "vMinerSignals", "signalCode", "levelOfSupport", and "pollDigest" are to be interpreted as described in ZIP 248. 7

The terms below are to be interpreted as follows:

Miner Poll
A poll of miners conducted as specified in this ZIP.
Ecosystem Poll
A poll of some part of the Zcash community, other than miners, on a question such as the scope or timing of a network upgrade.
Poll Coordinator
The party that constructs and publishes the Poll Definition of a Miner Poll.
Poll Definition
The JSON document that specifies a Miner Poll; see [Poll Definitions].
Canonical Encoding
The byte sequence obtained from a Poll Definition by the procedure in [Canonical Encoding and Poll Digest].
Poll Digest
The BLAKE2b-128 hash of the Canonical Encoding of a Poll Definition, which identifies the Poll Definition in coinbase transactions.
Option Code
An integer from 1 to 255 that identifies one option of one question of a Poll Definition.
Level of Support
An integer from 0 to 255 that a miner assigns to an option. 0 means that the miner does not rate the option; from 1 to 255, a greater Level of Support means greater support.
Miner Ballot
The Poll Digest and the list of (Option Code, Level of Support) pairs carried by the coinbase bundle of a block; see [Miner Ballots].
Voting Period
The inclusive range of block heights in which Miner Ballots for a Poll Definition are counted, from the Voting Start Height to the Voting End Height.
Participation Threshold
The minimum share of the blocks in a Voting Period that rate at least one option of a question, for the result of that question to be considered representative of miners.

#Abstract

This proposal specifies a mechanism for polling miners. A Poll Definition is a JSON document that gives a set of questions, an Option Code for each option, a Voting Period fixed in block heights, and the method by which the responses to each question are to be interpreted. A normalization procedure maps the Poll Definition to a Canonical Encoding, whose BLAKE2b-128 hash is its Poll Digest.

A miner votes by putting the Poll Digest and a Level of Support for each option it rates into the miner signalling fields of the coinbase bundle defined in ZIP 248, in each block it mines within the Voting Period. Each block in the Voting Period is one ballot. Anyone can compute the result from the block chain and the Poll Definition.

This ZIP does not specify who holds Miner Polls or what weight their results carry. It RECOMMENDS that whoever coordinates an Ecosystem Poll also publish a Poll Definition with the same questions, so that miners can be polled alongside.

#Motivation

The scope of network upgrades is decided with input from polls of parts of the Zcash community; for example, ZIP 259 cites the results of polls held for NU7. 8 9 Miners are currently not polled, although network upgrades affect them directly. NU7 changes the block target spacing and the block subsidy per block 10, and removes 60% of transaction fees from circulation 11. An upgrade also activates safely only if miners run node software that supports it.

Miners already have the ability to put free-form text in coinbase transactions, but without a common format that text cannot be tallied. This ZIP proposes that the coinbase bundle defined by ZIP 248 include structured miner signalling fields, and gives those fields a meaning: it specifies how a poll is defined and identified, how a miner responds to it, and how responses are interpreted. Because the Poll Definition commits to the method of interpretation of each question, the result of a Miner Poll is determined by the Poll Definition and the block chain, and should be interpreted using those semantics after miners have voted.

#Privacy Implications

Miner Ballots are public by design and linked to the blocks that carry them and to their coinbase outputs. Coinbase transactions are already linked to the blocks that contain them, so a Miner Ballot reveals only the miner's ratings.

A Miner Poll has no ballot secrecy: the positions of mining pools and solo miners become public. A mining pool votes with its hashers' work; individual hashers are not identified, and their preferences are not recorded.

#Requirements

  • A Miner Ballot identifies, unambiguously and compactly, the exact Poll Definition to which it responds.
  • Two Poll Definitions that differ only in JSON formatting, member order, or Unicode normalization form have the same Poll Digest.
  • The Poll Definition commits to how the responses to each question are interpreted.
  • Miners can express graded support for each option, and can decline to rate an option.
  • Every block counts as a single ballot.
  • The result is fully determined by the Poll Definition and public block chain data.
  • A Miner Poll can ask the same questions, with the same options, as an Ecosystem Poll.

#Non-requirements

  • Specifying who holds Miner Polls, when they are held, or what weight their results carry.
  • Ballot secrecy for miners.
  • A binding effect of the results, or activation signalling enforced by consensus.
  • Separate representation of hashers within a mining pool.
  • Miner Polls in blocks whose coinbase transaction does not use the transaction format of ZIP 248.

#Poll Definitions

A Poll Definition is a JSON text 12 that conforms to I-JSON 13 and is a single JSON object with the following members:

votingStartHeightintegerThe Voting Start Height, from 1 to 499999999.
votingEndHeightintegerThe Voting End Height, from votingStartHeight to 499999999.
participationThresholdBasisPointsintegerThe Participation Threshold, in hundredths of a percent, from 0 to 10000.
questionsarrayOne or more questions, each a JSON object as below.

Each question is a JSON object with the following members:

MemberTypeMeaning

descriptionstringFurther explanation of the question; MAY be empty.
tallyobjectThe method of interpretation of the question, as below.
optionsarrayTwo or more options, each a JSON object as below.

The tally object of a question has the following members:

MemberTypeMeaning

winnersintegerThe number of options to be chosen, from 1 to one less than the number of options of the question.

Each option is a JSON object with the following members:

MemberTypeMeaning

In addition:

  • Each object MUST have exactly the members listed for it.
  • Every number MUST be written as an integer, without a fraction or exponent part.
  • The Option Codes of all options of all questions MUST be distinct. A Poll Definition therefore has at most 255 options in total.

#Canonical Encoding and Poll Digest

The Canonical Encoding of a Poll Definition is computed as follows:

  1. Parse the Poll Definition as I-JSON. If it is not valid UTF-8, is not valid JSON, has an object with two members of the same name, or has a string that contains an unpaired surrogate, it is not a valid Poll Definition.
  2. Replace each string value by its Normalization Form C (NFC). 15
  3. Check the result against the requirements of [Poll Definitions]. If it does not meet them, it is not a valid Poll Definition.
  4. Serialize the result with the JSON Canonicalization Scheme (JCS) 16, and encode it as UTF-8.

The Poll Digest of a Poll Definition is the 16-byte BLAKE2b-128 hash 17 of its Canonical Encoding, with the 16-byte personalization string "Zcash_MinerPoll_". When a Poll Digest is written as text, it is written as 32 lowercase hexadecimal digits, in the order of the bytes of the hash output.

Since every member name is an ASCII string and every number is an integer, JCS reduces to the following for a Poll Definition: members of each object are sorted by name, no whitespace is emitted outside strings, integers are written in decimal without leading zeros, and strings are escaped as by ECMAScript's JSON.stringify.

Any change to a Poll Definition other than its formatting, member order, or Unicode normalization changes its Poll Digest. A Miner Ballot therefore commits to the questions, options, Voting Period, Participation Threshold, and method of interpretation of the Poll Definition to which it responds.

#Miner Ballots

A miner casts a Miner Ballot for a Poll Definition P in a block it mines at a height within the Voting Period of P by setting the miner signalling fields of the coinbase bundle of that block's coinbase transaction as follows:

  • pollDigest is the Poll Digest of P;
  • for each option of P that the miner rates, vMinerSignals has one entry whose signalCode is the Option Code of that option and whose levelOfSupport is the miner's Level of Support for it.

vMinerSignals SHOULD NOT have entries whose levelOfSupport is 0; such an entry has the same effect as no entry. ZIP 248 requires the entries to be in strictly ascending order of signalCode.

Since each block counts separately, a miner MAY change its Miner Ballot during the Voting Period. A miner that wants its Miner Ballot to count in proportion to its hashrate SHOULD include it in every block it mines during the Voting Period. A mining pool that casts Miner Ballots SHOULD publish its Miner Ballot to its hashers before the Voting Start Height.

#Preparing a Miner Ballot

Software that prepares Miner Ballots SHOULD:

  1. load a Poll Definition from a file, and reject it if it is not a valid Poll Definition;
  2. compute and display its Poll Digest, so that the miner can compare it with the Poll Digest published by the Poll Coordinator;
  3. display the network, the Voting Period, and each question with its description, its options, and its method of interpretation, including its number of winners;
  4. for each option, let the miner choose a Level of Support from 0 to 255, with 0 as the default;
  5. include the resulting Miner Ballot only in the coinbase transactions of blocks on the network of the Poll Definition, at heights within its Voting Period.

This ZIP does not specify how such software stores a miner's ratings, or how it configures the software that constructs coinbase transactions.

#Determining the Miner Ballot of a Block

For a Poll Definition P and a block B at a height within the Voting Period of P, B has a Miner Ballot for P if and only if:

  • the coinbase transaction of B has a coinbase bundle;
  • nMinerSignals is greater than 0, and pollDigest equals the Poll Digest of P;
  • each signalCode in vMinerSignals is an Option Code of P; and
  • at least one levelOfSupport in vMinerSignals is nonzero.

If B has a Miner Ballot for P, then LB,o, the Level of Support of B for option o, is the levelOfSupport of the entry whose signalCode is the Option Code of o, or 0 if there is no such entry. If B has no Miner Ballot for P, then LB,o=0 for every option o.

Blocks before the activation of ZIP 248 on the network of P have no coinbase bundle, and so have no Miner Ballot.

#Interpretation of Results

The result of a Miner Poll is defined over the best valid block chain of the network of its Poll Definition, once that chain contains the block at the Voting End Height. Parties that compute the result SHOULD wait until the block at the Voting End Height has at least 100 confirmations.

Let N be the number of blocks in the Voting Period, i.e. Voting End Height − Voting Start Height + 1, and let V be the set of blocks in the Voting Period. Each block in V is one ballot, regardless of who mined it or the value of its coinbase outputs. A block rates option o if LB,o>0; a block without a Miner Ballot rates no option.

A Miner Ballot gives each option a score, which is sufficient information to interpret the responses to a question by several voting methods. This ZIP RECOMMENDS STAR voting, and version 1 of the Poll Definition format supports only that method.

For a question q, let Aq be the number of blocks in V that rate at least one option of q. If Aq=0, q has no result. Otherwise, for a question whose tally has "method": "star" and "winners": W, the winners of q are chosen by W rounds of STAR voting 18, as follows. Let C be the set of options of q. In each round:

  1. Scoring. For each option o in C, let the score total So=∑B∈VLB,o.
  2. Finalists. A pair of distinct options {a,b} in C is a possible finalist pair if no option in C∖{a,b} has a score total greater than Sa or greater than Sb. If the score totals of the options in C are distinct, there is exactly one possible finalist pair; if score totals are equal, there can be several.
  3. Runoff. For a possible finalist pair {a,b}, let Ra,b be the number of blocks B in V with LB,a>LB,b, and Rb,a the number with LB,b>LB,a. The runoff winner of the pair is the option with the greater of these counts. If Ra,b=Rb,a, it is the option with the greater score total. If the score totals are also equal, the pair has no runoff winner.
  4. Winner. If every possible finalist pair has a runoff winner, and all of those runoff winners are the same option, that option wins the round, and is removed from C. Otherwise, the round is tied.

The winners of q are the winners of its rounds, in order. With W=1 this is single-winner STAR voting; with W>1 it is Bloc STAR voting. Since W is less than the number of options, C has at least two options in every round. If a round is tied, the result of q consists of the winners of the earlier rounds and the tied round, and later rounds are not computed.

The result computed as above is the interpretation to which the Poll Definition commits, but it informs the community's judgment rather than replacing it. For example, the winner of a runoff can have a much lower score total than the other finalist, and this ZIP cannot determine in advance how the community would judge such a result. Likewise, this ZIP does not specify how a tied round is resolved or interpreted, and that may differ from one Miner Poll to another. A Poll Coordinator MAY state, in the announcement at url, how it intends a tied round to be interpreted.

The result of q is representative of miners if and only if 10000⋅Aq/N is at least participationThresholdBasisPoints.

A published result of a Miner Poll SHOULD include:

  • the Poll Digest;
  • the height and hash of the block at the Voting End Height in the block chain that was tallied;
  • N, and the number of blocks in V that have a Miner Ballot;
  • for each option o, and each Level of Support ℓ from 1 to 255, the number of blocks B in V with LB,o=ℓ, where nonzero;
  • for each question q: Aq and the percentage 100⋅Aq/N; whether the result is representative; and, for each round, the score totals, the possible finalist pairs, their runoff counts, and the winner, or that the round is tied.

The counts of blocks by option and Level of Support determine everything else in the result, and are authoritative. Any percentage in a summary of the result SHOULD be relative to N.

#Recommendations for Poll Coordinators

When an Ecosystem Poll is coordinated, it is RECOMMENDED that the party coordinating it also act as Poll Coordinator for a Miner Poll that accompanies it, as follows:

  • The Poll Definition SHOULD have the same questions and options as the Ecosystem Poll, identical in wording and order, so that the results of the two polls can be compared. An explicit "Abstain" option of the Ecosystem Poll is an ordinary option.
  • A question for which the Ecosystem Poll allows a single selection SHOULD have "winners": 1. A question for which it allows up to k selections, such as the election of k members of a committee, SHOULD have "winners": k.
  • The Voting Period SHOULD coincide with the voting window of the Ecosystem Poll. To convert times to block heights, the Poll Coordinator SHOULD use the block target spacing in effect, accounting for any network upgrade scheduled to activate before the Voting End Height.
  • The Poll Coordinator SHOULD publish the Poll Definition, as a file, and its Poll Digest together with the announcement of the Ecosystem Poll, and at least 14 days before the block at the Voting Start Height is expected to be mined, so that mining pools have time to reconfigure.
  • The Poll Coordinator SHOULD NOT change a Poll Definition once it is published. To change it, the Poll Coordinator SHOULD publish a new Poll Definition, which has a different Poll Digest, before the block at the Voting Start Height of the original is mined, and state that it supersedes the original.
  • The Voting Periods of two Poll Definitions on the same network SHOULD NOT overlap, since a block carries at most one Poll Digest. Questions that would be asked in concurrent Miner Polls SHOULD be combined into a single Poll Definition.
  • The id of a Poll Definition SHOULD differ from the id of every earlier Poll Definition on the same network.
  • The Poll Coordinator SHOULD publish the result of the Miner Poll alongside the result of the Ecosystem Poll.

This ZIP does not specify what weight the result of a Miner Poll carries relative to the result of an Ecosystem Poll, or how the two are combined.

#Testnet-specific considerations

It is RECOMMENDED that a Miner Poll on Mainnet be rehearsed on Testnet. A Poll Definition on Testnet has "network": "testnet" and Testnet block heights, so its Poll Digest differs from that of any Poll Definition on Mainnet. A Poll Definition on Testnet that rehearses a Miner Poll on Mainnet SHOULD use the questions, options, and methods of interpretation of that Mainnet Poll Definition, so that miners rehearse the same ratings with the same tools.

#Rationale

#Rationale for separating mechanism from governance

Who polls miners, on what, and with what weight are matters for the Zcash community's governance processes, which change more often than a data format and a tally procedure should. This ZIP therefore specifies only the mechanism, and limits itself to recommendations on its use. Recommending that whoever coordinates an Ecosystem Poll also construct the Poll Definition keeps the questions of the two polls identical without assigning that role to any particular party.

#Rationale for counting blocks

The number of blocks mined approximates a miner's share of hashrate, and proof of work makes Sybil voting pointless, since more Miner Ballots require more work. Mining pools represent their hashers, who can switch pools if they disagree with their pool's Miner Ballot.

Blocks are not weighted by coinbase output value or timestamp, which keeps the tally independent of transaction fees, the block subsidy, and timestamps chosen by miners. A change to the block target spacing within a Voting Period changes the number of blocks per unit of time for all miners alike, so counting blocks still approximates share of hashrate.

Rented hashrate could buy an outcome at the cost of that hashrate, and public Miner Ballots make bribes verifiable; both are reasons why the results indicate sentiment and are not binding.

#Rationale for STAR voting

STAR (Score Then Automatic Runoff) voting uses a score ballot, which a Level of Support provides directly, and combines the expressiveness of score voting with a majoritarian runoff: the runoff gives the result to whichever finalist more ballots prefer, which reduces the incentive to exaggerate scores. Question 5 of the [Example] shows the runoff overriding the score totals. Bloc STAR voting, which repeats STAR voting with each winner removed, chooses several winners without a separate ballot format, so the same Miner Ballot can answer a question that has one winner and a question that has several. A Level of Support of 0 counts as the lowest possible score, as an unscored candidate does in STAR voting.

STAR voting is usually described with scores from 0 to 5. The scores here range from 0 to 255 because that is the range of levelOfSupport; a finer scale does not change the method.

The method of interpretation is part of the Poll Definition, and so is committed to by the Poll Digest, so that miners know before voting how their ratings will be used, and no one can choose a method after seeing the ratings. The method member allows later versions of this ZIP to add other methods.

A tie in the runoff is broken by score totals, as in STAR voting. Other ties are not broken. Breaking them by the order of the options would let whoever writes the Poll Definition favour an option, and breaking them with randomness derived from the block chain would let the miner of the last block of the Voting Period influence the outcome. Since a Miner Poll measures sentiment and does not decide anything, a tie is itself a meaningful result, and how to treat it is left to the community. A tie in score totals has no effect when every way of breaking it leads to the same winner, as in question 2 of the [Example], so it does not make the round tied. With tens of thousands of blocks in a Voting Period, ties that do affect the winner are unlikely except among options that few blocks rate.

#Rationale for the Participation Threshold

The winners of a question depend only on the blocks that rate its options, so a single miner could decide a question that few others answer. The Participation Threshold flags such results as unrepresentative. It applies to each question, since a Miner Ballot can leave a question unanswered, and it is given in basis points so that the Poll Definition contains only integers. The tally does not group blocks by miner, because coinbase outputs and pool tags are chosen by miners and do not reliably identify them.

#Rationale for coinbase bundle fields

Only the miner of a block controls its coinbase transaction, so proof of work authenticates the Miner Ballot. The miner signalling fields of ZIP 248 are structured, so a Miner Ballot is found without searching free-form text, cannot be confused with a pool tag, and does not take space from coinbaseData. A Miner Ballot for a poll with dozens of options is a few dozen bytes. Consensus requires only that signal codes be in ascending order, which gives each Miner Ballot a single encoding.

Three alternatives were rejected:

  • An ASCII ballot in the coinbase script or a shielded coinbase memo: it needs no consensus change, but a ballot has to be found by searching text that pool tags share, its length is limited by the space in the coinbase script, and it can express only choices, not scores.
  • Block header version bits: consensus only requires the block version number to be at least 4 19, but a bit expresses only yes or no.
  • Separate transactions: anyone can create them, and they are not tied to block production.

The cost of using the ZIP 248 fields is that Miner Polls are possible only after the network upgrade that deploys ZIP 248.

#Rationale for the Poll Digest

The Poll Digest binds a Miner Ballot to the exact text of the questions and options that the miner rated, and to the Voting Period, Participation Threshold, and methods of interpretation under which they will be tallied. Option Codes therefore need to be unique only within a Poll Definition, a miner still configured for a superseded or earlier Poll Definition never contributes to a later one, and a Poll Definition on Testnet never counts on Mainnet. Sixteen bytes make an accidental collision negligible; a deliberate collision gains nothing, since the Poll Coordinator publishes the Poll Definition and the Poll Digest together. The personalization string separates Poll Digests from other BLAKE2b hashes used in Zcash.

The Canonical Encoding makes the Poll Digest independent of how the Poll Definition was formatted, so that tools written in different languages compute the same Poll Digest from the same document. JCS is a published standard with implementations in many languages. Restricting the document to integers and ASCII member names avoids the parts of JCS that are hardest to implement: floating-point serialization and sorting by UTF-16 code units. NFC normalization makes strings that are canonically equivalent in Unicode, and therefore display identically, produce the same Poll Digest. Rejecting unknown members makes every byte of the Canonical Encoding meaningful to the tools that display the Poll Definition, so a miner can see everything its Miner Ballot commits to.

#Rationale for leaving tooling unspecified

Interoperability requires only that miners and tallying software agree on the Poll Definition and on the encoding of a Miner Ballot in the coinbase bundle. How a miner's ratings reach the software that constructs coinbase transactions differs between node implementations and mining setups, and needs no common format.

#Rationale for block-height Voting Periods

Block heights are deterministic, whereas block timestamps are chosen by miners. Changes to the block target spacing are accounted for when the Voting Period is chosen. The recommended 14-day notice period gives mining pools time to reconfigure.

#Deployment

Miner Polls depend on the miner signalling fields of the coinbase bundle defined in ZIP 248, and can be held only in blocks after the activation of the network upgrade that deploys ZIP 248.

#Reference implementation

None yet. A reference implementation is needed of:

  • software that prepares a Miner Ballot from a Poll Definition and includes it in coinbase transactions;
  • computation of the result of a Miner Poll.

#Open issues

  • Whether one poll per block is sufficient, or whether ZIP 248 should allow a coinbase bundle to carry signals for more than one Poll Digest.
  • Whether a proportional multi-winner method, such as Proportional STAR, should be offered in addition to Bloc STAR for questions such as committee elections.
  • Whether a Poll Definition should commit to how a tied round is to be interpreted, with leaving ties unresolved as one of the choices.
