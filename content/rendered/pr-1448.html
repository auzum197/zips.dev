#Terminology

The key words "MUST", "MUST NOT", and "SHOULD" in this document are to be interpreted as described in BCP 14 1 when, and only when, they appear in all capitals.

The terms "block chain", "consensus branch", and "network upgrade" follow ZIP 200. 2 Block and transaction encodings follow the Zcash Protocol Specification. 3

MB means 1,000,000 bytes. GB means 1,000,000,000 bytes. The existing block size limit is 2 MB; this proposal increases it to 3 MB.

"Orphan rate" means distinct observed stale blocks divided by the sum of canonical and observed stale blocks. Here, a stale block is a block outside the final agreed chain. The experiment below counts a block only if at least one node recorded a successful commit. It does not count every solved block that a miner discarded before submission.

"Reach 90%" means elapsed time from the miner's solution-ready event to decoded block availability at 72 of the experiment's 80 nodes, including the originating node at time zero.

#Abstract

This proposal increases the block size limit from 2,000,000 to 3,000,000 bytes (3 MB) in a network upgrade after NU7. It preserves ZIP 218's shielded action limits and shared shielded budget. 4 It also preserves the 2,000,000-byte transaction cap enforced by zcashd and the existing signature-operation limit.

The additional space primarily increases capacity for transparent transactions. It prepares the block byte budget for future shielded throughput without raising today's shielded scanning burden through an action-limit increase. A future proposal to increase shielded action limits would depend on adoption and operational validation of private information retrieval (PIR), with measured wallet bandwidth and privacy costs.

The proposal also changes block-message size negotiation so that upgraded peers can relay valid 3 MB blocks. It leaves block target spacing to separate proposals. Larger blocks increase full-node bandwidth, storage, and potential validation work.

#Motivation

ZIP 218 separates the block byte budget from the shielded action budget. The byte budget limits serialized data; the action budget limits shielded work and compact sync bandwidth. Its action limits do not apply to the transparent components of transactions. 4

Increasing the byte budget now allows more transparent transactions when bytes are the binding constraint. Increasing transparent throughput is an intermediate benefit, not Zcash's long-term scaling objective. Deploying and measuring larger blocks also prepares the network for future shielded throughput once wallets can handle it privately and efficiently.

This proposal separates those decisions. It increases block space while retaining all shielded action limits. PIR adoption does not automatically activate higher limits; any change requires a separate consensus proposal.

#Privacy Implications

This proposal does not change transaction disclosure, shielded proofs, or the information that transparent transactions expose. It does not encourage wallets to replace shielded transactions with transparent transactions.

At unchanged block target spacing, retaining the shielded action limits preserves ZIP 218's bound on compact shielded fields per block and per day. This does not bound every wallet download: transaction metadata, transparent queries, and full-transaction retrieval can add traffic. A separately activated spacing reduction would also increase the daily bound.

Longer block propagation can increase stale blocks and reorganization risk. Wallets should not reduce their confirmation or anchor-depth policies on the strength of the experiment below. The observed orphan rate does not establish a reorganization-depth bound.

#Requirements

  • Increase the maximum serialized block size to exactly 3 MB.
  • Preserve historical validity and all existing shielded action limits.
  • Preserve transaction-size, signature-operation, and script limits.
  • Support full-sized blocks through relay, synchronization, and mining.
  • Bound resource use before accepting untrusted block bodies.

Replace the fixed block size bound in § 7.6 'Block Header Encoding and Consensus' with the requirement that a block at height h MUST have encoded size at most 𝖡𝗅𝗈𝖼𝗄𝖲𝗂𝗓𝖾𝖫𝗂𝗆𝗂𝗍(h). 5

In the same section, qualify the comparison with Bitcoin's block size limit: Zcash's 2,000,000-byte limit applies below A; the 3,000,000-byte limit applies at or above A.

In ZIP 218's specification, replace the statement that the overall 2 MB block size limit continues to apply with a reference to 𝖡𝗅𝗈𝖼𝗄𝖲𝗂𝗓𝖾𝖫𝗂𝗆𝗂𝗍(h) after this proposal activates. ZIP 218's shielded action limits remain unchanged. 4

Encoded size includes the block header, its Equihash solution, the encoded transaction count, and every transaction, including the coinbase. It excludes the 24-byte P2P message header and storage or RPC wrappers. No field receives a size discount.

Validators MUST select the limit using the candidate block's height on its parent chain. The local tip height and the peer's advertised height MUST NOT determine consensus validity. Validators MUST retain the old limit below A, including during initial synchronization, side-chain validation, and reorganizations across activation.

#Transaction and computational limits

Define 𝖳𝗋𝖺𝗇𝗌𝖺𝖼𝗍𝗂𝗈𝗇𝖲𝗂𝗓𝖾𝖫𝗂𝗆𝗂𝗍:ℕ:=2,000,000 bytes. For every block at or above A, each transaction, including the coinbase, MUST have encoded size at most 𝖳𝗋𝖺𝗇𝗌𝖺𝖼𝗍𝗂𝗈𝗇𝖲𝗂𝗓𝖾𝖫𝗂𝗆𝗂𝗍. Pre-activation transaction rules remain unchanged.

The transaction bound remains independent of the block bound. The additional space admits more transactions. zcashd already enforces an explicit 2,000,000-byte transaction cap. The protocol specification states a 100,000-byte cap before Sapling; after Sapling, the block envelope also limits the size of any included transaction. This proposal makes the independent 2,000,000-byte post-activation transaction cap explicit, so increasing the block envelope does not admit larger individual transactions. 6 3

Implementations MUST continue to enforce ZIP 218's existing per-pool limits and shared global shielded budget. Orchard and Ironwood actions continue to consume the same shared budget. Extra transparent bytes do not exempt a mixed transaction's shielded components from those limits. 4

The block signature-operation limit remains 20,000, using the existing counting rules, including P2SH signature operations. Existing script limits and transaction-format bounds remain unchanged. 6

This proposal changes neither block target spacing nor the difficulty algorithm, issuance schedule, funding streams, transaction expiry, or coinbase maturity.

#Block relay and message framing

ZIP 204 currently limits each message payload to 2,097,152 bytes. That limit cannot carry a valid 3 MB block. Amend its 'Maximum Message Size' rules as follows. 7

Define 𝖳𝗁𝗋𝖾𝖾𝖬𝖡𝖯𝗋𝗈𝗍𝗈𝖼𝗈𝗅𝖵𝖾𝗋𝗌𝗂𝗈𝗇:ℕ, to be assigned by the deployment ZIP. For a connection whose negotiated protocol version is at least this value, the maximum block message payload is 3,000,000 bytes. For older negotiated versions, retain the 2,097,152-byte maximum. Other commands retain their existing payload and item-count limits.

Nodes MUST reject a declared payload length above the applicable maximum before allocating a buffer for that payload. A decoder MUST consume exactly one block from a block payload and reject trailing data, truncated fields, and invalid encodings. Existing checksum checks remain in force.

Upgraded nodes MUST support the larger block payload on upgraded connections even when their local tip is below A. They still apply the height-dependent consensus bound when validating the block. This permits initial synchronization and out-of-order delivery across activation without accepting oversized pre-activation blocks.

Senders MUST NOT send a payload above the peer connection's negotiated maximum. The deployment MUST update minimum peer versions and apply ZIP 201's upgrade peer-management rules so that upgraded nodes can retain compatible peers at activation. 8

#Mining and node interfaces

getblocktemplate MUST report sizelimit for the candidate height, normally one above the selected parent. Template selection MUST reserve space for the complete header, encoded transaction count, and completed coinbase. Miners MUST re-evaluate the limit when a parent change crosses activation.

Block submission and retrieval interfaces MUST support every otherwise-valid block within the applicable limit. This includes proposal validation, RPC submission, historical retrieval, and local block import. Hex-encoded RPC block data alone can occupy 6,000,000 characters; request limits also need room for the enclosing request.

Deserializers MUST distinguish the block envelope limit from transaction and field limits. Increasing the block limit MUST NOT implicitly increase tx, inventory, address, or header-message limits. Nodes SHOULD bound aggregate queued block bytes and decoded memory, rather than relying only on a count of blocks or connections.

This proposal does not increase mempool memory defaults or change ZIP 317's fee calculation. ZIP 401's cost limit remains a node resource policy, not a fixed entitlement to a number of full blocks. 9 10

#Rationale

#Choice of block size

The authors chose 3 MB as an attainable limit for current Zakura and Zebra Andale implementations while keeping orphan rates within a reasonable range. This is an engineering target, not a claim that 3 MB is an optimal threshold. The experiment below provides preliminary Zakura evidence near that size. Matched measurements across both clients remain necessary before deployment.

#Throughput and resource costs

The new byte budget is 3,000,000/2,000,000=1.5 times the old budget, an increase of 50%. Transaction throughput depends on the workload. Transparent transactions can use the additional space, but signature operations, script execution, and UTXO access can become binding constraints. Action-limited shielded workloads do not receive a corresponding increase in transactions per block.

The following bounds assume every canonical block reaches 3 MB and blocks arrive at the stated target spacing:

Target spacingRaw block payload rateRaw block data per dayCapacity relative to 2 MB at 25 seconds
25 seconds120,000 bytes/second10.368 GB1.5×
20 seconds150,000 bytes/second12.96 GB1.875×

These figures exclude repeated relay, stale blocks, transport overhead, indexes, and state growth. They describe full-block traffic, not light-wallet compact sync. Disk and memory costs can grow differently from serialized bytes, especially for blocks with many small transparent outputs.

Keeping the 20,000 signature-operation limit bounds counted operations; it does not bound all validation work. Transparent-heavy blocks require measurements of script execution, UTXO reads and writes, memory, and validation-to-mining-tip latency.

#Propagation experiment

A November 2026 private-network experiment used 80 Zakura nodes across 12 regions at a 20-second target spacing. Blocks filled twice ZIP 218's normal shielded action limit: 660 Ironwood actions. The measured blocks occupied 3,026,379 bytes, approximately 3 MB and slightly above the proposed limit. 11

#Validation benchmarks

The original Zcash block-size increase prompted analysis of verification costs across different input/output mixes. 12 A fixed signature-operation limit does not capture every validation cost.

#Separating block space from shielded action limits

Shielded wallet bandwidth remains the constraint on increasing Ironwood actions. The experiment tests propagation under a heavier shielded workload; it does not demonstrate that wallets can afford that workload.

A future action-limit proposal should follow PIR adoption and operational testing. It should quantify query bandwidth, server cost, privacy assumptions, failure behavior, and wallet recovery costs. This ZIP creates neither an automatic action-limit increase nor an exception for PIR-enabled wallets.

#Deployment

Deploy through a network upgrade after NU7. A deployment ZIP will assign activation heights, consensus branch IDs, and the new protocol version. This proposal can activate with a separately specified spacing change, but does not require a 20-second target.

Before advancing to Proposed status, publish reproducible experiment inputs and resolve the deployment assignments. Validate the byte and computational boundaries across independent clients. Run matched 3 MB transparent and mixed workloads at the selected spacing, including constrained bandwidth, propagation tails, stale blocks, UTXO growth, and mining-tip adoption.
