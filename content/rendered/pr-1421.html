#Terminology

The key words "MUST", "MUST NOT", "SHOULD", and "MAY" in this document are to be interpreted as described in BCP 14 1 when, and only when, they appear in all capitals.

The character § is used when referring to sections of the Zcash Protocol Specification. 2

The terms "Mainnet" and "Testnet" are to be interpreted as described in § 3.12 ‘Mainnet and Testnet’. 3

The terms "best valid block chain" and "block height" are to be interpreted as described in § 3.3 ‘The Block Chain’ 4, and the term "coinbase transaction" as described in § 3.11 ‘Coinbase Transactions’. 5

The term "network upgrade" is to be interpreted as described in ZIP 200. 6

The term "Zcash Community Advisory Panel" (or "ZCAP") is to be interpreted as described in ZIP 1015. 7

The terms below are to be interpreted as follows:

Election : A round of sentiment polling on the scope or timing of one or more upcoming network upgrades, consisting of a ZCAP Poll and the Miner Poll specified in this ZIP.

ZCAP Poll : The poll of ZCAP members held for an Election. 8

Miner Poll : The poll of miners held for an Election, as specified in this ZIP.

Poll Organizer : The ZCAP, as the organizer of the ZCAP Poll of an Election.

Poll Definition : The document that specifies a Miner Poll; see [Poll Definitions].

Election Identifier : The short string that identifies an Election in Miner Ballots.

Voting Period : The inclusive range of block heights in which Miner Ballots for an Election are counted, from the Voting Start Height to the Voting End Height.

Miner Data : The bytes of the script of the transparent input of a coinbase transaction that follow the encoding of the block height required by § 7.1.2 ‘Transaction Consensus Rules’. 9

Coinbase Memo : The memo field of a shielded output of a coinbase transaction, as recovered by decrypting the output using a sequence of 32 zero bytes as the outgoing viewing key, as specified in § 4.20.3 ‘Decryption using an Outgoing Viewing Key (Sapling and Orchard)’. 10 11

Miner Ballot : A string that encodes a miner's answers to the questions of an Election; see [Miner Ballots].

Answer Character : A byte that is an ASCII digit 1 to 9, an uppercase ASCII letter A to Z, or a hyphen -.

Participation Threshold : The minimum percentage of the blocks in a Voting Period that answer a question, for the Miner Poll results on that question to be considered representative of miners.

#Abstract

This proposal specifies a process for gauging miners' sentiment on upcoming network upgrades. For each Election, miners answer the same questions, with the same options, as the ZCAP.

A miner votes by including a compact ASCII Miner Ballot in the coinbase transaction of each block it mines within a Voting Period, which the community agrees upon through public review and which is fixed in block heights in advance. The Miner Ballot goes in the Miner Data of the coinbase script or in a Coinbase Memo. Each block in the Voting Period is one vote, and a block without a valid Miner Ballot answers no question, so results are shares of all blocks in the Voting Period and approximate shares of hashrate. Anyone can compute them from the block chain.

Miner Poll results are published alongside ZCAP Poll results. Miner Ballots are public and linked to the blocks that carry them. No consensus change is required.

#Motivation

The scope of network upgrades is decided with input from polls of the ZCAP, whose NU7 results ZIP 259 cites. 12 Coinholder polls, such as the NU7 coinholder vote 13, are also held, but are not officially recognized.

Miners are not polled, although network upgrades affect them directly. NU7 changes the block target spacing and the block subsidy per block 14, and removes 60% of transaction fees from circulation 15. An upgrade also activates safely only if miners run node software that supports it.

Miners already put free-form text in coinbase transactions, and ZIP 213 anticipated identifying text in shielded coinbase memos 11, but without a common format that text cannot be tallied. A common encoding makes the tally reproducible by anyone, and asking the questions of the ZCAP Poll makes the results directly comparable.

#Privacy Implications

Miner Ballots are public by design and linked to the blocks that carry them and to their coinbase outputs. Coinbase outputs are already public: transparent outputs directly, and shielded outputs because they decrypt with the all-zero outgoing viewing key 11. A Miner Ballot therefore reveals only the miner's answers.

Unlike a ZCAP Poll, a Miner Poll has no ballot secrecy: the positions of mining pools and solo miners become public. A mining pool votes with its hashers' work; individual hashers are not identified, and their preferences are not recorded.

#Requirements

  • Miners can answer exactly the questions of the ZCAP Poll, with exactly its options.
  • Casting a Miner Ballot requires no consensus change or new transaction type.
  • Existing node software can cast Miner Ballots through string-valued configuration.
  • Every block counts as a single vote.
  • Support for each option is reported as a share of all blocks in the Voting Period, including blocks without a Miner Ballot.
  • The tally is fully determined by the Poll Definition and public block chain data.
  • The community agrees upon the Voting Period of each Election through public review, and the Voting Period is fixed in advance and unambiguous.
  • Miner Poll results are comparable with ZCAP Poll results.

#Non-requirements

  • Ballot secrecy for miners.
  • A binding effect of the results, or activation signalling enforced by consensus.
  • Separate representation of hashers within a mining pool.

#Specification

For each Election, the Poll Organizer MUST hold a Miner Poll on Mainnet as specified below.

#Poll Definitions

For each Election, the Poll Organizer MUST publish a Poll Definition on the Zcash Community Forum, in the announcement of the ZCAP Poll or in a post linked from it. A Poll Definition gives:

  • the Election Identifier;
  • the network (Mainnet or Testnet);
  • the Voting Start Height and the Voting End Height;
  • the questions, and the options for each question;
  • the Participation Threshold, as a percentage;
  • a link to the announcement of the ZCAP Poll.

The questions and options MUST be identical in wording, order, and number to those of the ZCAP Poll. Questions and the options of each question are numbered from 1 in order of appearance; an explicit "Abstain" option is an ordinary option. A question MUST NOT have more than 35 options, and an Election MUST NOT have more than 489 questions, so that every Miner Ballot fits in a 512-byte Coinbase Memo.

The Election Identifier MUST have 1 to 16 characters, each a lowercase ASCII letter a to z, an ASCII digit 0 to 9, or a hyphen -. It MUST NOT equal the Election Identifier of any earlier Poll Definition on the same network.

A published Poll Definition MUST NOT be changed. To change its questions, options, Voting Period, or Participation Threshold, the Poll Organizer publishes a new Poll Definition, which supersedes it and is subject to the requirements in [Voting Period]. A Poll Definition can only be superseded before the block at its Voting Start Height is mined, and a superseded Poll Definition is not tallied. Once the Voting Period of a Poll Definition has started, its Miner Poll MUST be tallied and its results published, even if a new Poll Definition is published afterward.

#Voting Period

The Voting Period consists of the block heights from the Voting Start Height to the Voting End Height inclusive. The Voting End Height MUST be greater than or equal to the Voting Start Height. The Voting Period of each Election is agreed upon as follows:

  1. The Poll Organizer proposes the Voting Period, together with the questions, in the announcement of the ZCAP Poll and invites feedback on the forum.
  2. The proposed Voting Period SHOULD coincide with the voting window of the ZCAP Poll. To convert times to block heights, the Poll Organizer SHOULD use the block target spacing in effect, accounting for any network upgrade scheduled to activate before the Voting End Height.
  3. After considering the feedback, the Poll Organizer publishes the final Poll Definition. Its Voting Period MUST have been proposed on the forum, as in step 1, at least 7 days earlier, so a Voting Period changed in response to feedback is proposed again. With the final Poll Definition, the Poll Organizer MUST answer on the forum each objection to the Voting Period raised during the feedback period, stating how it was addressed or why it was not. The final Poll Definition MUST be published at least 14 days before the block at the Voting Start Height is expected to be mined.

#Miner Ballots

A Miner Ballot is a string of ASCII bytes with the following ABNF syntax 16. The prefix is given as bytes because quoted ABNF strings are case-insensitive.

miner-ballot  = %x7A.70.6F.6C.6C.3A election-id ":" answer-string  ; "zpoll:"
election-id   = 1*16( %x61-7A / DIGIT / "-" )
answer-string = 1*answer
answer        = %x31-39 / %x41-5A / "-"

The i-th Answer Character of the answer string answers question i:

  • a digit 1 to 9 selects options 1 to 9 respectively;
  • a letter A to Z selects options 10 to 35 respectively;
  • a hyphen - leaves the question unanswered.

The answer string is the longest run of Answer Characters immediately following zpoll: ‖ election-id ‖ :. It ends at the first byte that is not an Answer Character, or at the end of the containing data.

A Miner Ballot is valid for an Election E if and only if:

  • its election-id equals the Election Identifier of E;
  • its answer string has exactly one character per question of E;
  • each character of its answer string that is not a hyphen selects an option that exists for the corresponding question;
  • at least one character of its answer string is not a hyphen.

#Casting Miner Ballots

A miner casts a Miner Ballot by including it in the coinbase transaction of a block it mines at a height within the Voting Period: in the Miner Data, in the Coinbase Memo of one or more shielded outputs, or in both. A Coinbase Memo that carries a Miner Ballot MUST be a text memo as defined in ZIP 302 17: its first byte MUST be 0xF4 or smaller, and it MUST be valid UTF-8 after trailing zero bytes are stripped.

The bytes of a Miner Ballot MUST be consecutive, and the byte immediately following it, if any, MUST NOT be an Answer Character. In the Miner Data, both requirements apply to the raw bytes, including script opcodes. Placing the whole Miner Ballot in a single data push satisfies the first requirement, and ending the Miner Data, or the text of a text memo before its zero padding, with the Miner Ballot satisfies the second.

A miner SHOULD include its Miner Ballot in every block it mines during the Voting Period. Since each block counts separately, a miner MAY change its Miner Ballot during the Voting Period. A mining pool that casts Miner Ballots SHOULD publish its Miner Ballot to its hashers before the Voting Start Height.

#Determining the Miner Ballot of a Block

For an Election E and a block B at a height within the Voting Period of E, the Miner Ballot of B for E is determined as follows:

  1. Search the raw bytes of the Miner Data of B, without parsing them as script, for occurrences of zpoll: ‖ Election Identifier of E ‖ :. The first occurrence that, together with its answer string, forms a Miner Ballot valid for E gives the Miner Ballot of B.
  2. Otherwise, search the Coinbase Memos of the shielded outputs of the coinbase transaction of B in the same way, in the order in which the outputs appear in the transaction encoding. Skip each Coinbase Memo that is not a ZIP 302 text memo: one whose first byte is greater than 0xF4, or that is not valid UTF-8 after trailing zero bytes are stripped. The first Miner Ballot valid for E found in this order gives the Miner Ballot of B.
  3. Otherwise, B has no Miner Ballot for E.

Any other Miner Ballots for E in B have no effect.

#Tallying

The tally of a Miner Poll is computed over the best valid block chain of the network given in its Poll Definition, once that chain contains a block at height Voting End Height + 99, giving the block at the Voting End Height 100 confirmations.

Each block in the Voting Period counts as a single vote. Its Miner Ballot, as determined in [Determining the Miner Ballot of a Block], counts exactly once, regardless of who mined it or the value of its coinbase outputs. A block without a Miner Ballot for the Election counts as answering no question.

Let:

  • N be the number of blocks in the Voting Period, i.e. Voting End Height − Voting Start Height + 1;
  • P be the number of blocks in the Voting Period that have a Miner Ballot for the Election;
  • cq,o be the number of those blocks whose Miner Ballot selects option o for question q;
  • Aq=∑ocq,o be the number of those blocks whose Miner Ballot answers question q.

The results of the Miner Poll consist of:

  • for each question q and option o, the count cq,o and the percentage 100⋅cq,o/N;
  • for each question q, the count N−Aq of blocks that do not answer q, and the percentage 100⋅(N−Aq)/N;
  • N, P, and the overall participation 100⋅P/N as a percentage;
  • for each question q, whether 100⋅Aq/N is at least the Participation Threshold;
  • the height and hash of the block at the Voting End Height in the block chain that was tallied.

Percentages in the results, and in any summary of them by the Poll Organizer, MUST be relative to N. The counts are authoritative.

The results on question q are representative of miners if and only if 100⋅Aq/N is at least the Participation Threshold.

#Publication of Results

The Poll Organizer MUST publish the Miner Poll results in the same forum thread as the ZCAP Poll results, no later than 7 days after the block at height Voting End Height + 99 is mined.

A ZIP that cites an Election's ZCAP Poll results, as ZIP 259 does for NU7 12, SHOULD also cite that Election's Miner Poll results.

This ZIP does not specify what weight Miner Poll results carry relative to ZCAP Poll results, or how the two are combined. Coinholder polls are outside its scope.

#Testnet-specific considerations

Miner Polls SHOULD be rehearsed on Testnet before the first Miner Poll on Mainnet. Miner Polls on Testnet are rehearsals only: they are not the Miner Poll of any Election and have no significance for Zcash governance.

Miner Ballots have the same encoding on both networks, and Election Identifiers are unique only per network. A Poll Definition on Testnet that rehearses a Miner Poll on Mainnet SHOULD use the Election Identifier, questions, and options of that Mainnet Poll Definition, so that miners rehearse exactly the Miner Ballots they will cast on Mainnet. The 7-day and 14-day requirements in [Voting Period] do not apply on Testnet.

#Example

This subsection is non-normative.

Consider a hypothetical Mainnet Election with Election Identifier nu8 and five questions, which have 4, 4, 4, 3, and 4 options.

The 15-byte Miner Ballot zpoll:nu8:2311- selects option 2 for question 1, option 3 for question 2, and option 1 for questions 3 and 4; it leaves question 5 unanswered. A miner placing it in the Miner Data of a block at height 3,600,000 can use the 20-byte coinbase script 0380ee360f7a706f6c6c3a6e75383a323331312d: the height encoding 0380ee36, the push opcode 0f, and the Miner Ballot. As a Coinbase Memo, the Miner Ballot is its 15 bytes followed by 497 zero bytes. The same 15 bytes followed by 0xFF and 496 zero bytes are not valid UTF-8, so that memo is not a text memo and carries no Miner Ballot.

If the Voting Period has 100,000 blocks and only 10, all mined by one pool, carry zpoll:nu8:2311-, option 2 of question 1 has 10 votes (0.01%) and 99,990 blocks (99.99%) do not answer question 1. Question 1 is answered in only 0.01% of the Voting Period, so its results are not representative of miners unless the Participation Threshold is at most 0.01%.

If instead 99,990 blocks carry zpoll:nu8:2311- and 10 carry zpoll:nu8:23113, overall participation is 100% and questions 1 to 4 are each answered in 100% of the Voting Period. Question 5, however, is answered in only 0.01%, so its results are not representative of miners unless the Participation Threshold is at most 0.01%.

#Rationale

#Rationale for counting blocks

The number of blocks mined approximates a miner's share of hashrate, and proof of work makes Sybil voting pointless, since more Miner Ballots require more work. Mining pools represent their hashers, who can switch pools if they disagree with their pool's Miner Ballot.

Blocks are not weighted by coinbase output value or timestamp, which keeps the tally independent of transaction fees, the block subsidy, and timestamps chosen by miners. A change to the block target spacing within a Voting Period changes the number of blocks per unit of time for all miners alike, so counting blocks still approximates share of hashrate.

Rented hashrate could buy an outcome at the cost of that hashrate, and public Miner Ballots make bribes verifiable; both are reasons why the results indicate sentiment and are not binding.

#Rationale for counting blocks without Miner Ballots

Percentages are relative to all blocks in the Voting Period, as the version bits mechanism of BIP 9 counts a block that does not signal against activation. 18 Relative to Miner Ballots cast, the 10 Miner Ballots from one pool in the [Example] would show 100% support for their options; relative to the Voting Period, they show 0.01%. A miner's influence on any percentage is thus bounded by its share of the blocks in the Voting Period, however few other miners vote.

This is possible because the electorate of a Miner Poll, the blocks in the Voting Period, is fully observable, as the membership of the ZCAP is. Shares among the blocks that answer a question follow from the published counts cq,o and Aq.

The Participation Threshold flags low turnout. It applies to each question: since a Miner Ballot can leave questions unanswered, a heavily answered question would otherwise make the results on an unanswered question appear representative.

The tally does not group blocks by miner, because coinbase outputs and pool tags are chosen by miners and do not reliably identify them.

#Rationale for using coinbase transactions

Only the miner of a block controls its coinbase transaction, so proof of work authenticates the Miner Ballot. No consensus change is needed: consensus constrains the Miner Data only by the height encoding, the length limit 9, and the block-level limit on signature operations inherited from Bitcoin, to which the ASCII bytes of a Miner Ballot contribute nothing; and shielded coinbase outputs are publicly decryptable 11. The Zcash Stratum protocol keeps the extra nonce in the block header nonce 19, leaving room in the Miner Data.

Two alternatives were rejected:

  • Block header version bits: consensus only requires the block version number to be at least 4 20, but a bit expresses only yes or no.
  • Separate transactions: anyone can create them, and they are not tied to block production.

#Rationale for the Miner Ballot encoding

ASCII suits string-valued node configuration, ZIP 302 text memos, and block explorers. Compactness matters because the 100-byte coinbase script is shared with the height encoding and pool tags; the example Miner Ballot is 15 bytes. Positional answers need no question numbers, and a hyphen lets a miner skip a question that has no "Abstain" option.

The Election Identifier and the exact-length and option-range checks keep stale configurations from counting toward a later Election. Ending the answer string at the first byte that is not an Answer Character makes a length field unnecessary. The case-sensitive prefix gives the encoding a single canonical form; an incompatible future encoding would use a different prefix.

The Miner Ballot has no network field, and Election Identifiers are unique only per network, so that a rehearsal on Testnet can use exactly the Miner Ballots of the Miner Poll on Mainnet, keeping Testnet as close to Mainnet as possible. A Miner Ballot counts on the network whose block carries it: a miner that copies a rehearsal configuration to Mainnet votes with it on Mainnet.

The Miner Data is searched as raw bytes because consensus does not require it to be a well-formed script 9, and a tally that depended on parsing could differ between implementations that handle malformed scripts differently.

#Rationale for the precedence of Miner Ballots

The rule is deterministic, and duplicate Miner Ballots carry no penalty. The Miner Data is checked first because it is always present and needs no decryption.

#Rationale for block-height Voting Periods

Block heights are deterministic, whereas block timestamps are chosen by miners. Changes to the block target spacing are accounted for when the Voting Period is chosen. The 7-day feedback period and the public answers to objections make agreement on the Voting Period reviewable. As for the questions of the ZCAP Poll, that agreement is reached through public review; this ZIP does not define a separate vote on the Voting Period. The 14-day notice period gives mining pools time to reconfigure.

#Reference implementation

Miners can cast Miner Ballots with Zebra: its mining.extra_coinbase_data option places text in the Miner Data, and its mining.miner_memo option sets the Coinbase Memo of the miner's output when mining.miner_address has a shielded receiver. 21
