#Terminology

The key word "MUST" in this document is to be interpreted as described in BCP 14 1 when, and only when, it appears in all capitals.

The term "network upgrade" is to be interpreted as described in ZIP 200. 2

The character § is used when referring to sections of the Zcash Protocol Specification. 3

The terms "Mainnet" and "Testnet" are to be interpreted as described in § 3.12 'Mainnet and Testnet'. 4

"Scheduled Block Subsidy" means the block subsidy determined by the existing halving schedule, after applying the changes in ZIP 218. 5

"NSM Value Balance" is to be interpreted as defined in ZIP 237. 6

#Abstract

This proposal defines the deployment of the NU7 network upgrade. NU7 reduces the block target spacing from 75 seconds to 25 seconds, introduces per-pool and global shielded action limits, introduces the Network Sustainability Mechanism (NSM), and removes 60% of transaction fees from circulation. It also deploys ZIP 2008.

NU7 introduces no new transaction format. Once NU7 activates, version 4 transactions are invalid, while version 5 and version 6 transactions remain valid. Because Sprout transfers can only be represented by version 4 transactions, funds remaining in the Sprout pool become unspendable. 7

The changes do not increase the ZEC supply cap. Funds issued from the NSM Value Balance were previously removed from circulation in equal amount, or unclaimed by miners prior to ZIP 236 8. The NSM Value Balance is public consensus state and introduces no new transaction-level data.

#Motivation

NU7 is deliberately limited to changes that have strong support from coinholders, developers, and major ecosystem organizations. These changes can be deployed without another transaction-format migration. Faster blocks reduce confirmation latency, while the action limits in ZIP 218 bound the validation and shielded synchronization costs enabled by the increased block frequency.

#Specification

#NU7 consensus changes

The primary sources of information about NU7 consensus protocol changes are:

  • The Zcash Protocol Specification. 3
  • ZIP 200: Network Upgrade Mechanism. 2
  • ZIP 207: Funding Streams (Revision 2). 9
  • ZIP 214: Consensus rules for a Zcash Development Fund (Revision 3). 10
  • ZIP 218: 25-second Block Target Spacing. 5
  • ZIP 235: Remove 60% of Transaction Fees From Circulation. 11
  • ZIP 237: Network Sustainability Mechanism: Halving-Preserving Issuance. 6
  • ZIP 2003: Disallow version 4 transactions. 7
  • ZIP 2008: Update to FS_FPF_ZCG_H3 address list. 12

The network handshake and peer management mechanisms defined in ZIP 201 also apply to this upgrade. 13

NU7 deploys all of the consensus changes specified in the ZIPs listed above, including Revision 2 of ZIP 207 and Revision 3 of ZIP 214. NU7 does not deploy ZIP 233 or ZIP 234. 14 15

On Testnet, ZIP 218 changes the minimum-difficulty threshold of ZIP 208 at the Testnet NU7 activation height from six to 18 block target spacings. With the 25-second target spacing, a block time must be more than 450 seconds after the preceding block's time to qualify for minimum difficulty. This change does not affect Mainnet. 16

For NU7 only, the requirement in ZIP 200 2 that ACTIVATION_HEIGHT MUST exceed DEPRECATION_HEIGHT in the last software version without support for the upgrade is waived. The recommendation to allow approximately three months after the first supporting software release is also waived. This exception does not change the scheduling requirements for other network upgrades. Operators of unsupported software may therefore remain online at activation and follow a pre-NU7 consensus branch; deployment communications need to explicitly warn operators to upgrade before activation.

#NU7 network constants

The following network upgrade constants are defined for NU7: 2

CONSENSUS_BRANCH_ID : 0x77190AD9

ACTIVATION_HEIGHT (NU7)
Testnet: 4465026 : Mainnet: 3543405

Each ACTIVATION_HEIGHT (NU7) MUST be a multiple of 3, as required by Revision 3 of ZIP 214. 10 The Mainnet activation height MUST also satisfy the address-list constraint in ZIP 2008 12, so that the new funding recipient is selected before the stream ends.

NSM_REISSUANCE_HEIGHT
Testnet: 7305222 : Mainnet: 8939664

Each NSM_REISSUANCE_HEIGHT is as calculated in ZIP 237 6 for the corresponding network. The Testnet ACTIVATION_HEIGHT (NU7) A=4,465,026 lies between the second and third pre-NU7 Testnet halvings (2,796,000 and 4,476,000). The ZIP 218 third halving is therefore at H3=13,428,000−2A=4,497,948, and the Testnet reissuance height is H3+2,807,274=16,235,274−2A=7,305,222. The Mainnet ACTIVATION_HEIGHT (NU7) A=3,543,405 lies between the second and third pre-NU7 Mainnet halvings (2,726,400 and 4,406,400). The ZIP 218 third halving is therefore at H3=13,219,200−2A=6,132,390, and the Mainnet reissuance height is H3+2,807,274=16,026,474−2A=8,939,664.

MIN_NETWORK_PROTOCOL_VERSION (NU7)
Testnet: 170180 : Mainnet: 170190

For each network, nodes compatible with NU7 activation on that network MUST advertise a network protocol version greater than or equal to the corresponding MIN_NETWORK_PROTOCOL_VERSION.

#Backward compatibility

Before NU7 activates on a network, NU7 and pre-NU7 nodes can connect to each other. NU7 nodes will prefer other NU7 nodes, so pre-NU7 nodes will gradually be disconnected approaching activation.

Once NU7 activates, NU7 nodes will disconnect peers that advertise a lower network protocol version. Blocks produced under the pre-NU7 consensus rules may also be rejected because of the new target spacing, subsidy calculation, action limits, fee allocation, or transaction-version rule.

The version 4 prohibition applies to all version 4 transactions, including transparent-only and Sapling transactions, not only Sprout transfers. Wallets and transaction services need to stop constructing version 4 transactions for post-activation inclusion and clearly report pending transactions that become invalid. Where possible, users can recreate non-Sprout transactions in a supported format; re-signing alone cannot make a version 4 transaction valid. Saved and offline-signed transactions need the same activation checks. Sprout transactions have no supported post-activation replacement format.

Version 5 and version 6 transactions remain structurally unchanged. This does not imply that a transaction is valid across NU7 activation, because its signatures commit to a consensus branch ID.

#Rationale

#Coinholder and Community polling

The August and September 2026 NU7 polls asked five scope questions: whether to preserve halvings or smooth issuance; when NSM reissuance should begin; when version 4 transactions should be disabled; whether to deploy ZIP 218; and whether to ship promptly with only features ready by the September 30 deadline. The poll announcement records the complete questions and response options. 17

The coinholder and community poll results are available at 18.

The polls did not reach a shared majority position on when NSM reissuance should begin. NU7 uses the post-third-halving crossover of reference NSM issuance and the scheduled block subsidy, calculated from the assigned NU7 activation height as specified in ZIP 237 6.

#Rationale for no new transaction format

Avoiding a new format limits parser and wallet disruption in the upgrade immediately following the introduction of version 6 in NU6.3. 19 The fee contribution is a block-level consensus calculation and therefore does not require a new field in ordinary or coinbase transactions.
