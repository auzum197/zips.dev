#Terminology

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", and "MAY" in this document are to be interpreted as described in BCP 14 1 when, and only when, they appear in all capitals.

The terms "Unified Address", "Unified Viewing Key", "Receiver", "Metadata Item", "Typecode", "Producer", and "Consumer" are to be interpreted as defined in ZIP 316. 2 An "Orchard Receiver" is a Receiver with Typecode 𝟶𝚡𝟶𝟹.

A variable-length integer as used in the Bitcoin protocol, 3 in minimal encoding, with a value of at most 𝟶𝚡𝟶𝟸𝟶𝟶𝟶𝟶𝟶𝟶.

Recipient wallet

Payload
The typed content carried inside an Envelope.

#Abstract

This ZIP specifies an off-chain channel between Zcash wallets. A Sender wallet that holds a Recipient wallet's Unified Address deposits an encrypted Envelope in a Mailbox over an anonymity network, and the Recipient wallet fetches it later. Neither wallet reveals its network identity to the other, and the Mailbox operator does not learn who sent an Envelope.

Envelopes are encrypted to the Orchard Receiver of the Unified Address, using the Orchard key agreement with a domain-separated key derivation, so no new keys have to be exchanged. A new ZIP 316 Metadata Item carries the Mailbox Descriptor in the Unified Address. Payload types are defined for acknowledgements, text, ZIP 321 payment requests, and PCZTs, with codes reserved for FROST signing rounds and off-chain note delivery. Mailbox credentials are derived from the wallet seed with ZIP 32 registered key derivation.

Anyone who holds the recipient's Orchard incoming viewing key can read its Envelopes, and a Mailbox Descriptor links every Unified Address that carries it. Transport Bindings are specified separately; Appendix A sketches one for the Nym mixnet. 4

#Motivation

Several wallet protocols need a direct channel between wallets. Each wallet that wants one currently builds its own, so wallets from different vendors cannot talk to each other:

  • Multisig and hardware-signer flows pass PCZTs 5 between parties.
  • FROST signing (ZIP 312 6) runs over a confidential, authenticated channel between the Coordinator and the signers whose mechanism ZIP 312 leaves out of scope. This ZIP supplies the confidential, anonymous transport; a FROST payload would have to carry its own authentication.
  • Payment requests (ZIP 321 7) and acknowledgements have no wallet-to-wallet transport.
  • Project Tachyon 8 9 proposes removing in-band secret distribution from transactions, which makes an off-chain delivery channel a requirement rather than an add-on.

On-chain memos are the only standard channel today. ZIP 231 10 proposes to lift their 512-byte size cap, but memos would still cost fees, be stored by every full validator forever, and need a block confirmation per round, which rules out interactive protocols such as PCZT and FROST exchanges.

ZIP 324 11 delegates delivery to a channel the parties already share, such as a secure messenger or a QR code, for the case where the sender has no address for the recipient. It does not help when the sender does hold a Unified Address, which is the case this ZIP covers.

The idea is not new. Hornby's 2020 light wallet privacy review 12 lists out-of-band transaction delivery over a mixnet as an option and notes that scalable Zcash will need a mixnet or similar technology anyway. zips#629 13 suggests a mixnet plus a "private mailbox" to keep offline reception. The Nym × Zcash integration guide 14 covers routing a wallet's chain-sync and transaction-submission traffic through the mixnet, not wallet-to-wallet delivery. This ZIP fills that gap.

#Privacy Implications

Who can read Envelopes. Envelopes are encrypted to an Orchard Receiver, so anyone holding the account's Orchard incoming viewing key can decrypt them. That is the trust model of incoming notes, but Envelopes can carry more: a PCZT reveals a transaction the recipient is about to sign, including its outputs. Users who share incoming viewing keys with auditors or watch-only services should not expect Envelopes to be private from them.

Linkability. A Mailbox Descriptor is a stable identifier. Two Unified Addresses that carry the same descriptor are linked to one recipient by anyone who sees both, which defeats diversified addresses. Unlinkable addresses therefore need separate mailboxes, at the cost of more credentials to derive and more mailboxes to fetch from. A reply_to address inside an Envelope has the same property for the sender.

Network observers and the Mailbox operator. The anonymity network hides the sender's network identity from the operator and the recipient, and the recipient's from the sender. The operator still sees how many Envelopes a mailbox receives, their size classes, and when they are deposited and fetched. In bindings where the recipient connects to its own mailbox directly, as in the Nym sketch of Appendix A, the operator also learns the recipient's network identity unless the connection is tunnelled, for example over Tor. Network privacy is only as good as the anonymity set: while few wallets use a binding, cover traffic carries most of the weight.

Timing. A deposit made at the same moment as a related on-chain broadcast, a fetch triggered by opening the app, or an immediate acknowledgement each leak timing that an observer can correlate with chain activity. The wallet behaviour rules in the specification reduce but do not remove this.

No sender authentication and no forward secrecy. Envelopes do not authenticate their sender, so a Text payload can impersonate anyone; the specification forbids presenting it as coming from a named party. Envelope keys derive from long-lived keys, so compromise of an incoming viewing key exposes every Envelope the adversary has recorded, as for on-chain notes.

Denial of service. Anyone holding a Unified Address can fill its mailbox. The cost falls on the mailbox's storage and the recipient's bandwidth; trial decryption itself is cheap. Bindings are expected to document quotas, and the unencrypted Envelope header lets a wallet see size classes before fetching bodies where a binding allows that.

#Requirements

  • A sender holding only a recipient's Unified Address can deliver a message with no prior contact.
  • The recipient need not be online when the message is sent.
  • No long-term key material is needed beyond what the wallet derives from its seed, and a wallet restored from seed can recover its mailboxes on a best-effort basis.
  • Neither the Mailbox operator nor a network observer learns the sender's network identity or links a sender to a recipient. The sender does not learn the recipient's network identity.
  • An Envelope reveals nothing about its content beyond its size class.
  • Wallets that implement ZIP 316 but not this ZIP can still parse and pay a Unified Address that carries a Mailbox Descriptor, provided the Typecode registration requested in the Specification is granted.
  • The core protocol does not depend on any one network or token.

#Non-requirements

  • Sender authentication at the Envelope layer. Payload types that need it carry their own.
  • Guaranteed delivery. Delivery is best-effort; protocols built on top have to handle loss.
  • Forward secrecy.
  • Group messaging.
  • Hiding the recipient's network identity from its own Mailbox operator. A binding may provide this, and a wallet can add Tor, but the core does not require it.

#Unified Address Metadata Item

This ZIP defines a ZIP 316 Metadata Item, Mailbox Descriptors, with a Typecode in the Non-MUST-understand Metadata range 𝟶𝚡𝙲𝟶 to 𝟶𝚡𝙳𝙵, to be assigned by the ZIP Editors. 15

The Item's value MUST parse as one or more Mailbox Descriptors, concatenated with no trailing bytes, in the recipient's order of preference. Descriptors with an unrecognised binding_id MUST be skipped, not rejected. A Sender wallet SHOULD use the first descriptor whose binding it supports.

A Unified Address that carries this Item MUST also carry an Orchard Receiver; Envelopes are encrypted to that Receiver. The Item MUST NOT appear in a Unified Viewing Key.

A Mailbox Descriptor is a stable identifier. A wallet MUST NOT put the same descriptor into two Unified Addresses that the user expects to be unlinkable. Wallets SHOULD include the Item only in addresses generated for a purpose that calls for messaging, and SHOULD NOT include it by default.

If a binding's descriptors can go stale (for example in Appendix A, when the recipient changes gateway), the wallet SHOULD also set an Address Expiry Time Metadata Item 16 on the address. Address Expiry Typecodes are MUST-understand, so such an address can only be paid by Consumers that implement ZIP 316 Revision 2; see Open issues.

#Typecode registration

The ZIP 316 Typecode Registry 17 does not currently permit Producers to include Non-MUST-understand Metadata in any address type, and additions to the registry are made by 2xxx-series ZIPs. This ZIP requests the following row, to be applied when it reaches Proposed status:

The Item has no effect on transaction construction, so it meets ZIP 316's condition for zu addresses. Permitting it in Revision 0 addresses is what lets wallets that predate this ZIP pay the address, because Consumers ignore Items with Typecodes they do not recognise. If the ZIP Editors permit it only in Revision 2 addresses, the compatibility requirement holds only for Consumers that implement ZIP 316 Revision 2.

d lets the recipient attribute the Envelope to one of its addresses without trusting reply_to, and in_reply_to lets protocols with several rounds match answers to requests.

reply_to, if present, is the UTF-8 string encoding of a Unified Address 24 whose Human-Readable Part matches the network of the Envelope's recipient. It MUST carry an Orchard Receiver and MAY carry a Mailbox Descriptors Item. A reply is encrypted to that Receiver. It is deposited in the mailbox named by the Item if there is one, or sent by a transport-level anonymous reply if the binding provides one (see Mailbox operations); if neither is available, no reply is possible. A sender that wants replies without linking them to its other addresses SHOULD use a Unified Address and mailbox dedicated to replies.

Senders SHOULD round expiry_time to the hour, to avoid leaking clock skew.

Recipients:

  • MUST drop Envelopes whose expiry_time is nonzero and in the past.
  • MUST drop Envelopes whose message_id they have already processed, and SHOULD remember processed message_ids at least until their expiry, or for a wallet-chosen period when expiry_time is 0.
  • MUST ignore the payload of an Envelope with an unknown payload_type, but still record its message_id.

#Mailbox operations

A Transport Binding MUST provide these operations:

  • Deposit(descriptor, envelope): deliver an Envelope to the Mailbox named by the descriptor.
  • Fetch(credential) → envelopes: retrieve held Envelopes.
  • Delete(credential, handles): remove fetched Envelopes, unless the binding documents that Fetch removes them implicitly.

A Transport Binding MUST hide the sender's network identity from the Mailbox operator and from the recipient, and MUST hide the recipient's network identity from the sender. It SHOULD hide the recipient's network identity from the Mailbox operator, and SHOULD resist timing correlation by a global passive adversary. Bindings SHOULD rate-limit Deposit and SHOULD bound the storage a mailbox can consume.

A Transport Binding specification MUST state:

  • the descriptor encoding;
  • how the 64-byte mailbox key from Mailbox key derivation is turned into the binding's credentials;
  • the retention period, or how a wallet learns it;
  • per-mailbox storage quotas, if any;
  • which size classes it supports;
  • how replies work: by depositing to a reply_to mailbox, by a transport-level anonymous reply, or both, and how long each path stays usable;
  • rate limiting and cost, if any;
  • what network identity, timing, and size information each party can observe.

  • (𝗌𝗄b,𝖼b)=𝖢𝖪𝖣𝗋𝖾𝗀((𝗌𝗄n,𝖼n),𝚋𝚒𝚗𝚍𝚒𝚗𝚐_𝚒𝚍+231,[])

  • 𝖪i=𝖽𝖾𝗋𝗂𝗏𝖾_𝖼𝗁𝗂𝗅𝖽_𝖼𝗋𝗒𝗉𝗍𝗈𝗏𝖺𝗅𝗎𝖾((𝗌𝗄a,𝖼a),i+231,[])

where 𝖼𝗈𝗂𝗇_𝗍𝗒𝗉𝖾 is the ZIP 32 coin type of the network 26, so that Mainnet and Testnet mailboxes are unlinkable; 𝖺𝖼𝖼𝗈𝗎𝗇𝗍 is the ZIP 32 account index of the Orchard key whose addresses carry the descriptor; and i is a per-binding, per-account counter that the wallet increments for each new mailbox. 𝖪i is 64 bytes; each binding states how it is split into credentials.

A wallet restored from seed can rebuild its credentials by scanning i from 0 with a gap limit, subject to the binding's own limits (for example, knowing which gateway each mailbox used).

#Wallet behaviour

Sending:

  • Wallets SHOULD NOT deposit an Envelope at the same moment as a related on-chain broadcast, and SHOULD add a random delay when the use is not interactive.
  • Wallets MUST NOT fall back to a direct connection to a Mailbox when the binding's anonymity network is unavailable.

Fetching:

  • Wallets SHOULD fetch on a randomized schedule that does not depend on user actions, including when no message is expected.
  • Wallets SHOULD cap the bytes they fetch and trial-decrypt per Fetch.

Acknowledgements:

  • Wallets SHOULD send an Ack only when ack_requested is set, and SHOULD delay it by a random amount.

Display:

  • Envelopes are not authenticated. Wallets MUST NOT present a message as coming from a named party unless the payload type itself authenticates the sender, and SHOULD NOT open links in Text payloads without user confirmation.

Viewing keys:

  • Wallets that export an account's incoming viewing key to a third party SHOULD NOT advertise mailboxes on that account's addresses.

#Rationale

Why reuse Orchard key agreement? It needs no new keys and no prior contact: any Unified Address with an Orchard Receiver is already a public encryption key. The cost is that incoming viewing key holders can read Envelopes; a dedicated messaging key in the descriptor would avoid that at the cost of a larger Item.

Why fixed size classes? Exact lengths would leak payload types and content. Three classes keep the anonymity set per class large while still allowing PCZTs.

Why no ZIP 324 payload? A sender that can use this channel already holds the recipient's Unified Address and can pay it on chain, and a ZIP 324 URI carries spend authority that every incoming viewing key holder could use.

Why a transport-agnostic core? Tying a standard to one network and its token is a long-term risk. Nym is sketched first because it is live, packet-based, uses cover traffic, stores messages for offline clients, and offers sender-anonymous replies.

  • Assignment of the Metadata Item Typecode, whether it is permitted in Revision 0 addresses, and this ZIP's number, which the key derivation depends on.
  • Whether to encrypt to a dedicated messaging key carried in the descriptor instead of to the Orchard Receiver, so that incoming viewing key holders cannot read Envelopes.
  • Address Expiry Items make an address unpayable by ZIP 316 Revision 0 Consumers, while the compatibility requirement assumes they can pay it. Whether to recommend expiry, shorter-lived descriptors, or neither.
  • The cost of running one mailbox per unlinkable address, and whether wallets should offer a deliberately linkable "contact" mode.
  • A stable reference for the PCZT serialization.
  • The FROST round message format and its authentication layer.
  • The off-chain note delivery format, to be aligned with Tachyon.
  • Support for Sapling-only recipients.
  • A Tor onion-service binding.
  • Whether the Nym binding in Appendix A becomes normative in this ZIP or in a separate one, once its TBDs are resolved.

#Appendix A: Nym transport binding (non-normative)

This appendix sketches a binding for the Nym mixnet so that the core protocol can be evaluated against a real network. It is not a complete Transport Binding specification: the items marked TBD have to be resolved before it can be made normative. binding_id 𝟶𝚡𝟶𝟶𝟶𝟷 is reserved for it.

Descriptor. The 96-byte binary form of a Nym client address, 27 28 laid out as follows:

FieldTypeDescription
client identity keybyte[32]Ed25519 public key
client encryption keybyte[32]X25519 public key
gateway identity keybyte[32]Ed25519 public key of the gateway

Credentials. The first 32 bytes of 𝖪i would be the Ed25519 seed of the client identity key, and the last 32 bytes the X25519 secret key 29 of the client encryption key. The Nym Rust SDK accepts externally supplied client keys through a custom key store. 30

Deposit. The sender sends the Envelope as a Nym message to the descriptor's address through the mixnet, from an ephemeral Nym client with fresh keys rather than from its own mailbox client, attaching reply SURBs 31 if it expects a prompt reply. Each ephemeral client has to register with an entry gateway and hold bandwidth credentials; the cost and latency of doing so per message are unverified (TBD).

Fetch. The recipient runs a Nym client with the derived keys, connected to the gateway named in the descriptor, with cover traffic on. The gateway stores messages while the client is offline and delivers them when it connects. 27

Delete. Implicit on delivery by the gateway (TBD: confirm).

Retention. Not documented by Nym (TBD).

Size classes. All. Nym splits a message into fixed-size Sphinx packets, so larger classes take more packets and leave a larger timing footprint.

Replies. SURB reply keys expire after 24 hours, 31 so SURBs serve interactive exchanges only. A recipient that fetches later can reply only to a reply_to address that carries a Nym descriptor.

Rate limiting and cost. Sending through Nym consumes bandwidth credentials. Who pays, and whether they can be bought with shielded ZEC, is TBD.

Gateway changes. The gateway is part of the descriptor. If the recipient moves gateway, old descriptors stop working and a new Unified Address has to be issued. How a wallet restored from seed learns which gateway each mailbox index used is TBD.

Observability. The recipient's gateway, which is the Mailbox operator, sees the recipient's connection, including its IP address unless the connection is tunnelled over Tor, and the count and size of stored messages. The sender's entry gateway sees the sender's IP address but not the destination. Mix nodes see packets only. A global passive adversary faces Nym's mixing delays and cover traffic.
