#Terminology

The key words "MUST", "SHALL", "SHOULD", and "SHOULD NOT" in this document are to be interpreted as described in BCP 14 1 when, and only when, they appear in all capitals.

The term "network upgrade" is to be interpreted as defined in ZIP 200. 2

The term "block target spacing" is to be interpreted as defined in ZIP 218. 3

The character § is used when referring to sections of the Zcash Protocol Specification. 4

The terms "Mainnet" and "Testnet" are to be interpreted as described in § 3.12 'Mainnet and Testnet'. 5

"NU8" is the code name of the network upgrade that deploys this proposal.

#Abstract

This proposal changes the block target spacing from 25 seconds to 10 seconds in NU8. The block subsidy, the block size limit, and the shielded action limits of each block are scaled by the same factor, so that issuance, block space, and shielded capacity per unit of time are unchanged.

#Motivation

ZIP 218 reduces the block target spacing from 75 seconds to 25 seconds in NU7 in order to reduce transaction latency. 3 This proposal reduces it to 10 seconds, which reduces the expected time to a first confirmation from 25 seconds to 10 seconds.

The proposal changes latency only. Each quantity that NU7 specifies per unit of time is preserved: issuance, funding stream address periods, reissuance by the Network Sustainability Mechanism, the duration of the difficulty averaging window, and the resource limits of the block chain.

#Unchanged consensus rules

Consensus rules that are expressed in blocks and not changed above, including the coinbase maturity of 100 blocks and 𝖯𝗈𝖶𝖬𝖾𝖽𝗂𝖺𝗇𝖡𝗅𝗈𝖼𝗄𝖲𝗉𝖺𝗇, are unchanged.

#Non-consensus changes

From NU8 activation:

  • Wallets SHOULD use a default expiry delta of 300 blocks, in place of the 120 blocks recommended by ZIP 218.
  • Nodes SHOULD support rolling back at least 1,500 blocks, in place of the 600 blocks recommended by ZIP 218.
  • Implementations SHOULD multiply the block-count constants that ZIP 218 multiplies by 3 by 𝖭𝖴𝟪𝖯𝗈𝖶𝖳𝖺𝗋𝗀𝖾𝗍𝖲𝗉𝖺𝖼𝗂𝗇𝗀𝖱𝖺𝗍𝗂𝗈, rounding up.
  • Nodes SHOULD NOT admit to their mempools or relay, and wallets SHOULD NOT create, a transaction that alone exceeds the block size or shielded action limits above.

#Rationale

A target spacing of 10 seconds makes each scaled quantity an integer: the averaging window of 255 blocks, the halving interval of 12,600,000 blocks, the address period of 262,500 blocks, and the limits of 800,000 bytes, 132 actions, and 120 Sapling inputs and outputs.

Every post-NU7 halving height is even on both networks. An even activation height B therefore maps each such height H to the integer height B+5(H−B)/2, so that no halving boundary falls within a 25-second block.

Scaling the per-block limits by 2/5 keeps the worst-case validation work, compact sync bandwidth, and chain growth per unit of time at their NU7 values. ZIP 218 bounds worst-case compact sync bandwidth at 169.10 MB per day. 3 Without the scaling, each of these would increase by a factor of 5/2.

The post-NU8 block subsidy differs from 2/5 of the post-NU7 block subsidy by less than one zatoshi, due to rounding. If NU8 activates before the third halving, this reduces total scheduled issuance, relative to ZIP 218, by (H3−B)/2 zatoshi before the third halving and by 1.134 ZEC after it.

#Security and Privacy Considerations

The stale block rate increases with the ratio of block propagation time to the block target spacing. ZIP 218 reports a stale block rate of 4.86% for 2 MB blocks at 25-second spacing on a 99-node devnet. 3 The rate at 10-second spacing has not been measured; it needs to be measured before deployment. Smaller blocks and compact block relay 13 reduce propagation time.

A given number of confirmations corresponds to 2.5 times less time. Where propagation time is significant relative to the target spacing, it also provides less security against an attacker with a given fraction of the hash power.

Wallets that select an anchor three blocks behind the chain tip, as recommended by ZIP 315 14, select one about 30 seconds old. A rollback past the anchor invalidates the transaction, and links its revealed nullifiers to any later transaction that spends the same notes. More frequent blocks also give observers finer timing information.

#Deployment

This proposal is intended to be deployed in NU8. The NU8 deployment ZIP will specify 𝖭𝖴𝟪𝖠𝖼𝗍𝗂𝗏𝖺𝗍𝗂𝗈𝗇𝖧𝖾𝗂𝗀𝗁𝗍 for each network.
