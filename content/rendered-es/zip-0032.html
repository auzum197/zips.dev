#Terminología

Las palabras clave "DEBE (MUST)", "NO DEBE (MUST NOT)", "DEBERÍA (SHOULD)", "RECOMENDADO (RECOMMENDED)" y "PUEDE (MAY)" en este documento deben interpretarse como se describe en BCP 14 [1] cuando, y solo cuando, aparecen en mayúsculas.

"Jubjub" se refiere a la curva elíptica definida en [15].

Un "criptovalor" es un valor de alta entropía utilizado en un protocolo criptográfico que no es necesariamente una clave.

Un "código de cadena" es un criptovalor que se necesita, además de una clave de gasto, para derivar claves y direcciones descendientes de esa clave.

Los términos "Testnet" y "Mainnet" deben interpretarse como se describe en la sección 3.12 de la Zcash Protocol Specification (Especificación del Protocolo Zcash) [10].

#Resumen

Esta propuesta define un mecanismo para extender las billeteras jerárquicas determinísticas, como se describe en BIP 32 [2], para admitir las direcciones blindadas de Zcash.

Las partes iniciales de la especificación definen sistemas (en su mayor parte) equivalentes, pero independientes, para derivar un árbol de componentes de clave a partir de una sola semilla, para los siguientes pools blindados (que tienen estructuras de clave internas diferentes):

  • Sapling

  • Orchard

Las versiones anteriores de este documento también definían un sistema de derivación similar para el pool blindado Sprout. Este se ha eliminado dado que nunca se utilizó y es improbable que se utilice, ya que zcashd ya no genera direcciones Sprout (y ni Zebra ni los SDK móviles lo han hecho jamás).

La última parte muestra cómo utilizar estos árboles en el contexto de las billeteras existentes conforme a BIP 44 [6].

Esta especificación complementa el uso existente, por parte de algunas billeteras de Zcash, de BIP 32 y BIP 44 para direcciones transparentes de Zcash, y no tiene la intención de desaprobar ese uso (no obstante los riesgos de privacidad de utilizar direcciones transparentes).

#Motivación

BIP 32 [2] es el mecanismo estándar mediante el cual las billeteras para Bitcoin y sus derivados (incluidas las direcciones transparentes de Zcash [7]) generan claves y direcciones de forma determinística. Esto tiene varias ventajas sobre la generación aleatoria:

  • Las billeteras solo necesitan almacenar una sola semilla (particularmente útil para billeteras de hardware).

  • Una copia de seguridad única de la semilla (normalmente almacenada como un mnemónico BIP 39 [3] o participaciones SLIP 39 [4]) puede utilizarse para recuperar los fondos de todas las direcciones futuras.

  • Las claves se organizan en un árbol de cadenas, lo que permite a las billeteras representar "cuentas" u otras estructuras de alto nivel.

  • La autoridad de visualización o la autoridad de gasto pueden delegarse de forma independiente para subárboles sin comprometer la semilla maestra.

En la actualidad, no existe un equivalente para las direcciones blindadas de Zcash. Esto es de particular preocupación para las billeteras de hardware; todos los dispositivos que se comercializan actualmente solo almacenan una semilla internamente y han entrenado a sus usuarios para hacer copia de seguridad únicamente de esa semilla. Dado que la actualización de Sapling hará viable el uso de billeteras de hardware con direcciones blindadas, es deseable contar con un mecanismo estándar para derivarlas.

#Especificación: Semillas de billetera

Varios de los algoritmos de derivación de claves especificados en este ZIP derivan una clave maestra a partir de una secuencia de bytes de semilla. Cualquier secuencia de bytes de semilla de este tipo DEBE (MUST) tener al menos 32 y como máximo 252 bytes.

El método de generación de una secuencia de bytes de semilla de este tipo para fines de Zcash DEBE (MUST) asegurar que tenga al menos 256 bits de entropía. Este requisito también se aplica a cualquier mnemotécnico o aleatoriedad de entrada utilizada para obtener la secuencia de bytes de semilla. Consulte el ZIP 315 [27] para más orientación.

#Justificación del requisito de entropía de 256 bits

Haga clic para mostrar/ocultar

Zcash utiliza de forma consistente criptovalores de longitud igual o cercana a 256 bits, en todo su diseño criptográfico. Aunque el nivel de seguridad objetivo del protocolo frente a ataques criptoanalíticos clásicos es 2 125 (es decir, cualquier ataque de este tipo debería tomar al menos 2 125 operaciones, como se explica en [23]), esto no implica que las claves o semillas de 128 bits sean suficientes. La aparente brecha entre el objetivo de seguridad y la longitud de la clave está bien motivada: proporciona mejor resistencia a ataques que usan hardware paralelo [24] en el escenario multiusuario [25]; tiene en cuenta pequeñas pérdidas de entropía en el proceso de derivación de claves; y simplifica el análisis del protocolo frente a ataques cuánticos para direcciones desconocidas [23], o en el contexto de un futuro protocolo de recuperación postcuántico [30].

En particular, para el método de derivación jerárquica de claves descrito en este ZIP, si la semilla o el mnemotécnico tiene menos de 256 bits de entropía, será un eslabón débil en la derivación de todas las claves pertenecientes a esa billetera.

Cabe señalar que un adversario puede buscar usos de mnemotécnicos de menor entropía a través de múltiples billeteras simultáneamente. Puede recolectar un conjunto grande de direcciones objetivo (transparentes o blindadas) y/o claves de visualización, y luego realizar una búsqueda de fuerza bruta sobre mnemotécnicos en un subespacio de menor entropía, comprobando eficientemente si las primeras direcciones o claves de visualización que se generarían a partir de cada mnemotécnico coinciden con alguno de los objetivos.

#Claves extendidas de Sapling

BIP 32 define un método para derivar una cantidad de subclaves a partir de una clave padre. Con el fin de evitar que estas dependan únicamente de la clave padre misma, tanto las claves privadas como las públicas se extienden con un código de cadena de 32 bytes. De manera similar, aquí extendemos las claves de Sapling con un código de cadena. Sin embargo, los conceptos de claves "privadas" y "públicas" de BIP 32 no se corresponden limpiamente con los componentes de claves de Sapling. Adoptamos el siguiente enfoque:

  • Derivamos subclaves de gasto expandidas de Sapling, en lugar de claves de gasto de Sapling. Esto nos permite implementar tanto los modos de derivación endurecida como no endurecida (siendo este último incompatible con las claves de gasto de Sapling).

  • No derivamos claves públicas de Sapling directamente, ya que esto impediría el uso de direcciones diversificadas. En su lugar, derivamos claves de visualización completas de Sapling, a partir de las cuales se pueden generar direcciones de pago. Esto mantiene la semántica de confianza de BIP 32: alguien con acceso a una clave pública extendida de BIP 32 puede ver todas las transacciones que involucran esa dirección, lo cual una clave de visualización completa de Sapling también permite.

Las rutas de claves de Sapling y Orchard tienen los siguientes tres niveles de ruta en la parte superior, todos los cuales usan derivación endurecida:

  • $account$: numerado desde el índice 0 de manera secuencialmente creciente. Definido como en BIP 44 [6].

A diferencia de BIP 44, ninguna de las rutas de claves blindadas tiene un nivel de ruta $change$. El uso de direcciones de cambio en Bitcoin es un intento (fallido) de aumentar la dificultad de rastrear a los usuarios en el grafo de transacciones, mediante la separación del uso de direcciones externas e internas. Las direcciones blindadas nunca son públicamente visibles en las transacciones, lo que significa que enviar el cambio de vuelta a la dirección de origen es indistinguible de usar una dirección de cambio.

#Claves de gasto extendidas de Orchard

Una clave de gasto extendida de Orchard ( 𝗌 𝗄 , 𝖼 ) , a profundidad $depth$, con etiqueta de la clave de visualización completa del padre p a r e n t _ f v k _ t a g y número de hijo i , se representa como una secuencia de bytes:

  • 𝖨 𝟤 𝖫 𝖤 𝖮 𝖲 𝖯 8 ( d e p t h ) | | p a r e n t _ f v k _ t a g | | 𝖨 𝟤 𝖫 𝖤 𝖮 𝖲 𝖯 32 ( i ) | | 𝖼 | | 𝗌 𝗄 .

Para la clave de gasto extendida maestra, $depth$ es 0 , p a r e n t _ f v k _ t a g son 4 bytes en cero y i es 0 .

Cuando se codifica como Bech32, la parte legible por humanos es secret-orchard-extsk-main para Mainnet, o secret-orchard-extsk-test para Testnet.

Definimos esta codificación por completitud; sin embargo, dado que incluye la capacidad de derivar claves de gasto hijas, esperamos que la mayoría de las billeteras solo expongan a los usuarios la codificación de la clave de gasto normal de Orchard [21].

#Valores reservados debido a una especificación previa para Sprout

Los siguientes valores se usaron previamente en la especificación de la derivación jerárquica para Sprout y, por lo tanto, NO DEBERÍAN (SHOULD NOT) usarse en futuras especificaciones relacionadas con Zcash:

  • la personalización \mathsf{BLAKE2b}\textsf{-}\mathsf{512} \texttt{“ZcashIP32\_Sprout”}, especificada anteriormente para la derivación de la clave maestra del árbol Sprout;

  • la personalización \mathsf{BLAKE2b}\textsf{-}\mathsf{256} \texttt{“Zcash\_Sprout\_AFP”}, especificada anteriormente para la generación de huellas de direcciones Sprout;

  • el prefijo 𝖯 𝖱 𝖥 𝖾 𝗑 𝗉 𝖺 𝗇 𝖽 𝟶 𝚡 𝟾𝟶 , especificado anteriormente para la derivación de claves hijas Sprout;

  • las partes legibles por humanos de Bech32 zxsprout y zxtestsprout, especificadas anteriormente para las claves de gasto extendidas de Sprout en Mainnet y Testnet respectivamente.
