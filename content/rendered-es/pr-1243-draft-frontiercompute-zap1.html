#Terminología

Las palabras clave "DEBE (MUST)", "NO DEBE (MUST NOT)", "REQUERIDO (REQUIRED)", "DEBERÁ (SHALL)", "NO DEBERÁ (SHALL NOT)", "DEBERÍA (SHOULD)", "NO DEBERÍA (SHOULD NOT)", "RECOMENDADO (RECOMMENDED)", "NO RECOMENDADO (NOT RECOMMENDED)", "PUEDE (MAY)" y "OPCIONAL (OPTIONAL)" en este documento deben interpretarse según lo descrito en el BCP 14 cuando, y solo cuando, aparecen en mayúsculas, como se muestra aquí.

#Resumen

Este ZIP especifica un formato de atestación de capa de aplicación para eventos de ciclo de vida comprometidos en transacciones blindadas de Zcash. Define el tipado de eventos, las reglas de construcción del hash BLAKE2b, la agregación en árbol Merkle y un procedimiento de verificación para compromisos en cadena que mantienen fuera de la cadena los datos que identifican a los participantes.

Este borrador se basa en el protocolo de atestación ZAP1 desplegado (anteriormente NSM1). En el despliegue de referencia, las cargas útiles de los eventos se procesan con hash BLAKE2b-256 usando la cadena de personalización NordicShield_, se insertan en un árbol Merkle de solo adición y se anclan periódicamente a Zcash mediante una transacción con byte de tipo 0x09.

#Relación con el ZIP 302

Este ZIP define la semántica de atestación de la capa de aplicación. El formato portador se especifica por separado en el ZIP 302 1 (Structured Memos, PR #638). Cuando el ZIP 302 se despliegue, las cargas útiles de atestación de ZAP1 DEBERÍAN (SHOULD) codificarse como un tipo de parte del ZIP 302. Hasta entonces, la disposición binaria que sigue sirve como codificación transitoria dentro del campo de memo blindado sin procesar de 512 bytes.

Las partes de este ZIP que son independientes del contenedor son: el registro de tipos de evento, las reglas de construcción del hash, la agregación en árbol Merkle y el procedimiento de verificación.

#Motivación

Los memos blindados de Zcash pueden transportar compromisos de aplicación estructurados, pero el ecosistema carece de una convención para eventos de ciclo de vida tipados que los verificadores externos puedan recalcular de forma independiente.

Exponer el estado y las acciones de Zcash a agentes es sencillo. Un endpoint REST o GraphQL puede envolverse como un servidor MCP con una cantidad pequeña de código, y las implementaciones MCP de la capa de billetera pueden exponer saldos, flujos de firma, estado de sincronización y construcción de transacciones. Estas superficies comparten una propiedad: el consumidor debe confiar en la respuesta del servidor. Si el backend es incorrecto, está comprometido o deja de estar disponible, el agente no tiene un recibo independiente que pueda entregar a un tercero para su verificación.

ZAP1 cierra esa brecha. No expone saldos ni mueve valor. Produce un recibo: un evento tipado comprometido en un árbol Merkle BLAKE2b, con la raíz anclada en datos de memo de Zcash, verificable a partir del esquema público, el material de prueba y el ancla de la cadena, sin confiar en el servidor del emisor.

La distinción es categórica. Los servidores de herramientas responden "¿qué dice este backend ahora mismo?" ZAP1 responde "¿qué ocurrió, demostrable luego ante otro verificador?" El protocolo existe para el artefacto de prueba, no para la exposición de herramientas.

Las aplicaciones que rastrean eventos de propiedad, despliegue, facturación, transferencia y salida necesitan:

  • construcción determinista del hash
  • tipado de eventos estable
  • un formato de carga útil que pueda analizarse sin heurísticas específicas de la aplicación
  • una manera de comprometer historiales de eventos grandes sin escribir registros completos en texto plano en la cadena

Este ZIP estandariza las reglas de compromiso de eventos utilizadas por uno de esos despliegues, de modo que otros constructores puedan implementar herramientas, verificación y extensiones futuras compatibles.

#Requisitos

Una implementación de este ZIP:

  • DEBE (MUST) tratar la carga útil de la atestación como una estructura binaria antes de cualquier codificación de memo blindado específica de la billetera.
  • DEBE (MUST) codificar los enteros en orden de bytes big-endian.
  • NO DEBE (MUST NOT) colocar datos personales identificables de los participantes directamente en la carga útil de la atestación.
  • DEBE (MUST) derivar los hashes de las cargas útiles de eventos de manera determinista a partir de los campos subyacentes del evento.
  • DEBE (MUST) preservar el orden de inserción de los eventos al derivar las raíces de Merkle.
  • DEBE (MUST) permitir que los verificadores recalculen tanto el hash de la hoja del evento como la raíz anclada a partir de artefactos públicos más los datos de testigo proporcionados por la aplicación.

#Especificación

#Disposición de la carga útil binaria

Antes de la codificación del memo blindado (o de la codificación de partes de ZIP 302), la carga útil binaria de la atestación es:

byte 0      : version            = 0x01
byte 1      : type               = 0x01..0x0f
bytes 2..5  : cohort_id          = u32 big-endian
bytes 6..37 : payload_hash       = 32 bytes
bytes 38..45: timestamp          = u64 big-endian unix seconds
bytes 46..77: serial_hash        = 32 bytes, or 32 zero bytes when unused
bytes 78..n : label              = UTF-8 human-readable label, optional

Para un transporte legible por humanos, la carga útil DEBERÍA (SHOULD) representarse como:

ZAP1:{type}:{payload}

donde:

  • ZAP1 es el marcador de protocolo
  • {type} es el tipo de evento en hexadecimal de dos dígitos en minúsculas
  • {payload} es la codificación hexadecimal de la disposición binaria completa anterior

#Construcción del hash

Tamaños de los campos para las entradas de los hash:

  • wallet_hash: 32 bytes (identificador derivado de la aplicación)
  • serial_number: 32 bytes
  • contract_sha256: 32 bytes
  • facility_id: 32 bytes (rellenado con ceros si es más corto)
  • timestamp_be: u64 big-endian (8 bytes)
  • month_be: u16 big-endian (2 bytes)
  • year_be: u16 big-endian (2 bytes)
  • amount_zat_be: u64 big-endian (8 bytes)
  • epoch_be: u32 big-endian (4 bytes)
  • validator_id: 32 bytes
  • proposal_id: 32 bytes
  • proposal_hash, vote_commitment, result_hash: 32 bytes cada uno
  • old_wallet, new_wallet: 32 bytes cada uno

Salvo que se especifique lo contrario, los hash de las cargas útiles de eventos usan BLAKE2b con:

  • longitud del resumen: 32 bytes
  • personalización: NordicShield_ (13 bytes, rellenados con ceros hasta 16 bytes según la especificación de BLAKE2b)

La entrada del hash para cada tipo de evento se define en la tabla anterior. El evento MERKLE_ROOT es un caso especial cuyo hash de carga útil es la propia raíz Merkle de 32 bytes, sin un paso adicional de compresión BLAKE2b.

Para los tipos de evento que llevan un número de serie, el campo de carga útil serial_hash DEBE (MUST) ser:

BLAKE2b_32(serial_number)

con la misma cadena de personalización NordicShield_.

Si no se aplica ningún número de serie, serial_hash DEBE (MUST) ser 32 bytes en cero.

#Compromisos de árbol Merkle

Las aplicaciones que usan este protocolo de atestación DEBERÍAN (SHOULD) agregar los hash de las cargas útiles de eventos en un árbol Merkle binario de solo adición. Para el protocolo ZAP1 desplegado:

  • cada evento produce una hoja
  • las hojas se ordenan por secuencia de inserción
  • los nodos padre son BLAKE2b_32(left || right)
  • la personalización de nodo Merkle es NordicShield_MRK
  • si un nivel tiene cardinalidad impar, el nodo final se duplica

Una prueba de inclusión consiste en:

  • hash de la hoja
  • hash de los hermanos
  • posiciones de los hermanos
  • raíz Merkle derivada
  • identificador de la transacción de anclaje
  • altura de bloque de anclaje

#Anclaje en cadena

Al anclar una raíz Merkle en Zcash:

  • el tipo de evento DEBE (MUST) ser 0x09
  • el hash de la carga útil DEBE (MUST) ser la raíz Merkle actual sin procesar
  • el campo memo blindado DEBERÍA (SHOULD) codificarse como ZAP1:09:{payload}

La implementación ZAP1 desplegada difunde compromisos de memo blindados mediante zingo-cli. El despliegue actual ancla cada 10 eventos o cada 24 horas, lo que ocurra primero.

#Procedimiento de verificación

Para verificar un evento con compromiso, un verificador:

  1. recalcula el hash del payload del evento a partir de los campos de la aplicación
  2. reconstruye el payload de la atestación y el hash de la hoja del evento
  3. recorre la ruta de la prueba Merkle para derivar la raíz
  4. recupera la transacción de anclaje referenciada
  5. confirma que el campo memo blindado contiene el mismo compromiso de raíz 0x09
  6. confirma que la transacción está minada en la cadena prevista

#Justificación

Este diseño separa la semántica del protocolo del transporte de la billetera.

El diseño binario es de ancho fijo para todos los campos críticos, de modo que los analizadores puedan extraer el tipo de evento, el identificador de cohorte y el material relevante para la prueba sin necesidad de comprender ningún texto de etiqueta de formato libre. BLAKE2b-256 se usa por compacidad y rendimiento. Las cadenas de personalización proporcionan separación de dominio entre el hash de la carga útil del evento y el hash de los nodos internos del árbol Merkle.

Anclar raíces Merkle en lugar de registros completos de eventos minimiza la carga de la cadena y preserva la verificabilidad independiente. El campo memo blindado se mantiene corto y de tamaño constante para el caso del compromiso de raíz, incluso a medida que crece el historial de eventos subyacente.

#Consideraciones de privacidad

Este protocolo evita escribir en cadena datos en texto plano que identifiquen a participantes. Las implementaciones DEBEN (MUST) garantizar que wallet_hash, serial_hash, los resúmenes de contratos y otras entradas de la carga útil sean valores derivados y no registros de clientes que identifiquen directamente.

El campo opcional label puede filtrar metadatos de la aplicación si se usa incorrectamente. Los protocolos que usan este ZIP DEBERÍAN (SHOULD) omitir el campo label o limitarlo a cadenas operativas que no identifiquen a participantes.

#Consideraciones de seguridad

Este protocolo proporciona integridad y auditabilidad, no confidencialidad de la base de datos subyacente de la aplicación. La seguridad depende de:

  • la construcción correcta de los hash de eventos
  • el orden de inserción correcto en el árbol Merkle
  • la asociación correcta entre los paquetes de prueba y la raíz anclada que los cubre
  • la recuperación correcta, por parte de la billetera, de la transacción minada que contiene el memo blindado

Este ZIP no aborda:

  • el ingreso fraudulento de datos fuera de cadena antes del hash
  • el robo de la clave usada para autorizar transacciones de anclaje
  • la autorización a nivel de aplicación de transferencias o salidas

La pila ZAP1 desplegada actualmente usa la firma de anclaje de un solo operador, con un diseño de migración a FROST separado en desarrollo para la autorización de umbral de futuras anclas de raíz.

#Compatibilidad con versiones anteriores

Este ZIP codifica el formato ZAP1 versión 0x01 desplegado. Los paquetes de prueba existentes siguen siendo válidos siempre que los verificadores preserven la construcción original del hash de eventos, las reglas de hash Merkle y las referencias a transacciones de anclaje.

Los diseños de payload incompatibles futuros DEBEN (MUST) usar un nuevo byte de versión y DEBERÍAN (SHOULD) usar un marcador de protocolo legible por humanos distinto.

#Implementación de referencia

Las implementaciones de referencia están disponibles en:

  • Frontier-Compute/zap1, que implementa el protocolo de atestación ZAP1 desplegado, el mantenimiento del árbol Merkle, la generación de paquetes de prueba y el flujo de anclaje de raíz.
  • Frontier-Compute/zap1-verify 2, que proporciona un verificador independiente en Rust y WASM para hash de hoja y pruebas Merkle de ZAP1.

En la implementación zap1 desplegada:

  • los hash de payload de evento se calculan con BLAKE2b-256 y la personalización NordicShield_
  • los nodos internos del árbol Merkle usan la personalización NordicShield_MRK
  • los anclajes de raíz se transmiten como ZAP1:09:{root}

#Vectores de prueba

Un paquete de vectores de prueba complementario DEBERÍA (SHOULD) proporcionar:

  • un vector de hash de evento para cada tipo de evento desplegado desde 0x01 hasta 0x09
  • los campos de entrada exactos usados para derivar el hash de la carga útil
  • el leaf_hash esperado
  • las cadenas de personalización del hash usadas

La implementación ZAP1 desplegada 3 publica esos vectores por separado como:

  • Frontier-Compute/zap1/TEST_VECTORS.md
  • TEST_VECTORS.md
