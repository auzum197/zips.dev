#Terminología

Las palabras clave "DEBE (MUST)", "REQUERIDO (REQUIRED)", "NO DEBE (MUST NOT)", "DEBERÍA (SHOULD)" y "PUEDE (MAY)" en este documento deben interpretarse como se describe en BCP 14 [1] cuando, y solo cuando, aparecen en mayúsculas.

Los términos "Testnet" y "Mainnet" deben interpretarse como se describe en la sección 3.11 de la Zcash Protocol Specification (Especificación del Protocolo Zcash) [15].

Los términos "Activo Personalizado", "Identificador de Activo" y "descripción de activo" en este documento deben interpretarse como se describe en el ZIP 227 [11].

Los términos siguientes deben interpretarse de la siguiente manera:

pago

Una transferencia de fondos implementada mediante una salida blindada o transparente de una transacción de Zcash.

solicitud de pago

Una solicitud para que una billetera construya una única transacción de Zcash que contenga uno o más pagos.

#Resumen

Este ZIP propone un formato estándar para URI de solicitud de pago. Las billeteras que reconocen este formato permiten a los usuarios construir transacciones simplemente haciendo clic en enlaces en páginas web o escaneando códigos QR.

#Motivación

Para que evolucione un ecosistema transaccional robusto para Zcash, es necesario que los comerciantes puedan emitir solicitudes de pago. Al momento de la primera redacción de este ZIP, la mejor opción disponible era especificar manualmente una dirección de pago, un monto de pago y, potencialmente, contenido del campo de memo. De estos tres componentes, las billeteras existentes solo proporcionaban funcionalidad para leer direcciones de pago de forma semiautomática. Luego era necesario que el usuario ingresara manualmente los montos de pago y cualquier información de memo asociada, lo cual es tedioso y puede ser propenso a errores, en particular si un pago está destinado a múltiples destinatarios o si la información del campo de memo contiene datos estructurados que deben reproducirse fielmente.

Este ZIP busca eliminar estos problemas proponiendo un formato estándar que los proveedores de billeteras pueden admitir, de modo que la intervención humana solo sea necesaria para la aprobación, no para la creación, de dicha transacción.

En Bitcoin existen dos estándares diferentes para permitir que los comerciantes emitan solicitudes de pago que las billeteras comprendan: BIP 21 [5] y BIP 70 [6]. BIP 21 proporciona un formato de URI que una billetera puede interpretar para construir transacciones simples de un solo destinatario; BIP 70 utiliza un protocolo basado en protobuf que permite solicitar transacciones de complejidad arbitraria.

El formato propuesto en este ZIP busca un punto intermedio entre estos enfoques: proporcionar un formato basado en URI que admita tanto el caso de uso trivial como la situación algo más compleja en la que una transacción puede incluir pagos a múltiples destinatarios.

#Requisitos

El formato debe ser un formato de URI válido [3].

El formato debe permitir la representación de una o más tuplas de dirección de pago, monto, activo (si corresponde) y memo opcional.

#Especificación

#Sintaxis del URI

La siguiente especificación de sintaxis utiliza ABNF [2].

zcashurn        = "zcash:" ( zcashaddress [ "?" zcashparams ] / "?" zcashparams )
zcashaddress    = 1*( ALPHA / DIGIT )
zcashparams     = zcashparam [ "&" zcashparams ]
zcashparam      = [ addrparam / amountparam / assetparam / memoparam / messageparam / labelparam / otherreqparam / otherparam ]
NONZERO         = %x31-39
DIGIT           = %x30-39
paramindex      = "." NONZERO 0*3DIGIT
addrparam       = "address"   [ paramindex ] "=" zcashaddress
amountparam     = "amount"    [ paramindex ] "=" 1*DIGIT [ "." 1*8DIGIT ]
assetparam      = "req-asset" [ paramindex ] "=" *base64url
labelparam      = "label"     [ paramindex ] "=" *qchar
memoparam       = "memo"      [ paramindex ] "=" *base64url
messageparam    = "message"   [ paramindex ] "=" *qchar
paramname       = ALPHA *( ALPHA / DIGIT / "+" / "-" )
otherreqparam   = "req-" paramname [ paramindex ] [ "=" *qchar ]
otherparam      = paramname [ paramindex ] [ "=" *qchar ]
qchar           = unreserved / pct-encoded / allowed-delims / ":" / "@"
allowed-delims  = "!" / "$" / "'" / "(" / ")" / "*" / "+" / "," / ";"

Aquí, ALPHA, unreserved y pct-encoded son los definidos en [3]. "base64url" se define como en [4] con el relleno omitido. (Nótese que esto utiliza un alfabeto diferente al base64 habitual; los valores 62 y 63 del alfabeto se codifican como - y _ respectivamente. Las implementaciones NO DEBEN (MUST NOT) aceptar los caracteres +, / y = que aparecen solo en el base64 habitual.)

Las producciones de la forma 1*x indican una o más instancias sucesivas de la producción x. Las producciones de la forma <n>*<m>x indican al menos <n> y como máximo <m> instancias de la producción x.

Nótese que esta gramática no permite la codificación porcentual fuera de las producciones que utilizan qchar, es decir, los valores de los parámetros label, message, otherreqparam y otherparam.

Los presuntos URI ZIP 321 que no puedan analizarse según la gramática anterior NO DEBEN (MUST NOT) ser aceptados.

#Semántica del URI

Un URI ZIP-321 representa una solicitud de construcción de una transacción con uno o más pagos. En el caso de que solo se solicite un único pago, la dirección del destinatario DEBERÍA (SHOULD) incluirse en el componente hier-part del URI RFC 3986; de lo contrario, se pueden especificar múltiples direcciones de destinatario mediante parámetros addrparam con índices diferentes.

Las direcciones, montos, etiquetas y mensajes que comparten el mismo paramindex (incluido el paramindex vacío) se interpretan como asociados al mismo pago a efectos de la construcción del pago. Un paramindex NO DEBE (MUST NOT) tener cero(s) iniciales. El orden de los parámetros no tiene significado, y los valores de paramindex no necesitan ser secuenciales.

Las implementaciones DEBERÍAN (SHOULD) construir una única transacción que pague todas las instancias especificadas de zcashaddress. Por lo tanto, la cantidad de dichas direcciones está limitada por las restricciones de construcción de la transacción. En general, este límite depende, al menos, de la combinación de tipos de dirección de destino. Por ejemplo, si todos los pagos fueran a direcciones de pago Sapling (cada una especificada directamente o como un Receiver de una dirección unificada), el límite descrito en [16] implica que la construcción de una transacción para un URI ZIP-321 podría fallar si solicita más de 2109 pagos distintos. El límite efectivo podría ser menor si se incluyen pagos a direcciones Orchard u otros tipos futuros de dirección.

Un URI de la forma zcash:<address>?... DEBE (MUST) considerarse equivalente a un URI de la forma zcash:?address=<address>&... donde <address> es una instancia de zcashaddress.

Si hay parámetros que no son direcciones con un paramindex dado, entonces el URI DEBE (MUST) contener un parámetro de dirección con ese paramindex. NO DEBE (MUST NOT) haber más de una ocurrencia de un parámetro y paramindex dados.

Un URI que contenga tanto un parámetro amount como un parámetro req-asset con el mismo paramindex DEBE (MUST) ser rechazado.

Las implementaciones DEBERÍAN (SHOULD) verificar que cada instancia de zcashaddress sea una codificación de cadena válida de una dirección, distinta de una dirección Sprout, según lo especificado en las subsecciones de la sección 5.6 (Encoding of Addresses and Keys) de la especificación del protocolo de Zcash [17]. Al momento de escribir esto, esto incluye los siguientes formatos de dirección:

  • una dirección transparente de Zcash, como se define en [18], utilizando Base58Check [8];

  • una dirección de pago Sapling de Zcash como se define en [19], utilizando Bech32 [9];

  • una dirección unificada de Zcash como se define en [20] y [14], utilizando Bech32m [7].

Puede que en el futuro se agreguen nuevos formatos de dirección a [17], y estos DEBERÍAN (SHOULD) admitirse tanto si este ZIP se actualiza para incluirlos explícitamente como si no.

Si se dispone del contexto de si el URI de pago está destinado a Testnet o a Mainnet, entonces cada dirección DEBERÍA (SHOULD) verificarse para comprobar que corresponde a la red correcta.

Todos los requisitos del ZIP 316 [14] se aplican en el caso de pagos a direcciones unificadas.

Las direcciones Sprout NO DEBEN (MUST NOT) admitirse en solicitudes de pago. La justificación de esto es que, desde la activación de la actualización de red Canopy, las transferencias a direcciones Sprout están restringidas por el ZIP 211 [10]. En general, no se puede esperar que los remitentes dispongan de fondos en el pool de Sprout con los cuales satisfacer solicitudes de pago a una dirección Sprout. Si en el futuro la misma justificación se aplica a otros tipos de dirección, debería considerarse la actualización de este ZIP para excluir dichos tipos, como parte de su deprecación.

#Activos personalizados

El parámetro req-asset permite especificar tanto un identificador de activo como un monto para un pago. Se codifica de la siguiente manera:

$hspace{2em}mathtt{asset} = mathsf{base64url}big([mathtt{0x00}] ,||, mathsf{I2LEOSP}_{64}(value) ,||, mathsf{EncodeAssetId}(mathsf{AssetId})big)$

El byte de versión inicial (0x00) indica el formato de codificación. Para la versión 0x00, los siguientes 8 bytes representan el monto como un entero sin signo de 64 bits en orden de bytes little-endian, seguido del 𝖠 𝗌 𝗌 𝖾 𝗍 𝖨 𝖽 codificado, como se define en el ZIP 227 [13].

Las versiones futuras PUEDEN (MAY) definir estructuras o longitudes diferentes después del byte de versión; las implementaciones DEBEN (MUST) usar el valor de la versión para determinar cómo decodificar el resto del parámetro.

Si no hay ningún parámetro req-asset presente, el pago DEBE (MUST) considerarse como pago en ZEC, y el monto de la transferencia en ZEC se especifica mediante el parámetro amount.

Solo los receptores Orchard son válidos para pagos de activos personalizados. Por lo tanto, una solicitud de pago de un activo personalizado DEBE (MUST) usar una dirección unificada que codifique al menos un receptor Orchard.

#Monto de transferencia en ZEC

Si se proporciona un parámetro amount, su valor se interpreta como ZEC decimal.

Si hay una fracción decimal, entonces DEBE (MUST) usarse un punto (.) como carácter separador para separar el número entero de la fracción decimal, y tanto el número entero como la fracción decimal DEBEN (MUST) ser no vacíos. No se permiten otros separadores (como comas para agrupación o miles). Los ceros a la izquierda en el número entero o los ceros a la derecha en la fracción decimal se ignoran. NO DEBE (MUST NOT) haber más de 8 dígitos en la fracción decimal.

Por ejemplo,

  • amount=50.00 o amount=50 o amount=050 se trata como 50 ZEC;

  • amount=0.5 o amount=00.500 se trata como 0.5 ZEC; y

  • amount=50,000.00 o amount=50,00 o amount=50. o amount=.5 o amount=0.123456789 son inválidos.

El monto NO DEBE (MUST NOT) ser mayor que 21000000 ZEC (en general, los montos monetarios en ZEC en Zcash no pueden ser mayores que este valor).

#Claves de consulta

label

Etiqueta para una dirección (p. ej., nombre del receptor). Si hay una etiqueta presente en un paramindex, un cliente que muestre un pago para inspección por parte del usuario DEBERÍA (SHOULD) mostrar esta etiqueta (si es posible) junto con la dirección asociada. Si se muestra la etiqueta, DEBE (MUST) ser identificable como distinta de la dirección.

address

Cadena de dirección de Zcash (blindada o transparente)

memo

Contenido para el campo memo blindado de Zcash, codificado como base64url sin relleno =. El contenido del memo decodificado NO DEBE (MUST NOT) exceder 512 bytes, y si es más corto, se rellenará con ceros a la derecha hasta 512 bytes. Los analizadores DEBEN (MUST) considerar todo el URI como inválido si la dirección asociada al mismo paramindex no permite el uso de memos (es decir, si es una dirección transparente).

message

Mensaje que los clientes pueden mostrar con el propósito de presentar al usuario información descriptiva sobre el pago en el paramindex asociado.

#Ejemplos inválidos

zcash:?amount=3491405.05201255&address.1=ztestsapling10yy2ex5dcqkclhc7z7yrnjq2z6feyjad56ptwlfgmy77dmaqqrl9gyhprdx59qgmsnyfska2kez&amount.1=5740296.87793245

Una solicitud de pago inválida; falta una dirección de pago, con paramindex vacío.

zcash:?address=tmEZhbWHTpdKMw5it8YDspUXSMGQyFwovpU&amount=1&amount.1=2&address.2=ztestsapling10yy2ex5dcqkclhc7z7yrnjq2z6feyjad56ptwlfgmy77dmaqqrl9gyhprdx59qgmsnyfska2kez

También inválida; a esta solicitud le falta address.1=.

zcash:?address.0=ztestsapling10yy2ex5dcqkclhc7z7yrnjq2z6feyjad56ptwlfgmy77dmaqqrl9gyhprdx59qgmsnyfska2kez&amount.0=2

También inválida; address.0= y amount.0= no están permitidos porque los 0 iniciales están prohibidos en paramindex.

zcash:?amount=1.234&amount=2.345&address=tmEZhbWHTpdKMw5it8YDspUXSMGQyFwovpU

zcash:?amount.1=1.234&amount.1=2.345&address.1=tmEZhbWHTpdKMw5it8YDspUXSMGQyFwovpU

También inválida; campos amount= o amount.1= duplicados

zcash:tmEZhbWHTpdKMw5it8YDspUXSMGQyFwovpU?amount=1%30
zcash:tmEZhbWHTpdKMw5it8YDspUXSMGQyFwovpU?%61mount=1
zcash:%74mEZhbWHTpdKMw5it8YDspUXSMGQyFwovpU?amount=1

Inválida; la codificación porcentual solo está permitida en las producciones qchar, que no incluyen direcciones, montos ni nombres de parámetros.

zcash://tmEZhbWHTpdKMw5it8YDspUXSMGQyFwovpU?amount=1

Inválida; la gramática no permite //. Los URI de ZIP 321 no son "URI jerárquicos" en el sentido definido en la sección 1.2.3 de [3], y no tienen un "componente de autoridad".

zcash:?address=ztestsapling10yy2ex5dcqkclhc7z7yrnjq2z6feyjad56ptwlfgmy77dmaqqrl9gyhprdx59qgmsnyfska2kez
  &amount=5
  &req-asset=not@valid!chars

Inválida:

  • Se usa una dirección de Sapling con un parámetro req-asset. Los receptores de Sapling no admiten pagos de activos personalizados (solo las direcciones unificadas con un receptor Orchard lo hacen).

  • El valor de req-asset contiene caracteres (p. ej., @, !) que no están permitidos en base64url.

  • El parámetro amount está presente junto con req-asset. Estos parámetros son mutuamente excluyentes.

#Compatibilidad hacia adelante

Las variables que tienen como prefijo un req- se consideran requeridas. Si un analizador no reconoce alguna variable con prefijo req-, DEBE (MUST) considerar inválido todo el URI. Cualquier otra variable no reconocida que no tenga un prefijo req- DEBERÍA (SHOULD) ignorarse.

req- es potencialmente parte de un nombre de parámetro dado que puede definirse en una versión futura de este ZIP, no un modificador que pueda aplicarse a un parámetro arbitrario. Ninguno de los parámetros definidos originalmente (address, amount, label, memo y message) incluye el prefijo req-, porque se REQUIERE (REQUIRED) que todos los analizadores de URI de ZIP 321 conformes entiendan estos parámetros.

#Compatibilidad hacia atrás

Al momento de redactar este ZIP, varios clientes ya implementan un esquema de URI zcash: similar a este, aunque generalmente sin el requisito adicional del prefijo req- o sin la facilidad para especificar múltiples pagos usando paramindex. Estas implementaciones tampoco suelen admitir URI, incluso con un solo pago, donde la dirección se especifica como un parámetro de consulta address= en lugar de en el hier-part del URI. Pueden además no admitir el parámetro memo, o pueden no tratarlo como codificado en base64url.

#Despliegue

Los URI de solicitud de pago de ZIP 321 están ampliamente desplegados en el ecosistema de Zcash. Una implementación de referencia para el análisis y la construcción de URI de ZIP 321 (para el subconjunto del formato que solo admite ZEC, excluyendo la extensión req-asset) está disponible en el crate zip321 del repositorio librustzcash [12], y es usada por billeteras construidas sobre la biblioteca zcash_client_backend. El soporte para URI de ZIP 321 se ha publicado en billeteras en producción, entre otras Zashi, Nighthawk Wallet, Edge, Unstoppable Wallet, YWallet y (históricamente) ZecWallet Lite, y comúnmente se recurre a él para generar códigos QR y enlaces de pago clicables.

La extensión req-asset para pagos con activos personalizados descrita en este ZIP aún no está desplegada, pendiente de la activación de ZIP 227 [11].
