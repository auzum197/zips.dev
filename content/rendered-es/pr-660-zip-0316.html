#Terminología

Las palabras clave "DEBE (MUST)", "NO DEBE (MUST NOT)", "DEBERÍA (SHOULD)" y "PUEDE (MAY)" en este documento deben interpretarse como se describe en RFC 2119. [1]

Los términos siguientes deben interpretarse así:

Destinatario

Una billetera u otro software que puede recibir transferencias de activos (como ZEC) o, en el futuro, potencialmente otros cambios de estado basados en transacciones.

Productor

Una billetera u otro software que puede crear una dirección (en cuyo caso normalmente también es un Destinatario) o una clave de visualización.

Consumidor

Una billetera u otro software que puede hacer uso de una dirección o de una clave de visualización que se le haya proporcionado.

Emisor

Una billetera u otro software que pueda enviar transferencias de activos, u otros efectos secundarios de estado de consenso definidos en el futuro. Los emisores son un subconjunto de los consumidores.

Receptor

La información necesaria para transferir un activo a un Destinatario que generó ese Receptor mediante un protocolo de transferencia específico. Cada Receptor está asociado de forma inequívoca a un tipo de Receptor específico, identificado por un código de tipo entero.

Elemento receptor

Una codificación de un Receptor como secuencia de bytes.

Clave de visualización

La información necesaria para ver información sobre pagos a una dirección, o (en el caso de una clave de visualización completa) desde una dirección. Una clave de visualización entrante puede derivarse de una clave de visualización completa, y una dirección puede derivarse de una clave de visualización entrante.

Elemento de clave de visualización

Una codificación de una clave de visualización como secuencia de bytes.

Elemento de metadatos

Una codificación de metadatos que no es un Receptor ni una clave de visualización, pero que puede afectar la interpretación de la dirección unificada/clave de visualización unificada en su conjunto.

Ítem

Un Elemento receptor, Elemento de clave de visualización o Elemento de metadatos.

Dirección heredada

Una dirección transparente, Sprout o Sapling.

Dirección unificada (o UA)

Una dirección unificada combina múltiples Ítems de Receptor (y opcionalmente de Metadatos).

Clave de visualización completa unificada (o UFVK)

Una clave de visualización completa unificada combina múltiples Ítems de clave de visualización completa (y opcionalmente de Metadatos).

Clave de visualización entrante unificada (o UIVK)

Una Unified Incoming Viewing Key combina múltiples Ítems de Incoming Viewing Key (y opcionalmente de Metadatos).

Unified Viewing Key (o UVK)

Una Unified Full Viewing Key o una Unified Incoming Viewing Key.

Dirección

Una dirección heredada o una dirección unificada.

Protocolo de transferencia

Una especificación de cómo un Emisor puede transferir activos a un Destinatario. Por ejemplo, el Protocolo de transferencia para un Receptor Sapling es el subconjunto del protocolo de Zcash necesario para transferir ZEC con éxito mediante transferencias Spend/Output de Sapling, según lo especificado en la Zcash Protocol Specification (Especificación del Protocolo Zcash). (Una sola transacción de Zcash puede contener transferencias de múltiples Protocolos de transferencia. Por ejemplo, una transacción t→z que protege hacia el pool de Sapling requiere tanto los Protocolos de transferencia transparente como el de Sapling.)

Codificación de cadena unificada

Una codificación de una UA/UVK como cadena US-ASCII, destinada a la visualización y transferencia por parte de usuarios finales de Zcash, o al uso interno por parte de software relacionado con Zcash.

Codificación QR unificada

Una codificación de una UA/UVK como código QR, destinada a la visualización y transferencia por parte de usuarios finales de Zcash en situaciones donde las ventajas de usabilidad de un código de barras 2D pueden ser relevantes.

Codificación cruda unificada

Una codificación de una UA/UVK como una secuencia de bytes, destinada solo al uso interno de software relacionado con Zcash. Las Codificaciones crudas unificadas NO DEBEN (MUST NOT) exponerse a los usuarios finales, ya que carecen de las propiedades de resiliencia y no maleabilidad necesarias para ese propósito.

Codificación de dirección

Una codificación externamente visible de una dirección.

La notación para secuencias, conversiones y operaciones aritméticas sigue la especificación del protocolo de Zcash [3].

La notación 𝚇 [ i . . = j ] , donde 𝚇 es una secuencia de bytes, significa la subsecuencia de bytes de 𝚇 en los índices basados en cero desde i hasta j inclusive.

#Resumen

Esta propuesta define las direcciones unificadas, que agrupan direcciones de Zcash de distintos tipos de manera que puedan presentarse como una única Codificación de dirección. También define claves de visualización unificadas, que cumplen una función similar para las claves de visualización de Zcash.

#Motivación

Hasta la actualización de red Canopy incluida, Zcash admitía los siguientes tipos de dirección de pago:

  • Direcciones transparentes (P2PKH y P2SH)

  • Direcciones Sprout

  • Direcciones Sapling

Cada una de estas tiene sus propias Codificaciones de dirección, como cadena y como código QR. (Dado que el código QR se puede derivar de la codificación de cadena como se describe en [8], para muchos propósitos basta con considerar la codificación de cadena.)

La propuesta de Orchard [24] añade un nuevo tipo de Dirección, las direcciones Orchard.

La dificultad de definir nuevas Codificaciones de dirección para cada tipo de Dirección es que los usuarios finales se ven obligados a conocer los distintos tipos y, en particular, qué tipos admite un Consumidor o Destinatario dado. Para asegurarse de que las transferencias se completen con éxito, los usuarios pueden verse obligados a generar explícitamente Direcciones de distintos tipos y redistribuir codificaciones de ellas, lo que añade una fricción y una sobrecarga cognitiva significativas para comprender y usar Zcash.

Los objetivos de un estándar de dirección unificada son los siguientes:

  • Simplificar la coordinación entre Destinatarios y Consumidores eliminando la complejidad de la negociación de tipos de Dirección.

  • Proporcionar un “mecanismo de puente” que permita a las billeteras blindadas interactuar con éxito con billeteras conformes de solo transparente.

  • Permitir que las billeteras conformes más antiguas interactúen sin problemas con las billeteras más recientes.

  • Permitir que los usuarios de billeteras más recientes actualicen a tecnologías de transacción y/o grupos más nuevos, manteniendo interacciones sin problemas con contrapartes que usan billeteras más antiguas.

  • Facilitar que las billeteras asuman responsabilidades más sofisticadas de blindaje y/o migración de fondos del usuario.

  • Permitir que las billeteras desarrollen potencialmente nuevos mecanismos de transferencia sin cambios en el protocolo subyacente.

  • Admitir abstracciones correspondientes a una dirección unificada que proporcionen la funcionalidad de las claves de visualización completas y de las claves de visualización entrantes.

  • Proporcionar compatibilidad hacia adelante que sea estándar para todas las billeteras en una gama de posibles funciones futuras. Algunos ejemplos podrían ser funciones de capa 2, interoperabilidad y puentes entre cadenas, y exchange descentralizado.

  • Permitir que se incluyan ítems de metadatos en direcciones/claves de visualización unificadas para proporcionar extensibilidad futura.

  • El estándar debería funcionar bien para Zcash hoy y para las próximas posibles actualizaciones, y también anticipar casos de uso aún más amplios en el futuro, como la funcionalidad entre cadenas.

#Requisitos

#Descripción general

Las direcciones unificadas especifican múltiples métodos de pago a la billetera de un Destinatario. La billetera del Emisor puede entonces seleccionar el método de pago de forma no interactiva.

Es importante destacar que cualquier billetera puede admitir direcciones unificadas, incluso cuando esa billetera solo admite un subconjunto de métodos de pago para recibir y/o enviar.

A pesar de tener algunas características similares, el estándar de dirección unificada es ortogonal a los Payment Request URIs [26] y esquemas similares. Dado que las Payment Requests codifican las direcciones como cadenas alfanuméricas, no se requiere ningún cambio en el ZIP 321 para usar direcciones unificadas en Payment Requests.

#Conceptos

Las billeteras siguen un modelo de flujo de interacción como el siguiente:

  1. Un Productor genera una Dirección.

  2. El Productor codifica la Dirección.

  3. La billetera del Productor o el usuario humano distribuye esta Codificación de dirección. Este ZIP deja los mecanismos de distribución fuera del alcance.

  4. Una billetera o un usuario Consumidor importa la Codificación de dirección mediante cualquiera de una variedad de mecanismos (escaneo de código QR, Payment URIs, copiar y pegar, o protocolos “en banda” como los memos Reply-To).

  5. Una billetera Consumidora decodifica la Codificación de dirección y realiza verificaciones de validez.

  6. (Quizás más adelante en el tiempo) si la billetera Consumidora es un Emisor, puede ejecutar una transferencia de ZEC (u otros activos o cambios de estado del protocolo) a la Dirección.

Pueden distribuirse codificaciones de la misma Dirección cero o más veces por medios diferentes. Cero o más Consumidores pueden importar Direcciones. Cero o más de ellos (que son Emisores) pueden ejecutar una Transferencia. Un solo Emisor puede ejecutar múltiples Transferencias a lo largo del tiempo a partir de una sola importación.

Los pasos 1 a 5 inclusive también se aplican a los flujos de interacción para claves de visualización completas y claves de visualización entrantes.

#Direcciones

Una dirección unificada (o UA, por sus siglas en inglés) combina uno o más Receptores.

Cuando se introduzcan nuevos protocolos de transporte al protocolo de Zcash después de que las direcciones unificadas se estandaricen, estos deberían introducir nuevos tipos de Receptor, pero no tipos de Dirección diferentes fuera del estándar de UA. Debe haber una razón convincente para desviarse del estándar, ya que los beneficios de las UA provienen precisamente de su aplicabilidad a todas las nuevas actualizaciones del protocolo.

#Receptores

Toda billetera debe analizar correctamente las codificaciones de una dirección unificada o una clave de visualización unificada que contengan elementos no reconocidos.

Una billetera puede procesar elementos no reconocidos indicando al usuario su presencia o información similar con fines de usabilidad o diagnóstico.

Las direcciones unificadas y las claves de visualización unificadas deben admitir suficientes tipos de receptores como para permitir una expansión razonable en el futuro.

#Codificaciones de transporte

La Codificación de cadena unificada es “opaca” para los lectores humanos: no permite la identificación visual de qué Receptores o tipos de Receptor están presentes.

La Codificación de cadena unificada es resistente a errores de tipeo, de transcripción, de copiar y pegar, truncamientos u otros riesgos probables de UX.

La Codificación de cadena unificada es resistente, en la medida en que sea razonablemente posible, a los "ataques de maleabilidad" que intentan sustituir una cadena visualmente similar que representa una dirección válida diferente, con el fin de inducir a un usuario a enviar fondos a la dirección equivocada. En particular, siempre que un usuario verifique suficientes caracteres de una Codificación de cadena unificada dada (digamos, al menos 20 caracteres) contra los caracteres correspondientes de una Codificación de cadena unificada de referencia confiable, esa verificación debería ser suficiente para darle la confianza de que un ataque de maleabilidad sería inviable: o bien tiene una Codificación de dirección no válida, o bien una idéntica a la de referencia.

Existe una Codificación QR unificada bien definida de una dirección unificada (o UFVK o UIVK) como código QR, que produce códigos QR razonablemente compactos y robustos.

Existe una Codificación cruda unificada bien definida de una UA/UVK que es una secuencia de bytes compacta, sin una sobrecarga de codificación excesiva. Dado que la Codificación cruda unificada está destinada a usarse únicamente de forma interna en software relacionado con Zcash o a transmitirse por canales confiables, no necesita tener las propiedades de resiliencia y no maleabilidad descritas anteriormente.

Existen transformaciones bien definidas entre la Codificación QR unificada, la Codificación de cadena unificada y la Codificación cruda unificada de una UA/UVK dada, en cualquier dirección.

La Codificación de cadena unificada cabe en los URIs de pago de ZIP-321 [26] y en URIs generales sin introducir ambigüedades de análisis.

#Transferencias

Al ejecutar una Transferencia, el Emisor selecciona un Receptor mediante un proceso de Selección.

Dada una UA válida, la Selección debe tratar cualquier elemento no reconocido como si estuviera ausente.

  • Esta propiedad es crucial para la compatibilidad con versiones futuras, a fin de asegurar que los usuarios que actualicen a protocolos / UAs más nuevos no pierdan la capacidad de interactuar sin problemas con billeteras más antiguas.

  • Esta propiedad es crucial para permitir que las billeteras conformes solo transparentes interactúen con billeteras blindadas más recientes, eliminando un desincentivo para adoptar billeteras blindadas más recientes.

  • Esta propiedad también permite que las billeteras solo transparentes se actualicen para admitir soporte blindado sin volver a adquirir las UAs de las contrapartes. Si se vuelven a adquirir, el flujo del usuario y la usabilidad se verán mínimamente afectados.

#Uso experimental

Las direcciones unificadas y las Unified Viewing Keys deben poder incluir Receptores y Viewing Keys de tipos experimentales, posiblemente junto con otros no experimentales. Estos Receptores o Viewing Keys experimentales deben ser usados solo por billeteras cuyos usuarios hayan aceptado explícitamente participar en el experimento correspondiente.

#Claves de visualización

Una Unified Full Viewing Key (resp. Unified Incoming Viewing Key) puede usarse de manera similar a una Full Viewing Key (resp. Incoming Viewing Key), como se describe en la Zcash Protocol Specification [2].

Para una dirección P2PKH transparente derivada según BIP 32 [27] y BIP 44 [30], el equivalente más cercano a una clave de visualización completa o a una clave de visualización entrante para una cuenta BIP 44 dada es una clave pública extendida, como se define en la sección “Extended keys” de BIP 32. Por lo tanto, las UFVK y las UIVK deberían poder incluir tales claves públicas extendidas.

Una billetera debería admitir la derivación de una UIVK a partir de una UFVK, y de una dirección unificada a partir de una UIVK.

#Problemas abiertos y preocupaciones conocidas

Los impactos en la privacidad de las transacciones transparentes o entre pools, y los problemas de UX asociados, se abordarán en el ZIP 315 (en preparación).

#Especificación

En lugar de definir una codificación de cadena Bech32 de las direcciones de pago blindadas de Orchard, definimos un formato de dirección unificada capaz de codificar un conjunto de Receivers de distintos tipos. Esto permite que el Consumidor de una dirección unificada elija el Receiver del mejor tipo que soporte, lo que ofrece una mejor experiencia de usuario a medida que se agreguen nuevos Receiver Types en el futuro.

De manera similar, una clave de visualización completa unificada o una clave de visualización entrante unificada proporciona la visibilidad correspondiente sobre transacciones que pueden usar direcciones de distintos tipos. Normalmente estas serán las direcciones de cada pool derivadas de una Cuenta, tal como se define en [20]. (No es posible que una UVK incluya claves de visualización para múltiples direcciones del mismo tipo.)

Cuando se muestre al usuario una codificación de cadena de una dirección unificada o de una clave de visualización unificada, DEBE (MUST) codificarse mediante la Codificación de cadena unificada definida en Codificaciones de cadena de direcciones unificadas y claves de visualización unificadas. La razón principal de esto es satisfacer los requisitos relativos a la resiliencia ante errores del usuario y la resistencia a ataques de maleabilidad, tal como se describe en Codificaciones de transporte.

En los casos en que las direcciones unificadas o las Unified Viewing Keys no se muestren directamente a los usuarios, sino que deban codificarse como datos legibles por máquina, PUEDE (MAY) usarse la Codificación cruda unificada en lugar de la Codificación de cadena unificada. Esto tiene la ventaja de reducir el requisito de espacio, y también puede reducir los costos computacionales y la complejidad de implementación.

Una Codificación cruda unificada no tiene resiliencia ante la corrupción de datos ni los errores de transcripción, ni resistencia a ataques de maleabilidad, y por lo tanto NO DEBE (MUST NOT) usarse en situaciones donde se requieran estas propiedades. Para mayor claridad, esto incluye todas las situaciones donde las Codificaciones de direcciones se exponen directamente a los usuarios finales.

#Codificación cruda de direcciones unificadas

Supóngase que se nos da un conjunto de uno o más elementos de receptor de tipos distintos. Es decir, el conjunto puede contener, de forma opcional, un Receptor de cada uno de los tipos de receptor de la siguiente Lista de prioridad fija:

  • Typecode 𝟶 𝚡 𝟶𝟹 — una Orchard raw address según se define en [10];

  • Typecode 𝟶 𝚡 𝟶𝟸 — una Sapling raw address según se define en [9];

  • Typecode 𝟶 𝚡 𝟶𝟷 — una dirección P2SH transparente, o Typecode 𝟶 𝚡 𝟶𝟶 — una dirección P2PKH transparente.

Si, y solo si, el usuario de una billetera Productora o Consumidora acepta explícitamente participar en un experimento según se describe en Uso experimental, la especificación del experimento PUEDE (MAY) incluir adiciones a la Lista de Prioridad anterior (dichas adiciones DEBERÍAN (SHOULD) mantener la intención de preferir protocolos blindados más recientes).

Decimos que un Receiver Type es “preferido” sobre otro cuando aparece antes en esta Lista de Prioridad (según lo modificado potencialmente por experimentos).

El Sender de un pago a una dirección unificada DEBE (MUST) usar el Receiver del Receiver Type más preferido que soporte dentro del conjunto.

Por ejemplo, considérese una billetera que soporta enviar fondos a Orchard Receivers y no soporta enviar a ningún Receiver Type que sea preferido sobre Orchard. Si a esa billetera se le da una UA que incluye un Orchard Receiver y posiblemente otros Receivers, DEBE (MUST) enviar al Orchard Receiver.

Un HRP binario es un único byte de longitud 𝚑 𝚛 𝚙 _ 𝚕 𝚎 𝚗 de 0 a 16 inclusive, seguido de 𝚑 𝚛 𝚙 _ 𝚕 𝚎 𝚗 bytes de un HRP codificado en US-ASCII.

La Codificación Cruda Unificada de una dirección unificada es un HRP binario seguido de una concatenación de ( 𝚝 𝚢 𝚙 𝚎 𝚌 𝚘 𝚍 𝚎 , 𝚕 𝚎 𝚗 𝚐 𝚝 𝚑 , 𝚊 𝚍 𝚍 𝚛 ) codificaciones de los Receptores constituyentes, en orden ascendente de código de tipo:

#Codificación Cruda de Unified Full/Incoming Viewing Keys

Las Unified Full o Incoming Viewing Keys se codifican y decodifican de manera análoga a las direcciones unificadas. Para las Viewing Keys, un Consumidor normalmente tomará la unión de la información proporcionada por todos los Receivers contenidos, y por lo tanto no se usa la Lista de Prioridad definida en la sección anterior.

Para cada FVK Type o IVK Type definido actualmente en esta especificación, se usa el mismo Typecode que para el Receiver Type correspondiente en una dirección unificada. PUEDEN (MAY) definirse FVK Types y IVK Types adicionales en el futuro, y estos no necesariamente usarán el mismo Typecode que la dirección unificada correspondiente.

# Justificación de la derivación de direcciones

El diseño de la derivación de direcciones busca mantener la desvinculabilidad entre direcciones derivadas de la misma UIVK, en la medida de lo posible. Nótese que puede ser difícil conservar esta propiedad en los Metadata Items, y esto debería tenerse en cuenta en el diseño de tales Items.

  • Una dirección unificada o una clave de visualización unificada DEBE (MUST) contener al menos un elemento blindado (Typecodes 𝟶 𝚡 𝟶𝟸 y 𝟶 𝚡 𝟶𝟹 ). La justificación es que los formatos de dirección solo transparente existentes P2SH y P2PKH, y el formato de clave pública extendida P2PKH existente, bastan para representar elementos transparentes y ya están soportados por el ecosistema existente.

  • Los campos 𝚝 𝚢 𝚙 𝚎 𝚌 𝚘 𝚍 𝚎 y 𝚕 𝚎 𝚗 𝚐 𝚝 𝚑 se codifican como 𝚌 𝚘 𝚖 𝚙 𝚊 𝚌 𝚝 𝚂 𝚒 𝚣 𝚎 . [36].   • Dentro de una sola UA o UVK, todos los Receivers, FVKs e IVKs derivados por HD DEBERÍAN (SHOULD) representar una Address o Viewing Key de la misma cuenta (como se usa en el nivel de Cuenta de ZIP 32 o BIP 44).

  • Intencionalmente no se define ningún Typecode para una dirección de pago blindada de Sprout ni para una clave de visualización entrante de Sprout. Dado que ya no es posible (desde la activación del ZIP 211 en la actualización de red Canopy [23]) enviar fondos al pool de valor de la cadena Sprout, esto no sería generalmente útil.

  • Los consumidores DEBEN (MUST) rechazar direcciones/claves de visualización unificadas en las que el mismo código de tipo aparezca más de una vez, o que incluyan tanto una dirección transparente P2SH como una P2PKH, o que contengan solo una dirección transparente.

# Justificación del orden de los Items

La justificación para requerir que los Ítems estén ordenados canónicamente por Typecode es que permite a las implementaciones usar una representación en memoria que descarta el orden, manteniendo la misma serialización de ida y vuelta de una UA / UVK (siempre que se retengan los Ítems no reconocidos).

# Justificación de mostrar al menos los primeros 20 caracteres

Mostrar menos de 20 caracteres de la codificación como cadena de una UA/UVK permitiría potencialmente ataques prácticos en los que el adversario construye otra UA/UVK que coincide en los caracteres mostrados. Cuando se abrevia una UA/UVK es preferible mostrar un prefijo en lugar de alguna otra parte, tanto para una experiencia de usuario más consistente entre billeteras, como porque el análisis de seguridad del costo de los ataques de coincidencia parcial de cadenas de UA/UVK es más complicado si se incluyen caracteres de suma de verificación en los caracteres que se comparan.

#Uso de las claves de visualización de saliente

Cuando un Emisor construye una transacción que crea notas de Sapling u Orchard, usa una clave de visualización de saliente, como se describe en [6] y [7], para cifrar un criptograma de saliente. El descifrado con la clave de visualización de saliente permite recuperar el texto en claro de la nota enviada, incluidos la dirección de destino, el monto y el memo. La intención es que esta clave de visualización de saliente esté asociada con el origen de los fondos.

Sin embargo, la especificación de qué clave de visualización de saliente debe usarse queda algo abierta en [6] y [7]; en particular, no estaba claro si las transferencias debían considerarse como enviadas desde una dirección, o desde una cuenta del ZIP 32 [20]. La adopción de múltiples protocolos blindados que soportan claves de visualización de saliente (es decir, Sapling y Orchard) complica aún más esta cuestión, ya que desde la activación de NU5, nada a nivel de consenso impide que una billetera gaste tanto notas de Sapling como de Orchard en la misma transacción. (Se darán recomendaciones sobre el uso de múltiples pools por parte de las billeteras en el ZIP 315 [25].)

Aquí refinamos la especificación del protocolo a fin de permitir una determinación más precisa de la autoridad de visualización para las UFVK.

Un Emisor intentará determinar una "cuenta de envío" para cada transferencia. El enfoque preferido es que la API usada para realizar una transferencia especifique directamente una cuenta de envío. De lo contrario, si el Emisor puede constatar que todos los fondos usados en la transferencia provienen de direcciones asociadas con alguna cuenta, entonces DEBERÍA (SHOULD) tratar esa como la cuenta de envío. Si no, la cuenta de envío queda indeterminada.

El Remitente también determina un "protocolo de envío preferido" —uno de "transparente", "Sapling" u "Orchard"— correspondiente al Tipo de Receiver más preferido (según se indica en Codificación en bruto de direcciones unificadas) de cualquier fondo enviado en la transacción.

Si la cuenta de envío ha sido determinada, entonces el Emisor DEBERÍA (SHOULD) usar la 𝗈 𝗏 𝗄 externa o interna (según el tipo de transferencia), según lo especificado por el protocolo de envío preferido, de la clave de visualización completa para esa cuenta (es decir, a nivel de cuenta del ZIP 32).

Si la cuenta de envío está indeterminada, entonces el Emisor DEBERÍA (SHOULD) elegir una de las direcciones, restringido a direcciones para el protocolo de envío preferido, desde las cuales se envían fondos (por ejemplo, la primera para ese protocolo), y luego usar la 𝗈 𝗏 𝗄 externa o interna (según el tipo de transferencia) de la clave de visualización completa para esa dirección.

#Mezclado (jumbling)

Objetivo de seguridad (resistencia casi de segunda preimagen):

  • Se le da a un adversario q direcciones/claves de visualización unificadas, generadas honestamente.

  • El objetivo del ataque es producir una dirección/clave de visualización unificada válida "parcialmente en colisión" que:

    1. tenga una codificación textual que coincida con la de una de las direcciones/claves de visualización de entrada en algún subconjunto de caracteres (para ser concretos, considérense los primeros n y los últimos m caracteres, hasta cierto límite en n + m );

    2. esté controlada por el adversario (para ser concretos, el adversario conoce al menos una de las claves privadas de las direcciones constituyentes).

Objetivo de seguridad (no maleabilidad):

  • En esta variante, el punto b) anterior se reemplaza por la condición de que el significado de la nueva dirección/clave de visualización sea "útilmente" diferente del de aquella en la que se basa, aunque el adversario no conozca ninguna de las claves privadas. Por ejemplo, si fuera posible eliminar una dirección constituyente blindada de una UA dejando solo una dirección transparente, eso sería un ataque de maleabilidad significativo.

#Discusión

Existe un ataque genérico de fuerza bruta contra la resistencia casi de segunda preimagen. El adversario genera UAs / UVKs al azar con claves conocidas, hasta que una tenga una codificación que colisione parcialmente con uno de los q objetivos. Podría ser posible mejorar este ataque aprovechando propiedades de las sumas de verificación, etc.

El ataque genérico impone un límite superior a la seguridad alcanzable: si producir y verificar una UA / UVK requiere un trabajo w , y el tamaño del conjunto de caracteres es c , , entonces el ataque genérico cuesta ∼ w ⋅ c n + m q .

También existe un ataque genérico de fuerza bruta contra la no maleabilidad. El adversario modifica ligeramente la UA / UVK objetivo y calcula la decodificación correspondiente, luego repite hasta que la decodificación sea válida y además útil para el adversario (p. ej., que lleve al Remitente a usar una dirección transparente). Con w definido como arriba, el costo es w / p , donde p es la probabilidad de que una decodificación aleatoria tenga la forma requerida.

#Solución

Usamos una construcción Feistel de 4 rondas sin clave para aproximar una permutación aleatoria. (Como se explica más abajo, 3 rondas no serían suficientes.)

Sea H i un hash personalizado por i , con longitud máxima de salida de ℓ H bytes. Sea G i una XOF (una función hash con longitud de salida extendible) basada en H , personalizada por i .

Defínase ℓ M 𝖬 𝖠 𝖷 = ( 2 16 + 1 ) ⋅ ℓ H . Para la instanciación usando BLAKE2b definida abajo, ℓ M 𝖬 𝖠 𝖷 = 4194368 .

  • sea ℓ R = ℓ M − ℓ L

  • dividir M en a de longitud ℓ L bytes y b de longitud ℓ R bytes

  • sea x = b ⊕ G 0 ( a )

  • sea y = a ⊕ H 0 ( x )

  • sea d = x ⊕ G 1 ( y )

  • sea c = y ⊕ H 1 ( d )

  • retornar c | | d .

La función inversa 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 − 1 se obtiene de la manera usual para una construcción de Feistel, observando que r = p ⊕ q implica p = r ⊕ q .

El primer argumento de BLAKE2b más abajo es la personalización.

Instanciamos H i ( u ) por \mathsf{BLAKE2b‐}(8\ell_L)(\texttt{“UA_F4Jumble_H”} \,||\, [ i , 0 , 0 ] , u ) , con ℓ H = 64 .

Instanciamos G i ( u ) como los primeros ℓ R bytes de la concatenación de [\mathsf{BLAKE2b‐}512(\texttt{“UA_F4Jumble_G”} \,||\, [i] \,||\, 𝖨 𝟤 𝖫 𝖤 𝖮 𝖲 𝖯 16 ( j ) , u )  for  j  from 0  up to  𝖼 𝖾 𝗂 𝗅 𝗂 𝗇 𝗀 ( ℓ R / ℓ H ) − 1 ] .

(En la práctica, las longitudes ℓ L y ℓ R serán aproximadamente iguales hasta que ℓ M sea mayor que 128 bytes.)

#Uso para direcciones unificadas, UFVK y UIVK

Para prevenir el ataque genérico contra la no maleabilidad, es necesario que haya cierta redundancia en la codificación. Por lo tanto, el Productor de una dirección unificada, UFVK o UIVK añade el HRP, rellenado a 16 bytes con bytes cero, a la codificación en bruto, luego aplica 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 antes de codificar el resultado con Bech32m.

El Consumidor rechaza cualquier secuencia de bytes decodificada con Bech32m que tenga menos de 48 bytes o más de ℓ M 𝖬 𝖠 𝖷 bytes; de lo contrario, aplica 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 − 1 . . Rechaza cualquier resultado que no termine en el relleno esperado de 16 bytes, antes de eliminar estos 16 bytes y analizar el resultado.

(48 bytes permite que el tamaño mínimo de la codificación de un Ítem de dirección unificada, UFVK o UIVK blindado sea de 32 bytes, tomando en cuenta 16 bytes de relleno. Aunque actualmente no existe una codificación de Ítem blindado tan corta, es plausible que se agregue una en el futuro. ℓ M 𝖬 𝖠 𝖷 bytes es el tamaño máximo de entrada/salida soportado por 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 . )

#Análisis heurístico

Una Feistel de 3 rondas sin clave, como se muestra, no es suficiente:

Supóngase que un adversario tiene un par de entrada/salida objetivo ( a | | b , c | | d ) , y que la entrada a H 0 es x . . Al fijar x , podemos obtener otro par ( ( a ⊕ t ) | | b ' , ( c ⊕ t ) | | d ' ) tal que a ⊕ t esté cerca de a y c ⊕ t esté cerca de c . ( b ' y d ' no estarán cerca de b y d , , pero eso no es necesariamente requerido para un ataque válido).

Una Feistel de 4 rondas frustra este ataque y otros similares. Definiendo x y y como los valores intermedios del primer diagrama anterior:

  • si ( x ' , y ' ) se fijan a los mismos valores que ( x , y ) , , entonces ( a ' , b ' , c ' , d ' ) = ( a , b , c , d ) ;

  • si x ' = x pero y ' ≠ y , , entonces el adversario puede introducir una diferencia controlada a ⊕ a ' = y ⊕ y ' , de ⊕ , pero las otras tres piezas ( b , c , d ) están todas aleatorizadas, lo cual es suficiente;

  • si y ' = y pero x ' ≠ x , , entonces el adversario puede introducir una diferencia controlada d ⊕ d ' = x ⊕ x ' , de ⊕ , pero las otras tres piezas ( a , b , c ) están todas aleatorizadas, lo cual es suficiente;

  • si x ' ≠ x y y ' ≠ y , , las cuatro piezas están aleatorizadas.

Nótese que el tamaño de cada pieza es de al menos 24 bytes.

Sería posible hacer un ataque más costoso haciendo más costoso el trabajo realizado por un productor. (Esto no tendría necesariamente que incrementar el trabajo realizado por el consumidor). Sin embargo, dado que las direcciones unificadas podrían necesitar producirse en plataformas de computación restringidas, esto no se consideró beneficioso en general.

El relleno contiene el HRP para que el HRP tenga la misma protección contra maleabilidad que el resto de la dirección. Esto puede ayudar contra ataques entre redes, o ataques que confundan direcciones con claves de visualización.

#Eficiencia

El costo está dominado por 4 compresiones BLAKE2b para ℓ M ≤ 128 bytes. Una dirección unificada que contenga una dirección transparente, una dirección Sapling y una dirección Orchard tendría ℓ M = 128 bytes. La restricción a una sola dirección con un Typecode dado (y a lo sumo una dirección transparente) implica que esta es también la longitud máxima de una dirección unificada que contenga solo Receiver Types definidos a partir de la activación de NU5.

Para direcciones unificadas más largas (cuando se agreguen otros Receiver Types) o UVKs, el costo aumenta a 6 compresiones BLAKE2b para 128 < ℓ M ≤ 192 , y 10 compresiones BLAKE2b para 192 < ℓ M ≤ 256 , , por ejemplo. El costo máximo para el cual el algoritmo está definido sería de 196608 compresiones BLAKE2b a ℓ M = ℓ M 𝖬 𝖠 𝖷 bytes.

Una implementación ingenua de la función 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 − 1 requeriría aproximadamente ℓ M bytes más el tamaño de un estado de hash BLAKE2b. Sin embargo, es posible reducir esto transmitiendo en flujo la parte d de la codificación mezclada tres veces desde un dispositivo con menos restricciones de memoria. Es esencial que el valor transmitido de d sea el mismo en cada pasada, lo cual puede verificarse mediante un código de autenticación de mensajes (con una clave mantenida solo por el Consumidor) o una función hash resistente a colisiones. Después de la primera pasada de d , la implementación puede calcular y ; ; después de la segunda pasada puede calcular a ; , y la tercera le permite calcular y analizar incrementalmente b . . El uso máximo de memoria durante este proceso sería de 128 bytes más dos estados de hash BLAKE2b.

Dado que esta implementación de flujo de 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 − 1 es bastante complicada, no requerimos que todos los Consumidores soporten flujo. Si una implementación de un Consumidor no puede soportar direcciones unificadas / UVKs hasta la longitud máxima, DEBE (MUST) no obstante soportar direcciones unificadas / UVKs con ℓ M de al menos 256 bytes. Nótese que esto define efectivamente dos niveles de conformidad con esta especificación. Una implementación completa soportará direcciones unificadas / UVKs hasta la longitud máxima.

#Codificaciones QR de direcciones unificadas y claves de visualización unificadas

La codificación QR unificada de una dirección unificada o UVK es la especificada en [8]; es decir, la representación en código QR de su codificación de cadena unificada convertida a mayúsculas, usando el modo alfanumérico especificado en las secciones 7.3.4 y 7.4.4 de [37].

Un Consumidor PUEDE (MAY) soportar el análisis sintáctico de múltiples tipos de dirección y/o clave de visualización a partir de un código QR, en cuyo caso DEBERÍA (SHOULD) usar el HRP para reconocer provisionalmente (sujeto a validación adicional) posibles tipos de dirección o clave de visualización.

Cuando un Consumidor reconoce el contenido de un código QR como una posible codificación de cadena unificada, NO DEBERÍA (SHOULD NOT) presentar el contenido resultante al usuario como si representara una dirección, sin verificar primero que es una codificación de cadena unificada válida intentando decodificarla.

Un Productor NO DEBE (MUST NOT) generar una codificación QR directamente a partir de una codificación cruda unificada (usando el "modo Byte" de QR definido en la sección 7.3.5 de [37], o de otro modo).

#Justificación de no usar el modo Byte

Un código QR que use la codificación cruda unificada en modo Byte podría ser ligeramente más pequeño; sin embargo, creemos que esta elección probablemente causaría problemas de interoperabilidad. Tampoco satisfaría el requisito de que la codificación cruda unificada no se muestre a los usuarios, ya que es común que el software que soporta códigos QR intente decodificar el contenido y presentarlo como una cadena. (La cláusula 6.1 b) 3) de [37] especifica que la interpretación por defecto de los datos de bytes es como una cadena de texto ISO-8859-1.)
