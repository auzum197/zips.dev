#Terminología

Las palabras clave "DEBE (MUST)" y "PUEDE (MAY)" de este documento deben interpretarse como se describe en el RFC 2119. [1]

#Resumen

Este documento propone un cambio de la base de datos que la billetera de zcashd utiliza actualmente, de BerkeleyDB a SQLite. También propone la separación de las transacciones de la billetera y otros datos recuperables en un archivo de base de datos separado.

#Motivación

La razón principal del cambio de base de datos es la confiabilidad; SQLite tiene una muy buena implementación de atomicidad [2]. Las bases de datos relacionales reducen la redundancia y SQLite específicamente es la más usada del mundo para almacenamiento local; además, está bien mantenida, tiene una buena interfaz para C++, es portátil y de código abierto.

La separación de la base de datos entre datos recuperables y no recuperables tiene como objetivo evitar escribir con demasiada frecuencia en el archivo donde se encuentran los datos importantes no recuperables, como las claves públicas y privadas. Aislar las transacciones y otros datos de la base de datos principal de la billetera aumentará el rendimiento y reducirá el riesgo de corrupción.

#Especificación

Después de [3] y su información detallada sobre todas las claves-valores de la base de datos y su funcionalidad, sabemos qué se necesita para cambiar la base de datos fundamental a otra cosa.

Este documento propone un nuevo esquema relacional para 2 nuevas bases de datos SQLite donde todas las propiedades originales están presentes, pero solo organizadas de una manera diferente. El esquema siguiente es una aproximación y puede cambiar durante la implementación.

Se propone el siguiente esquema sql para una base de datos llamada wallet.sqlite con información no recuperable:

CREATE TABLE accounts(
    id                INTEGER PRIMARY KEY AUTOINCREMENT
    id_address        INTEGER
    name              TEXT
    account           BLOB);

CREATE TABLE account_entries(
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    id_account        INTEGER,
    entry             BLOB);

CREATE TABLE addresses(
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    address           TEXT,
    id_account        INTEGER,
    name              TEXT,
    purpose           TEXT);

CREATE TABLE destdata(
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    id_address        INTEGER,
    key               TEXT,
    value             TEXT);

CREATE TABLE sapling(
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    id_address        INTEGER,
    key               BLOB,
    ckey              BLOB,
    meta              BLOB,
    cmeta             BLOB,
    ivk               BLOB,
    extfvk            BLOB);

CREATE TABLE settings(
    chdseed           BLOB
    hdchain           BLOB
    hdseed            BLOB
    minversion        TEXT
    mkey              BLOB
    version           TEXT
    cscript           BLOB);

CREATE TABLE sprout(
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    id_address        INTEGER,
    key               BLOB,
    ckey              BLOB,
    meta              BLOB,
    cmeta             BLOB,
    vkey              BLOB);

CREATE TABLE transparent(
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    id_address        INTEGER,
    key               BLOB,
    ckey              BLOB,
    poolindex         INTEGER,
    meta              BLOB,
    cmeta             BLOB,
    destination       TEXT,
    is_default        BOOLEAN);

Se propone una base de datos separada llamada transactions.sqlite con información recuperable y las siguientes tablas:

CREATE TABLE transactions(
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    hash              BLOB,
    tx                BLOB);

CREATE TABLE state(
    bestblock         BLOB,
    orderposnext      INTEGER,
    witnesscachesize  INTEGER);

Se agregará una nueva clase SQLite a la colección de clases de la billetera, donde se pueden encontrar las siguientes funciones de bajo nivel:

  • Open(strFile) - Abrir un nuevo archivo de base de datos.

  • Exist(strFile) - Comprobar si existe una base de datos.

  • Schema(strSchema) - Crear un nuevo esquema.

  • Write(strSql) - Insertar o actualizar una tabla de la base de datos.

  • Read(strSql) - Seleccionar datos de una tabla.

  • Erase(strSql) - Eliminar filas de una tabla.

  • Count(strSql) - Obtener la cantidad de filas de una consulta de selección. Este es un caso especial de Read().

  • GetRow(strSql) - Obtener una sola fila de una tabla. Este es un caso especial de Read().

  • GetVersion(strFile) - Obtener la versión de la base de datos actual.

CWalletDB se renombra a CWalletDBD para evitar ambigüedad. Se creará una nueva clase CWalletSQLite como una copia de la misma definición. Esto significa que la nueva clase tendrá las mismas funciones miembro con los mismos argumentos y los mismos valores de retorno que la versión original; la diferencia está en la implementación de las funciones, donde las de la nueva clase escribirán/leerán en/desde SQLite usando las funciones de bajo nivel enumeradas anteriormente.

Como ejemplo, en CWalletDB actualmente tenemos WriteSaplingPaymentAddress:

return Write(std::make_pair(std::string("sapzaddr"), addr), ivk, false);

Después de la implementación, esta función se ubicará en CWalletDBD::WriteSaplingPaymentAddress() con la misma funcionalidad.

En CWalletSQLite::WriteSaplingPaymentAddress() una implementación posible puede ser algo similar a:

auto id_address = GetRow("SELECT id from addresses WHERE address=addr");
return Write("INSERT OR REPLACE INTO sapling(id_address, ivk) VALUES(id_address, ivk)");

Todas las funciones miembro de la nueva clase CWalletSQLite deben refactorizarse para interactuar con la nueva base de datos. Pueden existir excepciones a esta regla si el rendimiento puede aumentarse cambiando las entradas/salidas de cualquiera de las funciones miembro o combinando 2 o más funciones en 1.

#Adición de más claves

Es una práctica común de los desarrolladores de zcashd añadir nuevas claves y valores a la base de datos para diferentes propósitos; para hacerlo en SQLite el esquema debe cambiar. La implementación debe garantizar que añadir nuevos campos a cualquier tabla sea un cambio no disruptivo, mientras que renombrar tablas, renombrar columnas o cambiar los tipos de columna puede ser fatal si no se implementa correctamente.

Para mitigar el riesgo debe implementarse un sistema de versiones, de modo que los esquemas más antiguos de la base de datos puedan actualizarse correctamente. La implementación debe crear pruebas del esquema.

#Requisitos

Se necesita Sqlite3 como dependencia de zcashd [5]. No se necesitan dependencias adicionales.

#Compatibilidad con versiones anteriores

Una nueva billetera creada después de que el código esté implementado y probado se creará con SQLite. Pueden proporcionarse opciones de línea de comandos para elegir la base de datos subyacente. Una herramienta de conversión desde/hacia SQLite/BDB puede ser útil y puede proporcionarse como parte de la implementación.
