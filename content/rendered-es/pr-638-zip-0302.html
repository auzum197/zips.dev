#Resumen

Este ZIP describe una especificación propuesta para un formato estandarizado destinado a clientes que deseen transmitir o recibir contenido dentro del campo memo cifrado de transacciones blindadas.

#Motivación

Un estándar bien definido para dar formato al contenido dentro del campo memo cifrado ayudará a ampliar su uso en el ecosistema de Zcash al proporcionar un formato comúnmente reconocido para valores de memo que transportan distintos tipos de datos. Los usuarios y los servicios de terceros se benefician de reglas de formato estandarizadas que definen el tipo y la longitud de los datos contenidos en él.

#Especificación

La sección 5.5 de la especificación del protocolo de Zcash [1] define tres casos para la codificación de un campo memo:

  • una cadena legible por humanos en UTF-8 [2], rellenada mediante la adición de bytes cero al final; o

  • el byte 0xF6 seguido de 511 bytes 0x00, lo que indica "sin memo"; o

  • cualquier otra secuencia de 512 bytes que comience con un valor de byte 0xF5 o mayor (que por lo tanto no es una cadena UTF-8 válida), según lo especificado en el ZIP 302.

Este ZIP refina la especificación del tercer caso.

La siguiente especificación restringe a una parte, llamada el "lector", que interpreta el contenido de un memo. No define requisitos de consenso.

  • Si el primer byte (byte 0) tiene un valor de 0xF4 o menor, entonces el lector DEBE (MUST):

    • eliminar los bytes cero finales

    • decodificarlo como una cadena UTF-8 (si la decodificación falla, reportar un error).

  • Si el primer byte tiene un valor de 0xF6, y los 511 bytes restantes son 0x00, entonces el usuario no suministró ningún memo, y el campo memo cifrado debe tratarse como vacío.

  • Si el primer byte tiene un valor de 0xF7, entonces el lector DEBE (MUST) interpretar el memo como un memo estructurado; véase la siguiente sección para su formato.

  • Si el memo coincide con alguno de estos patrones, entonces este memo proviene del futuro, porque estos rangos están reservados para futuras actualizaciones de esta especificación:

    • El primer byte tiene un valor de 0xF6, y los 511 bytes restantes no son todos 0x00.

    • El primer byte tiene un valor entre 0xF8 y 0xFE inclusive.

  • Si el primer byte tiene un valor de 0xFF, el lector no debería hacer ninguna otra suposición sobre el memo. Para colocar datos arbitrarios en un campo memo (que podría tener alguna estructura privada no estándar), el valor del primer byte DEBERÍA (SHOULD) establecerse en 0xFF; los 511 bytes restantes quedan entonces sin restricción.

  • Si el primer byte tiene un valor de 0xF5, el lector no debería hacer ninguna otra suposición sobre el memo. Este valor se usó de manera ambigua en el pasado por acuerdo privado; las aplicaciones DEBERÍAN (SHOULD) preferir 0xFF, que está inequívocamente destinado a este propósito.

#Memos estructurados

Un memo puede usarse para almacenar datos estructurados estableciendo su primer byte en un valor de 0xF7. Los bytes restantes contienen un conjunto de "partes de memo", codificadas como tuplas Tipo-Versión-Longitud-Valor concatenadas, seguidas de relleno fijo (si quedan bytes de memo después de las tuplas TVLV).

No se permiten múltiples partes de memo del mismo tipo en los memos estructurados.

#Análisis sintáctico de un memo estructurado

Después del byte inicial 0xF7, los lectores analizan los bytes de memo restantes de la siguiente manera:

  • Mientras queden bytes de memo sin analizar:

    • Analizar un compactSize para obtener partType. Si no hay bytes suficientes para analizar un compactSize, devolver un error.

    • Si partType == 0:

      • Este es un tipo de marcador que indica que no hay más tuplas TVLV. Si alguno de los bytes de memo restantes no es 0x00, devolver un error.

    • De lo contrario, si partType ya fue analizado en una parte de memo anterior, devolver un error.

    • En caso contrario:

      • Analizar un compactSize para obtener partVersion. Si no hay bytes suficientes para analizar un compactSize, devolver un error.

      • Analizar un compactSize para obtener partLength. Si no hay bytes suficientes para analizar un compactSize, devolver un error.

      • Leer los siguientes partLength bytes para obtener partValue. Si partLength requeriría que el lector lea más allá del final de los bytes del memo, devolver un error.

      • Almacenar (partType, partVersion, partValue) y continuar el análisis.

Si ocurre un error, los lectores DEBEN (MUST) tratar el memo completo como inválido (ignorando cualquier MemoPart que se haya analizado con éxito antes del error).

#Adición de nuevos tipos

Es intencional que los nuevos tipos de parte de memo DEBERÍAN (SHOULD) introducirse mediante una modificación a este ZIP, ya sea directamente o a través de una sección de cambios de un nuevo ZIP, de conformidad con el Proceso de ZIP [4].

Los enteros partType en el rango de 10000 a 19999 inclusive son asignados por los Editores de ZIP para "uso privado asignado". Están destinados a respaldar el uso a largo plazo de tipos de parte de memo sin especificaciones públicas de codificación partValue (especialmente en entornos de despliegue donde el tipo de parte de memo de "datos sin restricciones" no es adecuado debido a la posibilidad de colisión de usos). Para solicitar uno o más tipos de parte de memo para uso privado asignado, consulte directamente a los Editores de ZIP o abra una incidencia en el repositorio de ZIPs. Los solicitantes NO DEBEN (MUST NOT) asignar enteros específicos por sí mismos, ni asumir que un subrango particular está sin usar.

Para experimentar antes de proponer un nuevo tipo de parte de memo en un ZIP, PUEDEN (MAY) añadirse partes de memo experimentales utilizando los partTypes 65530 a 65535 inclusive reservados. Esto permite seis experimentos simultáneos, que pueden denominarse experimentos A a F. Esto debería ser suficiente porque se espera que los experimentos sean razonablemente de corto plazo, y de lo contrario deberían ser estandarizados en un ZIP (y asignárseles un partType fuera de este rango reservado) o descontinuados.

#Justificación

La nueva especificación del protocolo es una mejora respecto de la especificación actual del contenido del campo memo que estaba en la especificación del protocolo hasta la versión 2020.1.0, la cual establecía:

El uso del campo memo es por acuerdo entre el emisor y el destinatario de la nota. El campo memo DEBERÍA (SHOULD) codificarse como:

  • una cadena UTF-8 legible por humanos [Unicode], rellenada mediante la adición de bytes cero al final; o

  • una secuencia arbitraria de 512 bytes que comienza con un valor de byte de 0xF5 o mayor, que por lo tanto no es una cadena UTF-8 válida.

En el primer caso, se espera que el software de la billetera elimine cualquier byte cero final y luego muestre la cadena UTF-8 resultante al usuario destinatario, donde corresponda. Las secuencias de bytes codificadas incorrectamente en UTF-8 deberían mostrarse como caracteres de reemplazo (U+FFFD).

En el segundo caso, el contenido del campo memo NO DEBERÍA (SHOULD NOT) mostrarse. Un byte inicial de 0xF5 está reservado para su uso por software automatizado mediante acuerdo privado. Un byte inicial de 0xF6 o mayor está reservado para su uso en futuras extensiones del protocolo de Zcash.

Véase la incidencia #1849 para mayor discusión.

#partVersion en el nivel superior de los memos estructurados

Es intencional que solo esté presente una parte de memo de cada tipo en un memo; cualquier formato contenedor debería representarse dentro de partValue. Sin embargo, también es deseable que las codificaciones partValue puedan actualizarse con el tiempo a medida que se realizan cambios en los protocolos a nivel de billetera que las utilizan. Sin un campo de versión explícito, la única alternativa sería asignar un nuevo partType para la nueva versión, momento en el cual sería posible que un memo contenga dos versiones de los mismos datos semánticos. Al tener un campo de versión explícito, las billeteras pueden distinguir de manera compatible con versiones futuras entre una nueva versión de un tipo de parte de memo que están manejando actualmente, y un nuevo tipo de parte de memo que no conocen.

Un argumento previo contra los bytes de versión explícitos en el nivel superior era que el espacio del memo está limitado a 511 bytes, y requerir que cada tipo de parte de memo tenga un byte de versión añadiría una sobrecarga del 25-50% sobre el encabezado TLV. Sin embargo, una vez que se desplieguen los Memo Bundles del ZIP 231 [5], un solo memo puede tener como máximo 16384 bytes en una transacción v6, lo que debilita este argumento.

#Compatibilidad con versiones anteriores

Los contenidos del campo memo cifrado enviados sin el formato estandarizado propuesto aquí se interpretarán según la especificación establecida en versiones anteriores de la especificación del protocolo.
