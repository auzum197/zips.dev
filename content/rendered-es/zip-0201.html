#Terminología

Las palabras clave "DEBE (MUST)", "NO DEBE (MUST NOT)", "DEBERÍA (SHOULD)" y "PUEDE (MAY)" en este documento deben interpretarse como se describe en el BCP 14 [1] cuando, y solo cuando, aparecen en mayúsculas.

Los términos "rama de consenso" y "actualización de red" de este documento deben interpretarse como se describe en el ZIP 200. [3]

Los términos que siguen deben interpretarse así:

Overwinter

Nombre en clave de la primera actualización de red de Zcash, también conocida como Network Upgrade Zero.

#Resumen

Esta propuesta define una mejora del protocolo de enlace de red y de la gestión de pares requerida para las actualizaciones de red conforme al Mecanismo de Actualización de Red [3].

Relacionado con:

  • Validación de firmas de transacciones para Overwinter [2].

  • Formato de transacción versión 3 para Overwinter [4].

  • Expiración de transacciones [5].

#Motivación

Con actualizaciones de red programadas, en la altura de activación, los nodos de cada rama de consenso deberían desconectarse de los nodos de otras ramas de consenso y aceptar únicamente nuevas conexiones entrantes de nodos de la misma rama de consenso.

#Especificación

Cuando se recibe una nueva conexión entrante o se crea una conexión saliente, se instancia un objeto CNode con el campo version establecido en INIT_PROTO_VERSION, que tiene un valor de 209. Este valor no se transmite por la red, pero por razones de legado y deuda técnica que están fuera del alcance de este ZIP, este valor no se cambiará.

Una vez que los dos nodos se han conectado e iniciado el protocolo de enlace para negociar la versión del protocolo, el campo version de CNode se actualizará. El protocolo de enlace [8] consiste en el intercambio de mensajes "version" y "verack":

L -> R: Send version message with the local peer's version
R -> L: Send version message back
R -> L: Send verack message
R:      Sets version to the minimum of the 2 versions
L -> R: Send verack message after receiving version message from R
L:      Sets version to the minimum of the 2 versions

Para enviar un mensaje version, el nodo invocará PushVersion():

void CNode::PushVersion() {
    ...
    PushMessage("version", PROTOCOL_VERSION, nLocalServices, nTime, addrYou, addrMe, ...);
    ...
}

donde PROTOCOL_VERSION es la versión más alta del protocolo que admite el nodo.

#Rechazo de conexiones anteriores a Overwinter

Actualmente, los nodos rechazan conexiones de pares con una versión de protocolo anunciada inferior a la versión mínima del protocolo que admite el otro nodo.

Este valor se define como:

//! disconnect from peers older than this proto version
static const int MIN_PEER_PROTO_VERSION = 170002;

Con el rechazo implementado de la siguiente manera:

if (pfrom->nVersion < MIN_PEER_PROTO_VERSION)
{
    // disconnect from old peers running protocol version we don't support.

La activación de Overwinter tendrá lugar primero en testnet y, si resulta exitosa, continuará en mainnet.

Para preparar la activación en testnet, los nodos de Overwinter contendrán las siguientes constantes:

static const int PROTOCOL_VERSION = 170003;
static const int MIN_PEER_PROTO_VERSION = 170002;

Los nodos que ejecutan la versión de protocolo 170003 tienen una altura de activación de testnet establecida, pero no tienen una altura de activación de mainnet establecida.

En testnet, se define que un nodo anterior a Overwinter es un nodo cuya versión de protocolo más alta admitida es <= 170002.

Estas constantes permiten que los nodos anteriores a Overwinter que admiten la versión de protocolo 170002, y los nodos de Overwinter (que admiten tanto la versión de protocolo 170002 como la 170003 antes de la activación de Overwinter), permanezcan conectados hasta la activación.

Para preparar la activación en mainnet, los nodos de Overwinter contendrán las siguientes constantes:

static const int PROTOCOL_VERSION = 170005;
static const int MIN_PEER_PROTO_VERSION = 170002;

En mainnet, se define que un nodo anterior a Overwinter es un nodo cuya versión de protocolo más alta admitida es <= 170004. (Los nodos que ejecutan la versión de protocolo 170003 o 170004 no tienen una altura de activación de mainnet establecida. La versión de protocolo intermedia 170004 se usa para indicar la admisión del bit de servicio NODE_BLOOM definido en [6].)

Estas constantes permiten que los nodos anteriores a Overwinter que admiten las versiones de protocolo 170002 a 170004 inclusive, y los nodos de Overwinter (que admiten las versiones de protocolo 170002 a 170005 inclusive antes de la activación de Overwinter), permanezcan conectados hasta la activación.

Dado que estas constantes no se pueden cambiar en tiempo de ejecución, una vez que Overwinter se active en testnet o en mainnet, los nodos de Overwinter deberían tomar medidas para:

  • rechazar nuevas conexiones de nodos anteriores a Overwinter;

  • desconectar cualquier conexión existente con nodos anteriores a Overwinter.

#Coalescencia de la red

Antes de la activación de Overwinter, los nodos que ejecutan una versión de protocolo anterior a Overwinter (p. ej. 170002) y la versión de protocolo de Overwinter (170003 para testnet; 170005 para mainnet) permanecen conectados con las mismas reglas de consenso, pero es deseable que los nodos que admiten Overwinter se conecten de manera preferente a otros nodos que admitan Overwinter.

Esto tiene como objetivo ayudar a que la red se divida de forma fluida, ya que los nodos ya deberían estar conectados a (una mayoría de) pares que ejecutan la misma versión de protocolo. De lo contrario, un nodo de Overwinter podría ver cómo sus conexiones a nodos de Sprout se cortan repentinamente en la altura de activación, dejándolo potencialmente aislado y susceptible a ataques de eclipsado. [9]

Para asistir la coalescencia de la red antes de la altura de activación, actualizamos el proceso de desalojo para dar una mayor prioridad al desalojo de nodos de Sprout.

Actualmente, un proceso de desalojo tiene lugar cuando llegan nuevas conexiones entrantes, pero el nodo ya está conectado al número máximo de pares entrantes:

if (nInbound >= nMaxInbound)
{
    if (!AttemptToEvictConnection(whitelisted)) {
        // No connection to evict, disconnect the new connection
        LogPrint("net", "failed to find an eviction candidate - connection dropped (full)\n");
        CloseSocket(hSocket);
        return;
    }
}

Actualizamos este proceso añadiendo un comportamiento para que el conjunto de candidatos a desalojo dé preferencia a los nodos anteriores a Overwinter, cuando la punta de la cadena esté en un periodo de N bloques antes de la altura de bloque de activación, donde N se define como:

/** The period before a network upgrade activates, where connections to upgrading peers are preferred (in blocks). */
static const int NETWORK_UPGRADE_PEER_PREFERENCE_BLOCK_PERIOD = 24 * 24 * 3;

Los candidatos a desalojo se pueden modificar así:

static bool AttemptToEvictConnection(bool fPreferNewConnection) {
...
// Protect connections with certain characteristics
...
// Check version of eviction candidates...
// If we are connected to any pre-Overwinter nodes, keep them in the eviction set and remove any Overwinter nodes
// If we are only connected to Overwinter nodes, continue with existing behaviour.
if (nActivationHeight > 0 &&
    height < nActivationHeight &&
    height >= nActivationHeight - NETWORK_UPGRADE_PEER_PREFERENCE_BLOCK_PERIOD)
{
    // Find any nodes which don't support Overwinter protocol version
    BOOST_FOREACH(const CNodeRef &node, vEvictionCandidates) {
        if (node->nVersion < params.vUpgrades[Consensus::UPGRADE_OVERWINTER].nProtocolVersion) {
            vTmpEvictionCandidates.push_back(node);
        }
    }

    // Prioritize these nodes by replacing eviction set with them
    if (vTmpEvictionCandidates.size() > 0) {
        vEvictionCandidates = vTmpEvictionCandidates;
    }
}

El método existente de desconexión de un candidato permanece:

vEvictionCandidates[0]->fDisconnect = true;

El proceso de desalojo existente clasificará y dividirá a los candidatos a desalojo en grupos llamados netgroup. Si un netgroup solo tiene un par, este no será desalojado. Esto significa que al menos un nodo anterior a Overwinter permanecerá conectado hasta la altura de bloque de activación, salvo problemas de red o una puntuación de expulsión alta.

#Desconexión de conexiones existentes

En la altura de bloque de activación, un nodo de Overwinter puede seguir conectado a nodos anteriores a Overwinter. Actualmente, al conectarse, un nodo solo puede realizar el protocolo de enlace de red una vez, donde envía el mensaje version antes de que se procese cualquier otro mensaje. Para desconectar las conexiones existentes anteriores a Overwinter, se modifica ProcessMessage de modo que, una vez que Overwinter se active, si es necesario, la versión de protocolo de un par existente se valide cuando lleguen los mensajes entrantes.

Código de ejemplo:

bool static ProcessMessage(CNode* pfrom, string strCommand, CDataStream& vRecv, int64_t nTimeReceived)
    ...
    else if (pfrom->nVersion == 0)
    {
        // Must have a version message before anything else
        Misbehaving(pfrom->GetId(), 1);
        return false;
    }
    else if (strCommand == "verack")
    {
        ...
    }

    // Disconnect existing peer connection when:
    // 1. The version message has been received
    // 2. Overwinter is active
    // 3. Peer version is pre-Overwinter
    else if (NetworkUpgradeActive(GetHeight(), chainparams.GetConsensus(), Consensus::UPGRADE_OVERWINTER)
            && (pfrom->nVersion < chainparams.GetConsensus().vUpgrades[Consensus::UPGRADE_OVERWINTER].nProtocolVersion))
    {
        LogPrintf("peer=%d using obsolete version %i; disconnecting\n", pfrom->id, pfrom->nVersion);
        pfrom->PushMessage("reject", strCommand, REJECT_OBSOLETE,
                            strprintf("Version must be %d or greater",
                            chainparams.GetConsensus().vUpgrades[Consensus::UPGRADE_OVERWINTER].nProtocolVersion));
        pfrom->fDisconnect = true;
        return false;
    }

#Compatibilidad con versiones anteriores

Antes de que la actualización de red se active, los nodos de Overwinter y los nodos previos a Overwinter son compatibles y pueden conectarse entre sí. Sin embargo, los nodos de Overwinter tendrán una preferencia por conectarse a otros nodos de Overwinter, por lo que los nodos previos a Overwinter serán desconectados gradualmente en el periodo previo a la activación.

Una vez que la red se actualice, aunque los nodos previos a Overwinter aún puedan aceptar como válida la versión de protocolo numéricamente mayor usada por Overwinter, los nodos de Overwinter siempre desconectarán a los pares que usen versiones de protocolo inferiores.
