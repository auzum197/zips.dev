#Resumen

Esta propuesta especifica tres enfoques posibles para integrar el protocolo zk-Channels [#zk-Channels-paper]_ en Zcash.

#Motivación

Los protocolos de capa 2 como Lightning permiten pagos escalables para Bitcoin, pero carecen de los mecanismos para ofrecer garantías de privacidad sólidas en la red de pagos. Zcash ofrece transacciones privadas, pero actualmente carece de características que permitirían un canal de pago al estilo de Lightning. Esta propuesta especifica una integración del protocolo de canales de pago que preserva la privacidad zkChannel sobre Zcash [#zk-Channels-paper]_.

#Vista general de zk-Channels a alto nivel

zk-Channels permite que dos partes, un cliente y un comerciante, abran un canal de pago anónimo y asimétrico donde solo el cliente puede iniciar la apertura del canal y los pagos. Si bien la apertura y el cierre del canal se transmiten en la cadena, lo que hace que los participantes del canal sean a lo sumo seudónimos, los pagos se realizan directamente entre el cliente y el comerciante fuera de la cadena de forma anónima e inenlazable.

La apertura del canal puede dividirse en tres fases: inicialización, activación y desvinculación:

  1. en la fase de inicialización, el cliente y el comerciante configuran el canal acordando los saldos iniciales y la información auxiliar.

  2. en la fase de activación, el comerciante se asegura de que el canal haya sido financiado correctamente y envía al cliente un token de pago para permitirle transferir fondos.

  3. el objetivo de la fase de desvinculación es desvincular la apertura del canal de pagos posteriores realizando un primer pago no vinculable de monto nulo.

Los pagos fuera de la cadena también se dividen en tres fases: configuración, actualización de estado y revelación.

  1. en la fase de configuración, el cliente genera de forma privada un nuevo estado del canal y envía una solicitud de pago al cliente. El comerciante verifica que no sea un doble gasto y, en caso afirmativo, acepta o rechaza el nuevo pago.

  2. en la fase de actualización de estado, el cliente y el comerciante participan en un zk-protocolo donde el comerciante acuerda el nuevo pago firmando a ciegas el nuevo estado del canal, al mismo tiempo que revoca el estado actual.

  3. en la fase de revelación, el cliente y el comerciante obtienen el token de pago y de revocación para cerrar el zk-channel en la cadena.

El canal puede cerrarse de tres maneras diferentes:

  • unilateralmente por el comerciante. En ese caso, el comerciante usa la información de cierre intercambiada en la inicialización del canal para transmitir en la cadena una transacción de expiración; el monto total queda bloqueado temporalmente.

    1. durante el bloqueo temporal, el cliente puede transmitir un cierre de cliente que anula la transacción de expiración;

    2. después del bloqueo temporal, el comerciante puede reclamar los fondos.

  • unilateralmente por el cliente. En ese caso, el cliente usa el mensaje de autorización de cierre recibido en una fase de actualización de estado para transmitir en la cadena una transacción de cierre de cliente; el saldo del comerciante se envía directamente al comerciante, mientras que el saldo del cliente queda bloqueado temporalmente.

    1. durante el bloqueo temporal, el saldo del cliente puede ser disputado por el comerciante, en caso de que el cliente haya cerrado sobre un estado desactualizado, mediante la revelación del secreto de revocación. En ese caso, todos los fondos van al comerciante;

    2. después del bloqueo temporal, el cliente puede reclamar los fondos.

  • mutuamente. En ese caso, el cliente y el comerciante intercambian información para generar una transacción multisig que cierra el canal.

#1. Requisitos

#1.1 Requisitos generales del protocolo zk-Channels

Los canales de pago privados zk-Channels requieren las siguientes capacidades para proporcionar propiedades de anonimato a los usuarios en una red de pagos:

  1. Capacidad de crear una transacción de depósito en garantía de modo que las entradas de la transacción sean anónimas.

  2. Capacidad de depositar fondos en garantía hacia una dirección de tipo multifirma mediante transacciones no maleables.

  3. Capacidad de especificar bloqueos temporales relativos para las transacciones de compromiso, a fin de admitir el cierre unilateral del canal.

  4. Capacidad de validar transacciones de apertura y de cierre específicas de zk-Channels:

  1. verificar la validez de la firma aleatorizada/a ciegas sobre el estado del canal en el token de cierre;

  2. verificar la validez del bloqueo de revocación en caso de una disputa del canal por parte del comerciante.

  1. Capacidad de hacer cumplir un flujo de transacciones gracias a las Transparent ZCash Extensions [#zip-0222]

  2. Capacidad de verificar las salidas de las transacciones mediante TZE de modo que:

  1. si el cierre es iniciado por el cliente, una salida paga al cliente con un bloqueo temporal (para permitir que el comerciante dispute el saldo del cliente) y una salida paga al comerciante de inmediato;

  2. si el cierre es iniciado por el comerciante, una única salida paga al comerciante el saldo total del canal con un bloqueo temporal que permite la disputa del cliente.

Supuestos de operación del canal.

  • Se admiten tanto los canales financiados únicamente por el cliente como los canales con financiación dual.

  • Tanto el cliente como el comerciante pueden iniciar el cierre del canal.

  • Si el cliente inicia el cierre, el comerciante puede disputar la transacción de cierre si no está de acuerdo con el token de cierre incluido en la transacción de cierre.

  • Si el comerciante inicia el cierre, este publica una transacción que reclama para sí todos los fondos del canal con un bloqueo temporal. Esto le da al cliente la oportunidad de publicar su propia transacción de cierre válida con los saldos actuales del canal. Si el cliente publica su propia transacción de cierre, el comerciante tiene una oportunidad adicional de disputarla si es necesario.

#1.2 Requisitos de TZE para el protocolo zk-Channels

  1. Capacidad de verificar el remitente de la transacción actual;

  2. Capacidad de verificar el propietario de una dirección;

  3. Capacidad de verificar el monto de una dirección;

  4. Capacidad de verificar la altura de bloque actual;

  5. Capacidad de verificar información sobre una transacción de una dirección TZE de entrada;

  6. Capacidad de verificar firmas Pointcheval-Sanders sobre mensajes específicos;

  7. Capacidad de afirmar el resultado de un hash lock;

#2 Algoritmos y variables

#2.1 Claves de firma del cliente y del comerciante

El cliente y el comerciante tienen ambos pares de claves de un esquema de firma adecuado para enviar y recibir transacciones, p. ej., pares de claves de firma ECDSA o RedDSA. Estos se denotan como: <cust-pk>, <cust-sk> y <merch-pk>, <merch-sk>, respectivamente, donde pk significa "clave pública" y sk significa la "clave secreta" correspondiente.

El comerciante debe poder emitir firmas ciegas, por ejemplo firmas ciegas Pointcheval-Sanders (PS), por lo que tiene un par de claves adicional; este par de claves se denota como: <merch-ps-pk>, <merch-ps-sk>. Para verificar una firma PS, se utilizará la siguiente función: PS_sig.Verify(merch-ps-pk, message, signature).

El par de claves del cliente es específico del canal y no debe reutilizarse. El par de claves del comerciante es de largo plazo y debería usarse para todos los canales de clientes.

#2.2 Estados del canal

zk-Channels se basa en el concepto de estados. Cuando el cliente inicia un pago, consulta al comerciante para que acepte un nuevo estado mientras revoca el actual.

Los únicos invariantes de un zk-channel son el identificador del canal <cid> y las claves públicas de sus participantes. Un estado del canal consiste en:

  • el identificador del canal: <cid>;

  • las claves públicas del comerciante: <merch-pk>, <merch-ps-pk> (definidas en 1.1);

  • las claves públicas del cliente: <cust-pk> (definidas en 1.1);

  • el saldo del cliente: <cust-balance>;

  • el saldo del comerciante: <merch-balance>;

  • el candado de revocación: <rev-lock>, que se instancia como un candado de hash, <rev-lock> = SHA256(<rev-secret>), donde <rev-secret> es el secreto de revocación.

El comerciante necesita el candado de revocación para disputar un cierre del cliente sobre un estado desactualizado.

#3 Apertura de un canal

Para abrir un canal, el cliente y el comerciante intercambian información de claves y establecen el identificador del canal <cid>.

Acuerdan sus saldos iniciales respectivos <cust-balance> y <merch-balance>.

El cliente elige un candado de revocación inicial <rev-lock>.

El cliente y el comerciante depositan en custodia los fondos necesarios en una transacción de financiación, denotada escrow-tx.

Como tal, la transacción de custodia presenta:

  • un estado del canal de apertura <state> = <cid>, <merch-pk>, <merch-ps-pk>, <cust-pk>, <merch-balance>, <cust-balance>, <rev-lock>;

  • potencialmente información adicional, como un retardo <delay>.

#4 Cierre de un canal

Un cliente debería poder cerrar el canal de forma unilateral publicando una transacción close-tx. Esta transacción presenta:

  • un estado del canal de cierre <state> = <cid>, <merch-pk>, <merch-ps-pk>, <cust-pk>, <cust-balance>, <merch-balance>, <rev-lock>;

  • una firma no ciega del comerciante sobre el estado del canal: <merch-sig>, tal que PS_sig.Verify(<merch-ps-pk>, <state>, <merch-sig>) = 1.

Si la transacción se valida y se mina, <merch-balance> se envía al comerciante y <cust-balance> queda bloqueado durante un retardo <delay>, en el cual el comerciante puede disputar el cierre del canal mediante una transacción dispute-tx, y después del cual el cliente puede reclamarlo mediante una transacción cust-claim-tx.

El comerciante puede disputar un cierre del cliente publicando una transacción dispute-tx. Esta transacción presenta:

  • un secreto de revocación <rev-secret> tal que para el candado de revocación <rev-lock> publicado en close-tx se cumple <rev-lock> = SHA256(<rev-secret>).

Si la transacción se valida y se mina, el saldo total (<cust-balance> + <merch-balance>) se envía al comerciante.

Un comerciante debería poder cerrar el canal de forma unilateral publicando una transacción de cierre expiry-tx.

Si la transacción se valida y se mina, el saldo total queda bloqueado durante un retardo <delay>, en el cual el cliente puede sobrescribir el gasto mediante una transacción close-tx, y después del cual el comerciante puede reclamarlo mediante una transacción merch-claim-tx.

El cliente y el comerciante también pueden negociar fuera de la cadena para formar una transacción de cierre mutuo, mutual-close-tx. Esta transacción presenta:

  • un estado del canal de cierre truncado <state> sin el candado de revocación ni la clave pública de firma ciega del comerciante;

  • dos firmas, una del cliente <cust-sig> y otra del comerciante <merch-sig>, sobre este estado truncado, tales que Verify(<cust-pk>, <state>, <cust-sig>) = 1 y Verify(<merch-ps-pk>, <state>, <merch-sig>) = 1.

Si la transacción se valida y se mina, el saldo <cust-balance> se envía al cliente y el saldo <merch-balance> se envía al comerciante.

tze_verify(mode, precondition, witness):

  • // Verificar la estructura de la transacción

  • if context.tx.tx_in_count != 0 OR context.tx.tze_in_count != 1 OR context.tx.nShieldedSpend !=0 OR context.tx.nShieldedOutput != 0 OR context.tx.nJoinsplit != 0:

    • Return False

  • msg = TODO // hash de la transacción sin testigos

  • if mode == 0: // modo de depósito en garantía

    • init-cid || init-merch-pk || init-merch-ps-pk || init-cust-pk = precondition

    • if context.tx.tze_out_count == 1:

      • if context.tx.tze_out[0].precondition.tze_mode == 1: // Esta es una transacción de cierre

        • // Verificar la estructura de la transacción

        • if context.tx.tx_out_count != 1:

          • Return False

        • merch-ps-sig || cust-sig = witness

        • cid || merch-pk || cust-pk || rev-lock = context.tx.tze_out[0].precondition.tze_data_payload

        • merch-balance = context.tx.tx_out[0].value

        • cust-balance = context.tx.tze_out[0].amount

        • state = cid || cust-pk || rev-lock || cust-balance || merch-balance

        • if init-cid != cid OR init-merch-pk != merch-pk OR init-cust-pk != cust-pk:

          • Return False

        • if Verify(cust-pk, msg, cust-sig) != 1 OR PS_sig.Verify(merch-ps-pk, state, merch-ps-sig) != 1:

          • Return False

        • if context.tx.tx_out[0] == merch-balance || <ZCash P2PKH version bytes (0x1C || 0xB8 for mainnet)> || Hash_160(merch-pk)

          • Return True

      • if context.tx.tze_out[0].precondition.tze_mode == 2: // Esta es una transacción de vencimiento

        • // Verificar la estructura de la transacción

        • if context.tx.tx_out_count != 0:

          • Return False

        • merch-sig = witness

        • cid || merch-pk || merch-ps-pk || cust-pk = context.tx.tze_out[0].precondition.tze_data_payload

        • if init-cid != cid OR init-merch-pk != merch-pk OR init-merch-ps-pk != merch-ps-pk OR init-cust-pk != cust-pk:

          • Return False

        • if Verify(merch-pk, msg, merch-sig) == 1:

          • Return True

    • if context.tx.tze_out_count == 0 AND if context.tx.tx_out_count == 2: // Esta es una transacción de cierre mutuo

      • merch-sig || cust-sig = witness

      • if Verify(init-merch-pk, msg, merch-sig) == 1 AND Verify(init-cust-pk, msg, cust-sig) == 1:

        • Return True

  • else if mode == 1: // modo de cierre

    • cid, merch-pk, cust-pk, rev-lock = precondition

    • sig, (rev-secret) = witness

    • if context.tx.tx_out.count == 1:

      • // Verificar la estructura de la transacción

      • if context.tx.tze_out_count != 0:

        • Return False

      • if Verify(cust-pk, msg, sig) == 1: // Esta es una transacción de reclamo del cliente

        • expiry-height = find_block_height(context.tx.tze_input[0].prevout_hash) // TODO

        • if context.block-height >= expiry-height + DELAY:

          • Return True

      • if Verify(merch-pk, msg, sig) == 1:// Esta es una transacción de disputa

        • if rev-lock == SHA256(rev-secret):

          • Return True

  • else if mode == 2: // modo de vencimiento

    • init-cid || init-merch-pk || init-merch-ps-pk || init-cust-pk = precondition

    • if context.tx.tze_out_count == 1: // Esta es una transacción de cierre

      • // Verificar la estructura de la transacción

      • if context.tx.tx_out_count != 1:

        • Return False

      • merch-ps-sig || cust-sig = witness

      • cid || merch-pk || cust-pk || rev-lock = context.tx.tze_out[0].precondition.tze_data_payload

      • merch-balance = context.tx.tx_out[0].value

      • cust-balance = context.tx.tze_out[0].amount

      • state = cid || cust-pk || rev-lock || cust-balance || merch-balance

      • if init-cid != cid OR init-merch-pk != merch-pk OR init-cust-pk != cust-pk:

        • Return False

      • if Verify(cust-pk, msg, cust-sig) != 1 OR PS_sig.Verify(merch-ps-pk, state, merch-ps-sig) != 1:

        • Return False

    • else if context.tx.tx_out_count == 1: // Esta es una transacción de reclamo del comerciante

#Maleabilidad de las transacciones

Como el id de la transacción no se construye a partir de los testigos TZE, cualquier cambio en la firma de la transacción no modifica su id.

Las precondiciones no son maleables porque están firmadas con una firma no maleable.

Para evitar la maleabilidad del testigo, pretendemos fijar el tamaño del contenido del testigo en tze_verify de modo que la adición o eliminación de cualquier bit resulte en una falla de verificación. Cualquier cambio en los bits debería resultar, ya sea en una falla de verificación, cuando el secreto de revocación o una firma están corruptos, o en una aprobación, cuando la firma PS está aleatorizada.
