#Terminología

Las palabras clave "DEBE (MUST)", "NO DEBE (MUST NOT)", "DEBERÍA (SHOULD)", "NO DEBERÍA (SHOULD NOT)", "RECOMENDADO (RECOMMENDED)" y "PUEDE (MAY)" en este documento deben interpretarse según lo descrito en BCP 14 [1] cuando, y solo cuando, aparezcan en mayúsculas.

Los términos siguientes deben interpretarse así:

Destinatario

Una billetera u otro software que puede recibir transferencias de activos (como ZEC) o, en el futuro, potencialmente otros cambios de estado basados en transacciones.

Productor

Una billetera u otro software que puede crear una dirección (en cuyo caso normalmente también es un Destinatario) o una clave de visualización.

Consumidor

Una billetera u otro software que puede hacer uso de una dirección o de una clave de visualización que se le haya proporcionado.

Emisor

Una billetera u otro software que puede enviar transferencias de activos, u otros efectos secundarios sobre el estado de consenso que puedan definirse en el futuro. Los Emisores son un subconjunto de los Consumidores.

Receptor

La información necesaria para transferir un activo a un Destinatario que generó ese Receptor mediante un protocolo de transferencia específico. Cada Receptor está asociado de forma inequívoca a un tipo de Receptor específico, identificado por un código de tipo entero.

Codificación de Receptor

Una codificación de un Receptor como secuencia de bytes.

Clave de visualización

La información necesaria para ver información sobre pagos a una dirección, o (en el caso de una clave de visualización completa) desde una dirección. Una clave de visualización entrante puede derivarse de una clave de visualización completa, y una dirección puede derivarse de una clave de visualización entrante.

Codificación de clave de visualización

Una codificación de una clave de visualización como secuencia de bytes.

Codificación de metadatos

Una codificación de metadatos que no es un Receptor ni una clave de visualización, pero que puede afectar la interpretación de la dirección unificada/clave de visualización unificada en su conjunto.

Ítem

Una Codificación de Receptor, una Codificación de clave de visualización o una Codificación de metadatos.

Dirección heredada

Una dirección transparente, Sprout o Sapling.

Dirección unificada (o UA)

Una dirección unificada combina múltiples Ítems de Receptor (y opcionalmente de Metadatos).

Clave de visualización completa unificada (o UFVK)

Una clave de visualización completa unificada combina múltiples Ítems de clave de visualización completa (y opcionalmente de Metadatos).

Clave de visualización entrante unificada (o UIVK)

Una Unified Incoming Viewing Key combina múltiples Ítems de Incoming Viewing Key (y opcionalmente de Metadatos).

Unified Viewing Key (o UVK)

Una Unified Full Viewing Key o una Unified Incoming Viewing Key.

Dirección

Una dirección heredada o una dirección unificada.

Protocolo de transferencia

Una especificación de cómo un Emisor puede transferir activos a un Destinatario. Por ejemplo, el Protocolo de transferencia para un Receptor Sapling es el subconjunto del protocolo de Zcash necesario para transferir ZEC con éxito mediante transferencias Spend/Output de Sapling, según lo especificado en la Zcash Protocol Specification (Especificación del Protocolo Zcash). (Una sola transacción de Zcash puede contener transferencias de múltiples Protocolos de transferencia. Por ejemplo, una transacción t→z que protege hacia el pool de Sapling requiere tanto los Protocolos de transferencia transparente como el de Sapling.)

Codificación de cadena unificada

Una codificación de una UA/UVK como cadena US-ASCII, destinada a la visualización y transferencia por parte de usuarios finales de Zcash, o al uso interno por parte de software relacionado con Zcash.

Codificación QR unificada

Una codificación de una UA/UVK como código QR, destinada a la visualización y transferencia por parte de usuarios finales de Zcash en situaciones donde las ventajas de usabilidad de un código de barras 2D pueden ser relevantes.

Codificación de dirección

La codificación externamente visible de una Dirección (por ejemplo, como una cadena de caracteres o un código QR).

Tiempo Unix Epoch

Un entero que representa una hora UTC en segundos relativa al Unix Epoch de 1970-01-01T00:00:00Z.

La notación para secuencias, conversiones y operaciones aritméticas sigue la especificación del protocolo de Zcash [3].

#Resumen

Esta propuesta define las direcciones unificadas, que agrupan direcciones de Zcash de distintos tipos de manera que puedan presentarse como una única Codificación de dirección. También define claves de visualización unificadas, que cumplen una función similar para las claves de visualización de Zcash.

#Motivación

Hasta la actualización de red Canopy incluida, Zcash admitía los siguientes tipos de dirección de pago:

  • Direcciones transparentes (P2PKH y P2SH)

  • Direcciones Sprout

  • Direcciones Sapling

Cada una de estas tiene sus propias Codificaciones de dirección, como cadena y como código QR. (Dado que el código QR se puede derivar de la codificación de cadena como se describe en [9], para muchos propósitos basta con considerar la codificación de cadena.)

La propuesta de Orchard [29] añade un nuevo tipo de Dirección, las direcciones Orchard.

La dificultad de definir nuevas Codificaciones de dirección para cada tipo de Dirección es que los usuarios finales se ven obligados a conocer los distintos tipos y, en particular, qué tipos admite un Consumidor o Destinatario dado. Para asegurarse de que las transferencias se completen con éxito, los usuarios pueden verse obligados a generar explícitamente Direcciones de distintos tipos y redistribuir codificaciones de ellas, lo que añade una fricción y una sobrecarga cognitiva significativas para comprender y usar Zcash.

Los objetivos de un estándar de dirección unificada son los siguientes:

  • Simplificar la coordinación entre Destinatarios y Consumidores eliminando la complejidad de la negociación de tipos de Dirección.

  • Proporcionar un “mecanismo de puente” que permita a las billeteras blindadas interactuar con éxito con billeteras conformes de solo transparente.

  • Permitir que las billeteras conformes más antiguas interactúen sin problemas con las billeteras más recientes.

  • Permitir que los usuarios de billeteras más recientes actualicen a tecnologías de transacción y/o grupos más nuevos, manteniendo interacciones sin problemas con contrapartes que usan billeteras más antiguas.

  • Facilitar que las billeteras asuman responsabilidades más sofisticadas de blindaje y/o migración de fondos del usuario.

  • Permitir que las billeteras desarrollen potencialmente nuevos mecanismos de transferencia sin cambios en el protocolo subyacente.

  • Admitir abstracciones correspondientes a una dirección unificada que proporcionen la funcionalidad de las claves de visualización completas y de las claves de visualización entrantes.

  • Proporcionar compatibilidad hacia adelante que sea estándar para todas las billeteras en una gama de posibles funciones futuras. Algunos ejemplos podrían ser funciones de capa 2, interoperabilidad y puentes entre cadenas, y exchange descentralizado.

  • Permitir que se incluyan ítems de metadatos en direcciones/claves de visualización unificadas para proporcionar extensibilidad futura.

  • El estándar debería funcionar bien para Zcash hoy y para las próximas posibles actualizaciones, y también anticipar casos de uso aún más amplios en el futuro, como la funcionalidad entre cadenas.

#Requisitos

#Descripción general

Las direcciones unificadas especifican múltiples métodos de pago a la billetera de un Destinatario. La billetera del Emisor puede entonces seleccionar el método de pago de forma no interactiva.

Es importante destacar que cualquier billetera puede admitir direcciones unificadas, incluso cuando esa billetera solo admite un subconjunto de métodos de pago para recibir y/o enviar.

A pesar de tener algunas características similares, el estándar de dirección unificada es ortogonal a los Payment Request URIs [32] y esquemas similares. Dado que las Payment Requests codifican las direcciones como cadenas alfanuméricas, no se requiere ningún cambio en el ZIP 321 para usar direcciones unificadas en Payment Requests.

#Conceptos

Las billeteras siguen un modelo de flujo de interacción como el siguiente:

  1. Un Productor genera una Dirección.

  2. El Productor codifica la Dirección.

  3. La billetera del Productor o el usuario humano distribuye esta Codificación de dirección. Este ZIP deja los mecanismos de distribución fuera del alcance.

  4. Una billetera o un usuario Consumidor importa la Codificación de dirección mediante cualquiera de una variedad de mecanismos (escaneo de código QR, Payment URIs, copiar y pegar, o protocolos “en banda” como los memos Reply-To).

  5. Una billetera Consumidora decodifica la Codificación de dirección y realiza verificaciones de validez.

  6. (Quizás más adelante en el tiempo) si la billetera Consumidora es un Emisor, puede ejecutar una transferencia de ZEC (u otros activos o cambios de estado del protocolo) a la Dirección.

Pueden distribuirse codificaciones de la misma Dirección cero o más veces por medios diferentes. Cero o más Consumidores pueden importar Direcciones. Cero o más de ellos (que son Emisores) pueden ejecutar una Transferencia. Un solo Emisor puede ejecutar múltiples Transferencias a lo largo del tiempo a partir de una sola importación.

Los pasos 1 a 5 inclusive también se aplican a los flujos de interacción para claves de visualización completas unificadas y claves de visualización entrantes unificadas.

#Direcciones

Una dirección unificada (o UA, por sus siglas en inglés) combina uno o más Receptores.

Cuando se introduzcan nuevos protocolos de transporte al protocolo de Zcash después de que las direcciones unificadas se estandaricen, estos deberían introducir nuevos tipos de Receptor, pero no tipos de Dirección diferentes fuera del estándar de UA. Debe haber una razón convincente para desviarse del estándar, ya que los beneficios de las UA provienen precisamente de su aplicabilidad a todas las nuevas actualizaciones del protocolo.

Para la Revisión 2, los usuarios deben poder distinguir visualmente las direcciones que presentan riesgo de que se filtre información en la cadena como resultado de una transferencia, de las direcciones que no presentan tales riesgos, con la excepción de los montos que cruzan de un pool a otro. Estos últimos se aceptan como fuga de información en el diseño de las UA, con el fin de lograr las propiedades de compatibilidad de billeteras deseadas.

#Receptores

Toda billetera debe parsear correctamente las codificaciones de una dirección unificada o una clave de visualización unificada que contengan Ítems no reconocidos.

Una billetera puede procesar los Ítems no reconocidos indicando al usuario su presencia o información similar con fines de usabilidad o de diagnóstico.

#Codificación de transporte

La Codificación de cadena unificada es “opaca” para los lectores humanos: no permite la identificación visual de qué Receptores o tipos de Receptor están presentes.

La Codificación de cadena unificada es resistente a errores de tipeo, de transcripción, de copiar y pegar, truncamientos u otros riesgos probables de UX.

Existe una Codificación QR unificada bien definida de una dirección unificada (o UFVK o UIVK) como código QR, que produce códigos QR razonablemente compactos y robustos.

Existe una transformación bien definida entre la Codificación QR unificada y la Codificación de cadena unificada de una UA/UVK dada, en cualquier dirección.

La Codificación de cadena unificada cabe en los URIs de pago de ZIP-321 [32] y en URIs generales sin introducir ambigüedades de análisis.

La codificación debe admitir suficientes tipos de Destinatario para permitir una expansión futura razonable.

La codificación debe permitir que todas las billeteras analicen de forma segura y correcta los tipos de Receptor no reconocidos lo suficientemente bien como para ignorarlos.

#Transferencias

Al ejecutar una Transferencia, el Emisor selecciona un Receptor mediante un proceso de Selección.

Dada una dirección unificada válida, la Selección debe tratar todo Ítem no reconocido como si estuviera ausente (con la excepción de que los Ítems con typecodes en el rango de comprensión obligatoria (MUST-understand) no pueden ignorarse; el Emisor debe rechazar las direcciones que contengan Ítems de comprensión obligatoria (MUST-understand) que no reconozca).

  • Esta propiedad es crucial para la compatibilidad con versiones futuras, a fin de asegurar que los usuarios que actualicen a protocolos / UAs más nuevos no pierdan la capacidad de interactuar sin problemas con billeteras más antiguas.

  • Esta propiedad es crucial para permitir que las billeteras que solo admiten protocolos blindados más antiguos interactúen con billeteras blindadas más nuevas, eliminando un desincentivo para adoptar billeteras blindadas más nuevas.

  • Esta propiedad también permite que las billeteras actualicen su admisión de protocolos blindados más nuevos sin volver a adquirir las UAs de las contrapartes. Si se vuelven a adquirir, el flujo de usuario y la usabilidad se verán mínimamente afectados.

#Uso experimental

Las direcciones unificadas y las Unified Viewing Keys deben poder incluir Receptores y Viewing Keys de tipos experimentales, posiblemente junto con otros no experimentales. Estos Receptores o Viewing Keys experimentales deben ser usados solo por billeteras cuyos usuarios hayan aceptado explícitamente participar en el experimento correspondiente.

#Claves de visualización

Una Unified Full Viewing Key (resp. Unified Incoming Viewing Key) puede usarse de manera similar a una Full Viewing Key (resp. Incoming Viewing Key), como se describe en la Zcash Protocol Specification [2].

Para una dirección P2PKH transparente derivada según BIP 32 [34] y BIP 44 [39], el equivalente más cercano a una clave de visualización completa o a una clave de visualización entrante para una cuenta BIP 44 dada es una clave pública extendida, como se define en la sección “Extended keys” de BIP 32. Por lo tanto, las UFVK y las UIVK deberían poder incluir tales claves públicas extendidas.

Una billetera debería admitir la derivación de una UIVK a partir de una UFVK, y de una dirección unificada a partir de una UIVK.

#Problemas abiertos y preocupaciones conocidas

Los impactos en la privacidad de las transacciones transparentes o entre pools, y los problemas de UX asociados, se abordarán en el ZIP 315 (en preparación).

#Revisiones

  • Revisión 0: la versión inicial de esta especificación.

  • Revisión 1 (retirada): la Revisión 1 propuso una variante de esta especificación similar a la especificada para las direcciones de la Revisión 2 con la Human-Readable Part tu. Enfrentó oposición de la comunidad debido a la dificultad de discernir las implicaciones de privacidad de compartir una dirección como la especificada, y ha sido retirada. Véase la especificación propuesta previamente para más detalles.

  • Revisión 2: Esta versión añade soporte para Typecodes de comprensión obligatoria (MUST-understand) y Metadatos de Expiración de Direcciones. Introduce dos nuevas variantes de direcciones unificadas; las direcciones zu, que tienen prohibido contener receptores transparentes, y las direcciones tu, que permiten que los receptores transparentes se aumenten con ítems de metadatos. Para las Unified Viewing Keys, esta versión adopta los prefijos de codificación uvf y uvi para las Unified Full Viewing Keys y las Unified Incoming Viewing Keys respectivamente, elimina la restricción de que una UVK debe contener al menos un Ítem blindado, y añade soporte para Ítems de Clave de Visualización P2SH mediante políticas de billetera BIP 388 [45].

Una UA/UVK de Revisión 0 se distingue de una UA/UVK de Revisión 2 por su Human-Readable Part, de la siguiente manera.

Sea addr_prefix:

  • “u”, si se trata de una UA o UVK anterior a la Revisión 2;

  • “zu”, si se trata de una UA solo blindada desde la Revisión 2 en adelante.

  • “tu”, si se trata de una UA con transparencia habilitada desde la Revisión 2 en adelante.

Las Human-Readable Parts (según se definen en [43]) de las direcciones unificadas se definen como:

  • addr_prefix, para las direcciones unificadas en Mainnet;

  • addr_prefix || “test”, para las direcciones unificadas en Testnet.

Sea ivk_prefix:

  • “uivk” antes de la Revisión 2;

  • “uvi” desde la Revisión 2 en adelante.

Sea fvk_prefix:

  • “uview” antes de la Revisión 2;

  • “uvf” desde la Revisión 2 en adelante.

Las Human-Readable Parts de las claves de visualización unificadas se definen como:

  • ivk_prefix para las claves de visualización entrantes unificadas en Mainnet;

  • ivk_prefix || “test” para las claves de visualización entrantes unificadas en Testnet;

  • fvk_prefix para las claves de visualización completas unificadas en Mainnet;

  • fvk_prefix || “test” para las claves de visualización completas unificadas en Testnet.

# Codificación de las direcciones unificadas

En lugar de definir una codificación de cadena Bech32 de las direcciones de pago blindadas de Orchard, definimos un formato de dirección unificada capaz de codificar un conjunto de Receivers de distintos tipos. Esto permite que el Consumidor de una dirección unificada elija el Receiver del mejor tipo que soporte, lo que ofrece una mejor experiencia de usuario a medida que se agreguen nuevos Receiver Types en el futuro.

Supóngase que se nos da un conjunto de una o más Receiver Encodings para tipos distintos. Es decir, el conjunto puede contener opcionalmente un Receiver de cada uno de los Receiver Types de la siguiente Lista de Prioridad fija:

  • Typecode 𝟶 𝚡 𝟶𝟹 — una Orchard raw address según se define en [11];

  • Typecode 𝟶 𝚡 𝟶𝟸 — una Sapling raw address según se define en [10];

  • Typecode 𝟶 𝚡 𝟶𝟷 — una dirección P2SH transparente, o Typecode 𝟶 𝚡 𝟶𝟶 — una dirección P2PKH transparente.

Si, y solo si, el usuario de una billetera Productora o Consumidora acepta explícitamente participar en un experimento según se describe en Uso experimental, la especificación del experimento PUEDE (MAY) incluir adiciones a la Lista de Prioridad anterior (dichas adiciones DEBERÍAN (SHOULD) mantener la intención de preferir protocolos blindados más recientes).

Decimos que un Receiver Type es “preferido” sobre otro cuando aparece antes en esta Lista de Prioridad (según lo modificado potencialmente por experimentos).

El Sender de un pago a una dirección unificada DEBE (MUST) usar el Receiver del Receiver Type más preferido que soporte dentro del conjunto.

Por ejemplo, considérese una billetera que soporta enviar fondos a Orchard Receivers y no soporta enviar a ningún Receiver Type que sea preferido sobre Orchard. Si a esa billetera se le da una UA que incluye un Orchard Receiver y posiblemente otros Receivers, DEBE (MUST) enviar al Orchard Receiver.

La codificación cruda de una dirección unificada es una concatenación de ( 𝚝 𝚢 𝚙 𝚎 𝚌 𝚘 𝚍 𝚎 , 𝚕 𝚎 𝚗 𝚐 𝚝 𝚑 , 𝚊 𝚍 𝚍 𝚛 ) codificaciones de los Receivers constituyentes, en orden ascendente de Typecode:

  • 𝚝 𝚢 𝚙 𝚎 𝚌 𝚘 𝚍 𝚎 ∶ 𝚌 𝚘 𝚖 𝚙 𝚊 𝚌 𝚝 𝚂 𝚒 𝚣 𝚎 — el Typecode de la Lista de Prioridad anterior;

  • 𝚕 𝚎 𝚗 𝚐 𝚝 𝚑 ∶ 𝚌 𝚘 𝚖 𝚙 𝚊 𝚌 𝚝 𝚂 𝚒 𝚣 𝚎 — la longitud en bytes de 𝚊 𝚍 𝚍 𝚛 ;

  • 𝚊 𝚍 𝚍 𝚛 ∶ 𝚋 𝚢 𝚝 𝚎 [ 𝚕 𝚎 𝚗 𝚐 𝚝 𝚑 ] — la Receiver Encoding.

Los valores de los campos 𝚝 𝚢 𝚙 𝚎 𝚌 𝚘 𝚍 𝚎 y 𝚕 𝚎 𝚗 𝚐 𝚝 𝚑 DEBEN (MUST) ser menores o iguales a 𝟶 𝚡 𝟸𝟶𝟶𝟶𝟶𝟶𝟶 . (La limitación sobre la longitud total de las codificaciones descrita más abajo impone un límite menor para 𝚕 𝚎 𝚗 𝚐 𝚝 𝚑 en la práctica.)

Una Receiver Encoding es la codificación cruda de una Shielded Payment Address, o el hash de script de $160$ bits de una dirección P2SH [47], o el hash de clave de validación de $160$ bits de una dirección P2PKH [46].

Sea padding la Human-Readable Part de la dirección unificada en US-ASCII, rellenada a 16 bytes con bytes cero. Añadimos padding a las codificaciones concatenadas y luego aplicamos el algoritmo 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 según se describe en Mezclado. (Para que se cumpla la limitación sobre el tamaño de entrada de 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 , la longitud total de las codificaciones DEBE (MUST) ser de a lo más ℓ M 𝖬 𝖠 𝖷 − 16 bytes, donde ℓ M 𝖬 𝖠 𝖷 se define en Mezclado.) La salida se codifica entonces con Bech32m [43], ignorando cualquier restricción de longitud. Se elige esto en lugar de Bech32 para manejar mejor las entradas de longitud variable.

Para decodificar una Unified Address Encoding, un Consumidor DEBE (MUST) usar el siguiente procedimiento:

  • Decodificar usando Bech32m, rechazando cualquier dirección con una suma de verificación incorrecta.

  • Aplicar 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 − 1 (esto también puede rechazar si la entrada no está en el rango correcto de longitudes).

  • Sea padding la Human-Readable Part, rellenada a 16 bytes como en la codificación. Si el resultado termina en padding, eliminar estos 16 bytes; de lo contrario, rechazar.

  • Analizar el resultado como una codificación cruda según se describió anteriormente, rechazando la dirección unificada completa si no se analiza correctamente.

La Human-Readable Part es la especificada para una dirección unificada en Revisiones.

Una billetera PUEDE (MAY) permitir a su usuario o usuarios configurar a qué Receiver Types puede enviar. NO DEBE (MUST NOT) permitir que el usuario o usuarios cambien el orden de la Lista de Prioridad usada para elegir el Receiver Type, excepto al aceptar participar en experimentos.

# Codificación de las Unified Full/Incoming Viewing Keys

Las Unified Full o Incoming Viewing Keys se codifican y decodifican de manera análoga a las direcciones unificadas. Un Consumidor DEBE (MUST) usar el procedimiento de decodificación de la sección anterior. Para las Viewing Keys, un Consumidor normalmente tomará la unión de la información proporcionada por todos los Receivers contenidos, y por lo tanto no se usa la Lista de Prioridad definida en la sección anterior.

Para cada FVK Type o IVK Type definido actualmente en esta especificación, se usa el mismo Typecode que para el Receiver Type correspondiente en una dirección unificada. PUEDEN (MAY) definirse FVK Types y IVK Types adicionales en el futuro, y estos no necesariamente usarán el mismo Typecode que la dirección unificada correspondiente.

Las siguientes FVK o IVK Encodings se usan en lugar del campo 𝚊 𝚍 𝚍 𝚛 :

  • Una Orchard FVK o IVK Encoding, con Typecode 𝟶 𝚡 𝟶𝟹 , es la codificación cruda de la Orchard Full Viewing Key o de la Orchard Incoming Viewing Key, respectivamente.

# Justificación de la eliminación de la restricción de "al menos un Item blindado" para las UVK

Hacer clic para mostrar/ocultar

La justificación original de esta restricción era que los formatos de dirección existentes solo transparentes P2SH y P2PKH, y el formato existente de clave pública extendida P2PKH, bastaban para representar claves de visualización con Items transparentes, y ya eran compatibles con el ecosistema existente.

Sin embargo, a partir de la Revision 2 existen usos para UVK solo transparentes que no están cubiertos por los formatos existentes. En particular, permiten representar claves de visualización para direcciones P2SH, lo cual es un caso de uso importante con la llegada del ZIP 48 [26]. Además, las claves de visualización solo transparentes pueden usar Metadata Items para representar alturas/fechas de expiración como se describe en Address Expiration Metadata, lo cual es útil en la generación de direcciones con prefijo tu.

# Justificación de la eliminación de los Receivers transparentes de las direcciones unificadas con zu

Hacer clic para mostrar/ocultar

Una queja común sobre las direcciones unificadas de la Revision 0 era que no había forma de que un usuario distinguiera visualmente una dirección unificada que permitía la recepción de fondos transparentes de una que no lo permitía; las direcciones transparentes no proporcionan ninguna protección de privacidad, e incluirlas en las UA creaba un riesgo de que los Remitentes recurrieran a transferencias transparentes incluso cuando el Destinatario admite protocolos blindados. Históricamente, el prefijo de dirección z indicaba al usuario que ningún elemento de la dirección del destinatario causaría que se filtrara información sobre el destinatario en la cadena mediante transferencias a esa dirección. La Revision 2 restaura esta propiedad.

Los Items transparentes siguen permitidos en las claves de visualización unificadas porque las claves de visualización sirven a un propósito distinto: permiten observar la actividad de transacciones en todos los pools, incluido el transparente. Una UFVK o UIVK que incluye un componente transparente permite al poseedor derivar direcciones transparentes con fines de escaneo y rastrear los fondos transparentes asociados con la misma cuenta.

# Justificación del orden de los Items

Hacer clic para mostrar/ocultar

La justificación de requerir que los Items estén canónicamente ordenados por Typecode es que permite a las implementaciones usar una representación en memoria que descarta el orden, mientras se retiene la misma serialización de ida y vuelta de una UA/UVK (siempre que se conserven los Items no reconocidos).

# Justificación de mostrar al menos los primeros 20 caracteres

Hacer clic para mostrar/ocultar

Mostrar menos de 20 caracteres de la codificación como cadena de una UA/UVK permitiría potencialmente ataques prácticos en los que el adversario construye otra UA/UVK que coincide en los caracteres mostrados. Cuando se abrevia una UA/UVK es preferible mostrar un prefijo en lugar de alguna otra parte, tanto para una experiencia de usuario más consistente entre billeteras, como porque el análisis de seguridad del costo de los ataques de coincidencia parcial de cadenas de UA/UVK es más complicado si se incluyen caracteres de suma de verificación en los caracteres que se comparan.

Para analizar la dificultad de los ataques de coincidencia parcial, debemos restar la longitud del HRP y del separador "1" de los 20 caracteres. El HRP más largo definido para una UA/UVK de Mainnet en esta especificación es "uview" para las UFVK de la Revision 0 — y así, en el peor de los casos, solo 14 caracteres, correspondientes a 70 bits, de los datos mezclados de la UA/UVK de Mainnet estarán presentes. (No nos preocupan particularmente los ataques a UA/UVK de Testnet). Esto implica un ataque de coincidencia parcial más fácil que el nivel de seguridad habitual de Zcash contra ataques clásicos de 2 125 . Nótese también que son posibles ataques de múltiples objetivos. Por lo tanto, 20 caracteres deberían considerarse un mínimo absoluto, y los implementadores de billeteras pueden desear mostrar un número mayor de caracteres iniciales para las UA/UVK abreviadas, a fin de permitir a los usuarios defenderse contra ataques de coincidencia parcial de una dificultad mayor para el adversario.

Nótese que si diferentes fuentes muestran diferentes subcadenas de una UA/UVK, los usuarios solo pueden comparar los caracteres comunes a todas estas subcadenas, por lo que solo los caracteres iniciales contribuyen a satisfacer este requisito.

#Justificación

La intención de esta especificación es que los Consumers de direcciones unificadas no deban enviar a direcciones expiradas. Si solo se especifica un Address Expiry Time, una transacción a la dirección asociada podría ser minada después del Address Expiry Time dentro de una ventana de 24 horas.

La razón por la que la transacción NO DEBE (MUST NOT) enviarse cuando su nExpiryHeight tal como se construye normalmente es mayor que la Address Expiry Height es evitar la filtración innecesaria de información en ese campo sobre qué dirección se utilizó como destino. Si un emisor usara en cambio la altura de expiración para fijar directamente el campo nExpiryHeight, esto filtraría la información de expiración de la dirección de destino, que entonces podría ser identificable.

Al respetar un Address Expiry Time, la razón por la cual un emisor DEBERÍA (SHOULD) elegir un nExpiryHeight que se espera que ocurra dentro de las 24 horas siguientes a la construcción de la transacción es garantizar, cuando sea posible, que el tiempo de expiración se respete con una precisión de un día. Los Address Expiry Times son informativos y no representan límites estrictos porque los relojes de las computadoras a menudo discrepan, pero debe hacerse todo lo posible por garantizar que las transacciones expiren en lugar de ser minadas más de 24 horas después del tiempo de expiración de la dirección del destinatario. Cuando el Sender dispone de información de la altura de la cadena, es tanto permisible como aconsejable establecer este límite de forma más estricta; un delta de expiración común usado por muchas billeteras es de 40 bloques desde la punta actual de la cadena, como se sugiere en el ZIP 203 [27].

# Justificación de los metadatos de Viewing Key Birthday Height

Hacer clic para mostrar/ocultar

Una billetera que importa una viewing key sin un birthday height debe pedirle uno al usuario o escanear desde un valor predeterminado conservador, como la altura de activación del protocolo blindado más antiguo que la viewing key admita. Escanear desde tal valor predeterminado puede tardar mucho más que escanear desde el birthday height real. Incluir el birthday height en la viewing key elimina este costo y la necesidad de un canal separado para transmitirlo. Un Producer también puede establecer un Birthday Height posterior cuando el historial anterior de la viewing key no es relevante para su uso previsto.

La altura de cumpleaños recibe un Typecode fuera del rango de comprensión obligatoria (MUST-understand) porque un Consumidor que la ignore sigue siendo correcto: escanea desde una altura anterior, lo que cuesta tiempo pero no puede hacer que pierda fondos. Un Typecode de comprensión obligatoria (MUST-understand), en cambio, exigiría que todo Consumidor existente rechace una clave de visualización de otro modo utilizable, y prohibiría su uso en claves de visualización de la Revisión 0.

El birthday height describe una viewing key, no un destino de pago. Un Sender no le da uso, e incluirlo en una dirección unificada revelaría la edad aproximada de la billetera del destinatario a toda parte que vea la dirección. Por ello se prohíbe en las direcciones unificadas. Un Consumer ignora dicho Item en lugar de rechazar la dirección, porque el Item no afecta cómo un Sender usa los Receivers de la dirección, y rechazar la dirección no desharía la filtración de información. Quien posee una viewing key ya puede observar las alturas de las transacciones que la key detecta, de modo que incluir el birthday height en la viewing key revela poca información adicional a tal poseedor.

Cada dirección derivada de una viewing key con expiración expira en o antes del Address Expiry Height de la viewing key, de modo que un Sender conforme no enviará fondos a ella en un bloque por encima de esa altura. Un Birthday Height mayor que el Address Expiry Height dirigiría al Consumer a comenzar el escaneo después de todas esas transacciones. Dicha viewing key es inconsistente y se trata como inválida.

#Justificación de los metadatos de derivación de claves

Hacer clic para mostrar/ocultar

Sin estos Elementos, una billetera que importa una UFVK tiene que obtener la huella de la semilla y el índice de cuenta por separado, por ejemplo mediante un formato de exportación específico del proveedor, o preguntando al firmante cada vez que se firma una transacción.

Los Elementos no son de comprensión obligatoria (non-MUST-understand) porque ni cambian la interpretación de la UFVK ni otorgan autoridad de visualización adicional: un Consumidor que los ignore pierde únicamente la capacidad de construir solicitudes de firma sin ayuda del firmante. Por la misma razón se permiten en UFVKs de la Revisión 0, que un Productor puede extender sin cambiar la parte legible por humanos; los Consumidores de la Revisión 0 tienen la obligación de ignorar los Elementos con códigos de tipo que no reconozcan.

La huella de la semilla y las rutas de derivación son Elementos separados porque una sola huella de semilla aplica a cada Elemento FVK, mientras que cada Elemento FVK tiene su propia ruta. Las rutas se indican completas, y no como un único índice de cuenta, porque los árboles blindado y transparente usan niveles de propósito diferentes, y porque algunas derivaciones (como la derivación Sapling heredada zcashd bajo la cuenta 𝟶 𝚡 𝟽 𝙵 𝙵 𝙵 𝙵 𝙵 𝙵 𝙵 [24]) no siguen la convención a nivel de cuenta. La codificación de la ruta es la que usan los orígenes de claves de BIP 174 [42].

Los Elementos se excluyen de las UIVKs y de las direcciones unificadas porque el poseedor de una IVK o de una dirección no puede construir un gasto, y porque reducirían la privacidad. La huella de la semilla es la misma para cada cuenta derivada de una semilla, de modo que cualesquiera dos UFVKs que la contengan pueden vincularse a la misma semilla; la ruta de derivación revela el índice de cuenta. Una UFVK ya otorga plena autoridad de visualización sobre su cuenta, pero este vínculo entre cuentas es información adicional, razón por la cual se aconseja a los Productores incluir los Elementos solo cuando sean necesarios.

Los Elementos FVK P2SH no están cubiertos, porque cada clave de una política de multifirma puede derivarse de una semilla diferente. Los orígenes de tales claves necesitarían una codificación por clave, que puede definirse en una revisión futura.

  • Para una FVK de Orchard, el IVK de Orchard correspondiente se obtiene como se especifica en [5].

  • Para una FVK P2SH (a partir de la Revision 2), el IVK P2SH correspondiente se obtiene:

#Derivación de una dirección unificada a partir de una UIVK

Como consecuencia de la especificación en Typecodes de comprensión obligatoria (MUST-understand), a partir de la Revisión 2 un Consumidor de una UIVK DEBE (MUST) comprender el significado de todos los Typecodes de Ítems de Metadatos "de comprensión obligatoria (MUST-understand)" presentes en la UIVK para poder derivar de ella una dirección unificada.

Si la UIVK de origen es de la Revisión 2, entonces la dirección unificada derivada DEBERÍA (SHOULD) ser de Revisión 2; si la UIVK de origen incluye algún Ítem de Metadatos de comprensión obligatoria (MUST-understand), entonces la dirección unificada derivada DEBE (MUST) ser de Revisión 2.

Para los Metadata Items reconocidos por el Consumidor, el procesamiento del Item al derivar una dirección unificada se especifica en la sección o el ZIP que describe ese Item.

Para derivar una dirección unificada a partir de una UIVK es necesario elegir un índice diversificador, que DEBE (MUST) ser válido para todos los tipos de clave de visualización (Viewing Key Types) en la UIVK. Es decir,

  • Un índice diversificador de Sapling DEBE (MUST) generar un diversificador válido como se define en la sección “Sapling diversifier derivation” del ZIP 32 [18].

  • Un índice diversificador transparente DEBE (MUST) estar en el rango de 0 a 2 31 − 1 inclusive.

  • No hay restricciones adicionales sobre un índice diversificador de Orchard.

Nota: Un índice diversificador igual a 0 puede no generar un diversificador de Sapling válido (con probabilidad 1 / 2 ). Algunas billeteras (ya sea antes del despliegue del ZIP 316, en violación del requisito anterior, o porque no incluyen un componente de Sapling en sus direcciones unificadas) siempre generan una dirección transparente P2PKH en el índice diversificador 0. Por lo tanto, todas las billeteras de Zcash, con o sin soporte de direcciones unificadas, DEBEN (MUST) asumir que puede haber fondos transparentes asociados con el índice diversificador 0 para cada cuenta del ZIP 32, incluso en los casos en que la implementación de la billetera no generaría una dirección unificada con ese índice para una cuenta dada. Esto es necesario para garantizar una recuperación confiable de los fondos si el material de claves se importa entre billeteras.

Las siguientes derivaciones se aplican a cada IVK de componente usando el índice diversificador:

  • Para una IVK de Sapling, el receptor de Sapling correspondiente se obtiene como se especifica en [4].

  • Para una IVK de Orchard, el receptor de Orchard correspondiente se obtiene como se especifica en [5].

  • Para una IVK transparente P2PKH, el índice diversificador se usa como índice de clave hija de BIP 44 en el nivel de índice [41] para derivar el receptor transparente P2PKH correspondiente. Como es habitual para las derivaciones por debajo del nivel de cuenta de BIP 44, DEBE (MUST) usarse la derivación no endurecida (pública) [38]. Se asume que la IVK corresponde a la clave pública extendida del elemento externo (no de cambio) de la ruta. Es decir, si la UIVK se construyó correctamente, la ruta BIP 44 del receptor transparente P2PKH será m / 44' / \mathit{coin\_type\kern0.05em'} / \mathit{account\kern0.1em'} / 0 / \mathit{diversifier\_index}.

  • A partir de Revision 2, para una IVK transparente P2SH, el receptor P2SH correspondiente se obtiene:

    1. Para cada clave en el vector de información de claves, derivando la clave hija en el índice diversificador usando la derivación pública no endurecida de BIP 32 [38].

    2. Instanciando la plantilla de descriptor sustituyendo cada marcador de posición @N por la clave pública derivada correspondiente, evaluando el descriptor de salida resultante [44] para obtener el script de salida, y calculando el HASH160 del script serializado para producir la codificación del receptor P2SH.

Los Ítems (incluidos los Ítems de Metadatos que no son "de comprensión obligatoria (MUST-understand)") que un Consumidor dado no reconozca, o que estén especificados en experimentos a los que el usuario no haya dado su consentimiento (véase Experimental Usage), DEBEN (MUST) descartarse cuando el Consumidor derive una dirección unificada de una UIVK.

Véase Address Expiration Metadata para la discusión del posible enlace de direcciones unificadas diversificadas a través de sus metadatos.

#Uso de las claves de visualización de saliente

Cuando un Emisor construye una transacción que crea notas de Sapling u Orchard, usa una clave de visualización de saliente, como se describe en [6] y [7], para cifrar un criptograma de saliente. El descifrado con la clave de visualización de saliente permite recuperar el texto en claro de la nota enviada, incluidos la dirección de destino, el monto y el memo. La intención es que esta clave de visualización de saliente esté asociada con el origen de los fondos.

Sin embargo, la especificación de qué clave de visualización de saliente debe usarse queda algo abierta en [6] y [7]; en particular, no estaba claro si las transferencias debían considerarse como enviadas desde una dirección, o desde una cuenta del ZIP 32 [23]. La adopción de múltiples protocolos blindados que soportan claves de visualización de saliente (es decir, Sapling y Orchard) complica aún más esta cuestión, ya que desde la activación de NU5, nada a nivel de consenso impide que una billetera gaste tanto notas de Sapling como de Orchard en la misma transacción. (Se darán recomendaciones sobre el uso de múltiples pools por parte de las billeteras en el ZIP 315 [31].)

Aquí refinamos la especificación del protocolo a fin de permitir una determinación más precisa de la autoridad de visualización para las UFVK.

Un Emisor intentará determinar una "cuenta de envío" para cada transferencia. El enfoque preferido es que la API usada para realizar una transferencia especifique directamente una cuenta de envío. De lo contrario, si el Emisor puede constatar que todos los fondos usados en la transferencia provienen de direcciones asociadas con alguna cuenta, entonces DEBERÍA (SHOULD) tratar esa como la cuenta de envío. Si no, la cuenta de envío queda indeterminada.

El Emisor también determina un "protocolo de envío preferido" —uno de "transparente", "Sapling" u "Orchard"— correspondiente al tipo de receptor más preferido (según se indica en Codificación de direcciones unificadas) de cualquier fondo enviado en la transacción.

Si la cuenta de envío ha sido determinada, entonces el Emisor DEBERÍA (SHOULD) usar la 𝗈 𝗏 𝗄 externa o interna (según el tipo de transferencia), según lo especificado por el protocolo de envío preferido, de la clave de visualización completa para esa cuenta (es decir, a nivel de cuenta del ZIP 32).

Si la cuenta de envío está indeterminada, entonces el Emisor DEBERÍA (SHOULD) elegir una de las direcciones, restringido a direcciones para el protocolo de envío preferido, desde las cuales se envían fondos (por ejemplo, la primera para ese protocolo), y luego usar la 𝗈 𝗏 𝗄 externa o interna (según el tipo de transferencia) de la clave de visualización completa para esa dirección.

#Mezclado (jumbling)

Objetivo de seguridad (resistencia casi de segunda preimagen):

  • Se le da a un adversario q direcciones/claves de visualización unificadas, generadas honestamente.

  • El objetivo del ataque es producir una dirección/clave de visualización unificada válida "parcialmente en colisión" que:

    1. tenga una codificación textual que coincida con la de una de las direcciones/claves de visualización de entrada en algún subconjunto de caracteres (para ser concretos, considérense los primeros n y los últimos m caracteres, hasta cierto límite en n + m );

    2. esté controlada por el adversario (para ser concretos, el adversario conoce al menos una de las claves privadas de las direcciones constituyentes).

Objetivo de seguridad (no maleabilidad):

  • En esta variante, el punto b) anterior se reemplaza por la condición de que el significado de la nueva dirección/clave de visualización sea "útilmente" diferente del de aquella en la que se basa, aunque el adversario no conozca ninguna de las claves privadas. Por ejemplo, si fuera posible eliminar una dirección constituyente blindada de una UA dejando solo una dirección transparente, eso sería un ataque de maleabilidad significativo.

#Discusión

Existe un ataque genérico de fuerza bruta contra la resistencia casi de segunda preimagen. El adversario genera UAs / UVKs al azar con claves conocidas, hasta que una tenga una codificación que colisione parcialmente con uno de los q objetivos. Podría ser posible mejorar este ataque aprovechando propiedades de las sumas de verificación, etc.

El ataque genérico impone un límite superior a la seguridad alcanzable: si producir y verificar una UA/UVK toma un trabajo w , y el tamaño del conjunto de caracteres es c , entonces el ataque genérico cuesta ∼ w ⋅ c n + m q .

También existe un ataque genérico de fuerza bruta contra la no maleabilidad. El adversario modifica ligeramente la UA/UVK objetivo y calcula la decodificación correspondiente, luego repite hasta que la decodificación sea válida y además útil para el adversario (p. ej., que llevara al Emisor a usar una dirección transparente). Con w definido como arriba, el costo es w / p , donde p es la probabilidad de que una decodificación aleatoria tenga la forma requerida.

#Solución

Usamos una construcción Feistel de 4 rondas sin clave para aproximar una permutación aleatoria. (Como se explica más abajo, 3 rondas no serían suficientes.)

Sea H i un hash personalizado por i , con longitud máxima de salida de ℓ H bytes. Sea G i una XOF (una función de hash con longitud de salida extensible) basada en H , personalizada por i .

Defínase ℓ M 𝖬 𝖠 𝖷 = ( 2 16 + 1 ) ⋅ ℓ H . Para la instanciación usando BLAKE2b definida más abajo, ℓ M 𝖬 𝖠 𝖷 = 4194368 .

Dada una entrada M de longitud ℓ M bytes tal que 38 ≤ ℓ M ≤ ℓ M 𝖬 𝖠 𝖷 , defínase 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 ( M ) mediante:

  • sea ℓ L = 𝗆 𝗂 𝗇 ( ℓ H , 𝖿 𝗅 𝗈 𝗈 𝗋 ( ℓ M / 2 ) )

  • sea ℓ R = ℓ M − ℓ L

  • dividir M en a de longitud ℓ L bytes y b de longitud ℓ R bytes

  • sea x = b ⊕ G 0 ( a )

  • sea y = a ⊕ H 0 ( x )

  • sea d = x ⊕ G 1 ( y )

  • sea c = y ⊕ H 1 ( d )

  • devolver c | | d .

La función inversa 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 − 1 se obtiene de la forma habitual para una construcción Feistel, observando que r = p ⊕ q implica p = r ⊕ q .

El primer argumento de BLAKE2b más abajo es la personalización.

Instanciamos H i ( u ) por \mathsf{BLAKE2b‐}(8\ell_L)(\texttt{“UA\_F4Jumble\_H”} \,||\, $[i, 0, 0], u),$ con ℓ H = 64 .

Instanciamos G i ( u ) como los primeros ℓ R bytes de la concatenación de [\mathsf{BLAKE2b‐}512(\texttt{“UA\_F4Jumble\_G”} \,||\, [i] \,||\, \mathsf{I2LEOSP}_{16}(j), u) \textsf{ for } j \textsf{ from} 0 \textsf{ up to } \mathsf{ceiling}(\ell_R/\ell_H)-1].

(En la práctica, las longitudes ℓ L y ℓ R serán aproximadamente iguales hasta que ℓ M sea mayor que $128$ bytes.)

#Uso para direcciones unificadas, UFVK y UIVK

Para prevenir el ataque genérico contra la no maleabilidad, es necesario que haya cierta redundancia en la codificación. Por lo tanto, el Productor de una dirección unificada, UFVK o UIVK añade el HRP, rellenado a 16 bytes con bytes cero, a la codificación en bruto, luego aplica 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 antes de codificar el resultado con Bech32m.

El Consumidor rechaza cualquier secuencia de bytes decodificada de Bech32m que tenga menos de 38 bytes o más de ℓ M 𝖬 𝖠 𝖷 bytes; de lo contrario aplica 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 − 1 . Rechaza cualquier resultado que no termine en el relleno esperado de 16 bytes, antes de eliminar esos 16 bytes y analizar el resultado.

#Justificación de las restricciones de longitud

Hacer clic para mostrar/ocultar

Una longitud mínima de entrada a 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 − 1 de 38 bytes permite que el tamaño mínimo de la codificación de un ítem de UA/UVK sea de 22 bytes, incluyendo el código de tipo y la longitud, teniendo en cuenta 16 bytes de relleno. Esto permite una UA que contenga solo un receptor P2PKH transparente:

  • Ítem de receptor P2PKH transparente:

    • código de tipo de 1 byte

    • codificación de longitud de 1 byte

    • hash de dirección transparente de 20 bytes

ℓ M 𝖬 𝖠 𝖷 bytes es el tamaño máximo de entrada/salida soportado por 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 .

Permitir solo un receptor P2PKH transparente es consistente con la eliminación del requisito de tener al menos un ítem blindado en las UA/UVK de la revisión 2 (ver la justificación).

Nótese que la revisión 0 de este ZIP especificaba una longitud mínima de entrada a 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 − 1 de 48 bytes. Dado que no existían conjuntos de codificaciones de ítems de UA/UVK válidos en la revisión 0 a los cuales pudiera analizarse una secuencia de bytes (tras eliminar el relleno de 16 bytes) de longitud entre 22 y 31 bytes inclusive, la diferencia entre las restricciones de 38 y 48 bytes no es observable, salvo por el hecho de poder afectar qué error se reporta. Un consumidor que soporte la revisión 2 de esta especificación PUEDE (MAY) por lo tanto aplicar tanto el mínimo de 48 bytes como el de 38 bytes a las UA/UVK de la revisión 0.

#Análisis heurístico

Una Feistel de 3 rondas sin clave, como se muestra, no es suficiente:

Supóngase que un adversario tiene un par de entrada/salida objetivo ( a | | b , c | | d ) , y que la entrada a H 0 es x . Al fijar x , se puede obtener otro par ( ( a ⊕ t ) | | b ' , ( c ⊕ t ) | | d ' ) tal que a ⊕ t está cerca de a y c ⊕ t está cerca de c . ( b ' y $d'$ no estarán cerca de b y d , pero eso no es necesariamente requerido para un ataque válido).

Una Feistel de 4 rondas frustra este ataque y otros similares. Definiendo x y y como los valores intermedios del primer diagrama anterior:

  • si $(x', y')$ se fijan a los mismos valores que $(x, y)$, entonces $(a', b', c', d') = (a, b, c, d)$;

  • si $x' = x$ pero y ' ≠ y , entonces el adversario puede introducir una diferencia controlada ⊕ en a ⊕ a ' = y ⊕ y ' , pero las otras tres piezas $(b, c, d)$ se aleatorizan por completo, lo cual es suficiente;

  • si $y' = y$ pero x ' ≠ x , entonces el adversario puede introducir una diferencia controlada ⊕ en d ⊕ d ' = x ⊕ x ' , pero las otras tres piezas $(a, b, c)$ se aleatorizan por completo, lo cual es suficiente;

  • si x ' ≠ x y y ' ≠ y , las cuatro piezas se aleatorizan por completo.

Nótese que el tamaño de cada pieza es de al menos 19 bytes.

Sería posible hacer un ataque más costoso haciendo más costoso el trabajo realizado por un productor. (Esto no tendría necesariamente que incrementar el trabajo realizado por el consumidor). Sin embargo, dado que las direcciones unificadas podrían necesitar producirse en plataformas de computación restringidas, esto no se consideró beneficioso en general.

El relleno contiene el HRP para que el HRP tenga la misma protección contra maleabilidad que el resto de la dirección. Esto puede ayudar contra ataques entre redes, o ataques que confundan direcciones con claves de visualización.

#Eficiencia

El costo está dominado por 4 compresiones BLAKE2b para ℓ M ≤ 128 bytes. Una UA de revisión 0 que contenga una dirección transparente, una dirección Sapling y una dirección Orchard, tendría ℓ M = 128 bytes. Una UA que contenga una dirección Sapling y una dirección Orchard tendría ℓ M = 106 bytes.

Para UA más largas (cuando se agreguen otros tipos de receptor) o UVK, el costo aumenta a 6 compresiones BLAKE2b para 128 < ℓ M ≤ 192 , y 10 compresiones BLAKE2b para 192 < ℓ M ≤ 256 , por ejemplo. El costo máximo para el cual el algoritmo está definido sería de 196608 compresiones BLAKE2b a ℓ M = ℓ M 𝖬 𝖠 𝖷 bytes.

Una implementación ingenua de la función 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 − 1 requeriría aproximadamente ℓ M bytes más el tamaño de un estado de hash BLAKE2b. Sin embargo, es posible reducir esto transmitiendo en flujo la parte d de la codificación revuelta tres veces desde un dispositivo con menos restricciones de memoria. Es esencial que el valor transmitido en flujo de d sea el mismo en cada pasada, lo cual puede verificarse mediante un código de autenticación de mensajes (con la clave retenida únicamente por el consumidor) o una función hash resistente a colisiones. Después de la primera pasada de d , la implementación puede calcular y ; después de la segunda pasada puede calcular a ; y la tercera le permite calcular y analizar incrementalmente b . El uso máximo de memoria durante este proceso sería de 128 bytes más dos estados de hash BLAKE2b.

Dado que esta implementación en flujo de 𝖥 𝟦 𝖩 𝗎 𝗆 𝖻 𝗅 𝖾 − 1 es bastante complicada, no requerimos que todos los consumidores soporten transmisión en flujo. Si una implementación de consumidor no puede soportar UA / UVK de hasta la longitud máxima, DEBE (MUST) no obstante soportar UA / UVK con ℓ M de al menos $256$ bytes. Nótese que esto efectivamente define dos niveles de conformidad con esta especificación. Una implementación completa soportará UA / UVK de hasta la longitud máxima.
