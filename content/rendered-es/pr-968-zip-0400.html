#Resumen

Esta propuesta define el formato actual utilizado en zcashd para el almacenamiento persistente de la billetera, conocido comúnmente como wallet.dat.

#Motivación

El proceso de guardar los datos de la billetera en el disco actualmente no está especificado. Las claves-valores utilizados en la implementación actual no están documentados, y su estructura y funcionalidad son desconocidas sin un análisis profundo del código fuente involucrado. Este documento detalla el esquema y la mecánica de la base de datos de la billetera. Este es un documento informativo; no se harán cambios al código fuente.

#Especificación

Zcash almacena la información de la billetera en una base de datos Berkeley (BDB) [1] conocida comúnmente como wallet.dat. El propósito principal de esta es la persistencia de las claves públicas y privadas que el usuario creó y la capacidad de recuperar el estado de la billetera después de un reinicio del nodo. Este archivo también permite la migración de la información del usuario de un nodo a otro moviendo la base de datos al nuevo directorio de datos correspondiente, asumiendo que ambas instancias de zcashd ejecutan la misma versión o una similar. Puede ser necesaria una reindexación después de esta operación.

La base de datos actual es un almacén de claves y valores donde las claves y los valores pueden tener múltiples tipos de datos en formato binario. El primer dato que se encuentra en una clave de la base de datos es siempre el nombre de la propiedad; el resto de la clave generalmente se usa para identificar un registro, por ejemplo:

<------ KEY ----+- VALUE ->
---------------------------
| zkey | pubkey | privkey |
---------------------------

Aquí zkey es el nombre de la propiedad ubicado en la primera posición de la clave de la base de datos; la clave pública también forma parte de la clave de la base de datos y está ubicada en la segunda posición; la clave privada se guarda en la columna de valores de la base de datos, en la primera posición.

#Esquema

Se pueden encontrar las siguientes claves-valores: los nombres de propiedades en negrita significan que solo puede existir una instancia de este tipo en toda la base de datos, mientras que las otras, con el sufijo '*', pueden tener múltiples instancias. Las columnas de claves y valores de la tabla contienen los tipos que representan los datos almacenados. La columna Version indica la versión o versiones de zcashd que crean bases de datos que contienen esta clave. También se incluyen allí los nombres de las variables, con la esperanza de que esto añada algo de claridad sobre lo que representan los datos almacenados.

#Funcionalidad

Cuando se inicia por primera vez un nodo zcashd compilado con soporte de billetera, se crea una nueva base de datos de billetera. De forma predeterminada, el nodo ejecutará automáticamente acciones de billetera que se guardarán en la base de datos en el primer momento de vaciado.

El siguiente flujo ocurrirá cuando se inicia por primera vez un nodo con soporte de billetera:

  • Se agregarán al pool DEFAULT_KEYPOOL_SIZE (100 de forma predeterminada) claves, creando 100 registros con pool como nombre de propiedad (primer valor de la clave de la base de datos).

  • También se agregarán 100 propiedades key.

  • 100 keymeta.

  • La billetera creará una clave transparente predeterminada para recibir; esta también se agregará como propiedades key, pool y keymeta.

  • Esta clave predeterminada también se agrega como una propiedad defaultkey.

  • La última acción creó una entrada en la libreta de direcciones que se refleja en la base de datos mediante las propiedades name y purpose.

  • Si la billetera se crea con soporte HD, tendrá propiedades adicionales hdseed y hdchain que se guardarán.

  • Se agregan las propiedades version, minversion, witnesscachesize y bestblock. Estas son configuraciones e información de estado: la propiedad bestblock es un buen ejemplo del llenado de la base de datos que ocurre sin ninguna interacción del usuario, pero simplemente se actualizará a medida que cambie el mejor bloque de la cadena actual.

En cualquier momento después de crearse la base de datos, se pueden agregar nuevas propiedades a medida que los usuarios de la billetera realizan acciones. Por ejemplo, si el usuario crea una nueva dirección de Sapling con el comando RPC z_getnewaddress, entonces se agregarán a la base de datos nuevos registros con las propiedades sapzkey y sapzkeymeta.

En zcashd, los cambios en la base de datos no ocurren inmediatamente, sino que se vacían en su propio hilo mediante la función ThreadFlushWalletDB() periódicamente para evitar sobrecarga. El contador interno nWalletDBUpdated se incrementa cada vez que se realiza una nueva operación de escritura en la base de datos; este se compara con el último vaciado para confirmar los elementos nuevos.

Cuando el nodo se detiene por cualquier motivo, la información en la base de datos de la billetera DEBERÍA (SHOULD) persistir en el disco; la próxima vez que el nodo se inicie, el software detectará el archivo de la base de datos, leerá de allí y agregará los valores a estructuras en memoria que garantizarán la funcionalidad de la billetera.

#Transacciones

La base de datos de la billetera no guardará todas las transacciones que ocurren en la blockchain; sin embargo, guardará todas las transacciones en las que estén involucradas claves de la billetera. Esto es necesario, por ejemplo, para obtener saldos. Por lo tanto, la billetera debe tener todas las transacciones relacionadas con una clave para computar el valor final de las monedas disponibles en la dirección derivada.

La propiedad tx contendrá los datos relacionados con las transacciones, con el hash de la transacción como clave y la transacción completa como valor.

#Estado de la billetera y reordenamiento de transacciones

Las transacciones se guardan en la clave tx de la base de datos a medida que llegan; esto significa que las transacciones tienen una secuencia. El conjunto de todas las transacciones desde el inicio hasta un momento dado es el estado de la billetera en ese instante. El estado de la billetera es importante, entre otras cosas, para obtener el saldo actual de una billetera o dirección.

En la blockchain, las transacciones pueden invalidarse por reversiones; el código de la billetera manejará esto actualizando las transacciones en la base de datos en memoria. El nuevo estado debe reflejarse en la base de datos en disco; esto se hace en zcashd mediante el indicador fAnyUnordered, donde si es verdadero al momento del inicio, lanzará un reescaneo sobre todas las transacciones nuevamente.

#Recuperación de la billetera

El archivo de la base de datos de la billetera puede corromperse. Hay utilidades en el directorio zcutil/bin que pueden ayudar a recuperarlo si esto ocurre. Solicite ayuda en el foro de Zcash o en el Discord de la comunidad.

#Cifrado de la billetera

El cifrado no se tratará en detalle en este documento, ya que se espera que el algoritmo cambie en el futuro según el issue del ZIP sobre el formato de la billetera: [2].

Para una comprensión más profunda del mecanismo de cifrado actual, consulte [4].
