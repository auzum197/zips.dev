#Terminología

Las palabras clave "DEBE (MUST)", "DEBERÍA (SHOULD)" y "PUEDE (MAY)" en este documento deben interpretarse como se describe en BCP 14 [1] cuando, y solo cuando, aparecen en mayúsculas.

Los términos siguientes deben interpretarse de la siguiente manera:

Cliente ligero

Un cliente que no es un participante pleno en la red de pares de Zcash. Puede enviar y recibir pagos, pero no almacena ni valida una copia del block chain.

#Resumen

Esta propuesta define un protocolo para un cliente ligero de Zcash con soporte para transacciones blindadas de Sapling.

#Motivación

Actualmente, un cliente que desea enviar o recibir pagos blindados debe ser un nodo completo que participe en la red de Zcash. Esto requiere una cantidad de ancho de banda, espacio y capacidad de procesamiento disponibles que puede no ser adecuada para algunas clases de usuarios. Este protocolo de cliente ligero aborda esa necesidad y es apropiado para máquinas de baja potencia, conscientes del ancho de banda o limitadas de otra manera (como los teléfonos móviles).

#Diseño de alto nivel

Un sistema de cliente ligero de Zcash tiene tres componentes lógicos:

  • Nodo de Zcash que proporciona el estado de la cadena y sirve como raíz de confianza para el sistema.

  • Servidor proxy que extrae datos del block chain de zcashd para almacenarlos y servirlos en un formato de menor ancho de banda.

  • Cliente ligero que se suscribe al flujo de un servidor proxy y usa esos datos para actualizar su propia vista del estado de la cadena. El cliente ligero PUEDE (MAY) estar acoplado a un backend de billetera que rastreará notas particulares de Sapling.

#Modelo de seguridad

En este modelo, proponemos la privacidad de detección de pagos como nuestro principal objetivo de seguridad. Es decir, el proxy no debería conocer cuáles transacciones (recibidas del block chain) están dirigidas a una billetera ligera dada. Si además asumimos privacidad de red (mediante Tor o similar), el proxy no debería poder vincular distintas conexiones o consultas como derivadas de la misma billetera.

En particular, se asume que la combinación del nodo de Zcash subyacente y el proxy es "honesto pero curioso", y se confía en que proporcione una vista correcta del mejor estado actual de la cadena y que transmita fielmente consultas y respuestas.

Este ZIP no aborda cómo gastar notas de forma privada.

#Formato de flujo compacto

Una observación clave en este protocolo es que el campo cifrado actual de zcashd tiene una longitud de varios cientos de bytes, debido a la inclusión de un "memo" en la transacción. La necesidad de descargar todo este campo impone un costo sustancial de ancho de banda a cada billetera ligera, que puede ser un dispositivo móvil limitado en un plan de ancho de banda restringido. Si bien pueden desarrollarse técnicas más eficientes en el futuro, por el momento proponemos ignorar el campo memo durante la detección de pagos. Además, también podemos ignorar cualquier información que no sea directamente relevante para una transacción blindada de Sapling.

Un bloque compacto es un empaquetado de SOLO los datos de un bloque necesarios para:

  1. Detectar un pago a su dirección blindada de Sapling

  2. Detectar un gasto de sus notas blindadas de Sapling

  3. Actualizar sus testigos para generar nuevas pruebas de gasto de Sapling.

Un bloque compacto y sus transacciones compactas componentes se codifican en el canal usando el siguiente formato de Protocol Buffers [9]:

message BlockID {
     uint64 blockHeight = 1;
     bytes blockHash = 2;
}

message CompactBlock {
    BlockID id = 1;
    repeated CompactTx vtx = 3;
}

message CompactTx {
    uint64 txIndex = 1;
    bytes txHash = 2;

    repeated CompactSpend spends = 3;
    repeated CompactOutput outputs = 4;
}

message CompactSpend {
    bytes nf = 1;
}

message CompactOutput {
    bytes cmu = 1;
    bytes epk = 2;
    bytes ciphertext = 3;
}

#Detalles de codificación

blockHash, txHash, nf, cmu y epk se codifican como se especifica en el Protocol Spec de Zcash.

Las descripciones de salida y de gasto se manejan de forma distinta, como se describe en las secciones siguientes.

#Compresión de salidas

En el protocolo normal de Zcash, el texto cifrado de salida consiste en la forma cifrada con AEAD de un texto plano de nota [5]:

8 bits, 0x01

d de 88 bits

v de 64 bits

rseed de 256 bits

memo (512 bytes) + tag (16 bytes)

Un destinatario detecta sus transacciones mediante el descifrado por prueba de este texto cifrado. En un nodo completo que tiene todo el block chain, el costo principal es computacional. Para los clientes ligeros, sin embargo, hay un costo adicional de ancho de banda: cada texto cifrado del block chain debe recibirse desde el servidor (o nodo de red) al que está conectado el cliente ligero. Esto da un total de 580 bytes por salida que deben transmitirse en flujo al cliente (además de la clave pública efímera de 32 bytes).

Sin embargo, no necesitamos todo eso solo para detectar pagos. Los primeros 52 bytes del texto cifrado contienen los contenidos y la apertura del compromiso de nota, que son todos los datos necesarios para gastar la nota y para verificar que la nota es gastable. Si ignoramos el memo y la etiqueta de autenticación, nos quedan una clave pública efímera de 32 bytes, el compromiso de nota de 32 bytes y solo los primeros 52 bytes del texto cifrado por cada salida necesarios para descifrar, verificar y gastar una nota. Esto totaliza 116 bytes por salida, para una reducción del 80 % en el uso de ancho de banda.

Sin embargo, omitir el texto cifrado completo significa que ya no podemos calcular el tag de autenticación para todo el texto cifrado y tendremos que hacer algo más para validar la integridad del texto plano de nota descifrado.

Como el compromiso de nota se envía fuera del texto cifrado y es autenticado por la firma de enlace (binding signature) sobre toda la transacción, sirve como una verificación adecuada de la validez del texto plano descifrado (suponiendo que se confía en la entidad que ensambla las transacciones). Por lo tanto, recalculamos el compromiso de nota a partir del texto plano descifrado. Si el compromiso recalculado coincide con el que está en la salida, aceptamos la nota como válida y gastable.

#Operación del proxy

El propósito del proxy es proporcionar una interfaz escalable y eficiente en ancho de banda entre un nodo de Zcash y cualquier número de clientes ligeros. Lo logra analizando un flujo de transacciones bloque a bloque desde el nodo y convirtiéndolas al formato compacto descrito anteriormente.

Los detalles de la API descrita a continuación pueden diferir de la implementación.

El proxy ofrece la siguiente API a los clientes:

service CompactTxStreamer {
    rpc GetLatestBlock(ChainSpec) returns (BlockID) {}
    rpc GetBlock(BlockID) returns (CompactBlock) {}
    rpc GetBlockRange(RangeFilter) returns (stream CompactBlock) {}
    rpc GetTransaction(TxFilter) returns (FullTransaction) {}
}

// Remember that proto3 fields are all optional.

// Someday we may want to specify e.g. a particular chain fork.
message ChainSpec {}


// A BlockID message contains identifiers to select a block: either a
// height or a hash.
message BlockID {
    uint64 blockHeight = 1;
    bytes blockHash = 2;
}


message RangeFilter {
    BlockID start = 1;
    BlockID end = 2;
}

// A TxFilter contains the information needed to identify a particular
// transaction: either a block and an index, or a direct transaction hash.
message TxFilter {
    BlockID blockID = 1;
    uint64 txIndex = 2;
    bytes txHash = 3;
}

#Creación y actualización de testigos de notas

A medida que los CompactBlocks se reciben en orden de altura, y las transacciones dentro de ellos conservan su orden, los valores cmu de cada CompactOutput pueden añadirse secuencialmente a un árbol Merkle incremental de profundidad 32 para mantener una copia local del árbol de compromisos de notas de Sapling. [2] Este puede usarse luego para crear testigos incrementales para cada nota no gastada que el cliente ligero esté siguiendo. [10] Un testigo incremental actualizado hasta la altura X corresponde a una ruta Merkle desde la nota hasta el ancla del árbol de compromisos de Sapling para el bloque X. [3]

Sea tree el árbol de compromisos de notas de Sapling en la altura X-1, y note_witnesses los testigos incrementales para las notas no gastadas detectadas hasta la altura X-1. Cuando se recibe el CompactBlock en la altura X:

  • Para cada CompactTx en CompactBlock:

    • Para cada CompactOutput (cmu, epk, ciphertext) en CompactBlock:

      • Añadir cmu a tree.

      • Para witness en note_witnesses:

        • Añadir cmu a witness.

      • Si ciphertext contiene una nota relevante, crear un testigo incremental a partir de tree y añadirlo a note_witnesses.

Los árboles Merkle incrementales no pueden rebobinarse, por lo que el cliente ligero debería almacenar en caché tanto el árbol de compromisos de notas de Sapling como los testigos incrementales por nota para alturas de bloque recientes. La gestión de la caché depende de la implementación, pero un tamaño de caché de 100 es razonable, ya que ningún nodo completo de Zcash revertirá la cadena en más de 100 bloques.

#Detección de gastos

Las entradas de CompactSpend pueden compararse con los nullifiers locales conocidos, para por ejemplo asegurarse de que una transacción ha sido recibida por la red y minada.

#Validación de encabezados de bloque

Esta sección describe una mejora propuesta que solo se ha implementado parcialmente: actualmente solo se verifica prevHash.

Si el CompactBlock para la altura X contiene un encabezado de bloque, el cliente ligero puede validarlo de manera similar a los clientes SPV [11] realizando las siguientes comprobaciones:

  • version >= MIN_BLOCK_VERSION

  • prevHash == prevBlock.id.blockHash, donde prevBlock es el CompactBlock anterior recibido (en la altura X-1).

  • finalSaplingRoot es igual a la raíz del árbol de compromisos de notas de Sapling tras añadir cada cmu en el CompactBlock en orden.

  • La solución Equihash es válida.

  • targetFromBits(bits) != 0 && targetFromBits(bits) <= powLimit.

  • Si los últimos 27 CompactBlocks tienen todos encabezados de bloque, bits está correctamente establecido según el algoritmo de ajuste de dificultad.

  • toLittleEndian(blockHash) <= targetFromBits(bits).

Un CompactBlock que falle en cualquiera de estas comprobaciones DEBE (MUST) descartarse. Si se recibió como parte de una llamada a GetBlockRange, la llamada DEBE (MUST) abortarse.

La validación de encabezados de bloque proporciona a los clientes ligeros cierta seguridad de que los CompactOutputs que se les envían provienen efectivamente de bloques válidos que han sido minados. La seguridad más fuerte posible se logra cuando todos los encabezados de bloque están sincronizados; esto tiene un costo en ancho de banda y almacenamiento.

Por defecto, los CompactBlocks solo contienen CompactTxs para transacciones que contienen gastos o salidas de Sapling. Por lo tanto, no contienen información suficiente para validar que los identificadores de transacción recibidos correspondan a la raíz del árbol de transacciones en el encabezado de bloque. Esto no tiene un efecto significativo en la seguridad del cliente ligero: los clientes ligeros solo dependen directamente de CompactOutputs, que puede autenticarse mediante la validación de encabezados de bloque. Si se usa un txid en una llamada a GetTransaction, la transacción devuelta DEBERÍA (SHOULD) comprobarse contra el CompactOutputs correspondiente, además de verificar las firmas de la transacción.

#Extensiones potenciales

Una extensión trivial (con el correspondiente costo en ancho de banda) sería transmitir CompactTxs vacíos correspondientes a transacciones que no contienen gastos o salidas de Sapling. Una extensión más compleja enviaría los nodos internos de los árboles de transacciones correspondientes a subárboles no relevantes para Sapling; esto requeriría estrictamente menos ancho de banda que la extensión trivial. Estas extensiones no están actualmente definidas.

  • El cliente ligero consulta el estado del árbol de compromisos para el bloque X.

Fase B: El cliente ligero actualiza su vista local de la cadena por primera vez.

  • El cliente ligero consulta al servidor para obtener el Y de bloque más reciente.

  • Luego ejecuta una consulta de rango de bloques para obtener cada bloque entre X (inclusive) y Y (inclusive).

  • Se comprueba el bloque a la altura X para asegurar que el blockHash recibido coincida con la copia en caché del cliente ligero, y luego se descarta sin procesamiento adicional.

  • A medida que llega cada CompactBlock posterior, el cliente ligero:

    • Valida el encabezado de bloque si está presente.

      • Genera testigos incrementales para las notas y los actualiza de ahí en adelante.

      • Escanea sus nullifiers desde ese bloque en adelante.

  • A medida que llega cada CompactBlock posterior, el cliente ligero:

    • Valida el encabezado de bloque si está presente.

    • Actualiza los testigos incrementales para las notas conocidas.

    • Escanea cualquier nullifier conocido. Las notas correspondientes se marcan como gastadas a esa altura de bloque y se excluyen de actualizaciones posteriores de testigos.

    • Escanea cualquier transacción relevante para las direcciones generadas desde que se obtuvo Y. Estas se manejan como en la fase B.

#Importación de una semilla preexistente

La fase A de la interacción asume que las direcciones blindadas creadas por el cliente ligero nunca habrán sido usadas antes. Esta no es una suposición válida si el cliente ligero se inicializa con una semilla que no generó (p. ej., una semilla respaldada previamente). En este caso, la fase A se modifica de la siguiente manera:

Fase A: El cliente ligero se inicia por primera vez.

  • El cliente ligero establece X en la altura de bloque en la que se activó Sapling.

    • Las direcciones blindadas creadas por cualquier cliente ligero no pueden tener transacciones relevantes previas a la activación de Sapling.

#Privacidad de bloques mediante agrupamiento en buckets

Esta sección describe una mejora propuesta que no ha sido implementada.

La interacción anterior revela al servidor, al inicio de cada fase de sincronización (B y D), la altura de bloque a la que el cliente ligero se había sincronizado previamente. Esto es una fuga de información bajo nuestro modelo de seguridad (asumiendo privacidad de red). Podemos reducir la fuga de información mediante la agrupación en "buckets" del punto de inicio de cada sincronización. Hacerlo también nos permite manejar simultáneamente la mayoría de las reorganizaciones de la cadena.

Sea ⌊X⌋ = X - (X % N) el valor de X redondeado hacia abajo a algún múltiplo del tamaño de bucket N. Las fases de sincronización de la interacción anterior se modifican de la siguiente manera:

Phase   Client                Server
=====   ============================
  B     GetLatestBlock ------------>

        <---------------- BlockID(Y)

        GetBlockRange(⌊X⌋, Y) ----->

        <-------- CompactBlock(⌊X⌋)
        <-------- CompactBlock(⌊X⌋+1)
        <-------- CompactBlock(⌊X⌋+2)
                        ...
        <-------- CompactBlock(Y-1)
        <-------- CompactBlock(Y)

            ===

  D     GetLatestBlock ------------>

        <---------------- BlockID(Z)

        GetBlockRange(⌊Y⌋, Z) ----->

        <-------- CompactBlock(⌊Y⌋)
        <-------- CompactBlock(⌊Y⌋+1)
                        ...
        <-------- CompactBlock(Z-1)
        <-------- CompactBlock(Z)

Fase B: El cliente ligero actualiza su vista local de la cadena por primera vez.

  • El cliente ligero consulta al servidor para obtener el Y de bloque más reciente.

  • Luego ejecuta una consulta de rango de bloques para obtener cada bloque entre ⌊X⌋ (inclusive) y Y (inclusive).

  • Los bloques entre ⌊X⌋ y X se verifican para asegurar que el blockHash recibido coincida con la vista de la cadena del cliente ligero para cada altura, y luego se descartan sin procesamiento adicional.

    • Si se detecta una inconsistencia a la altura Q, el cliente ligero establece X = Q-1, descarta todos los bloques locales con altura >= Q y revierte el estado de todas las transacciones locales a la altura Q-1 (desminándolas según sea necesario).

  • Los bloques entre X+1 y Y se procesan como antes.

Fase D: El usuario ha gastado algunas notas. El cliente ligero actualiza su vista local de la cadena algún tiempo después.

  • El cliente ligero consulta al servidor para obtener el Z de bloque más reciente.

  • Luego ejecuta una consulta de rango de bloques para obtener cada bloque entre ⌊Y⌋ (inclusive) y Z (inclusive).

  • Los bloques entre ⌊Y⌋ y Y se verifican para asegurar que el blockHash recibido coincida con la vista de la cadena del cliente ligero para cada altura, y luego se descartan sin procesamiento adicional.

    • Si se detecta una inconsistencia a la altura R, el cliente ligero establece Y = R-1, descarta todos los bloques locales con altura >= R y revierte el siguiente estado local a la altura R-1:

      • Todas las transacciones locales (desminándolas según sea necesario).

      • Todos los nullifiers rastreados (revirtiendo su gasto o descartándolos según sea necesario).

      • Todos los testigos incrementales (las estrategias de caché no se tratan en este ZIP).

  • Los bloques entre Y+1 y Z se procesan como antes.

#Privacidad de transacciones

Las fases de sincronización le dan al cliente ligero información suficiente para determinar saldos precisos de las direcciones, mostrar cuándo se recibieron o gastaron fondos y gastar cualquier nota no gastada. Como la sincronización ocurre mediante un medio de difusión, no filtra información sobre qué transacciones le interesan al cliente ligero.

Sin embargo, si el cliente ligero necesita acceso a otros componentes de una transacción (como los campos de memo de las notas recibidas, o los textos cifrados salientes para recuperar información de gasto al importar una semilla de billetera), deberá descargar la transacción completa. El cliente ligero DEBERÍA (SHOULD) ocultar las transacciones exactas de interés descargando también numerosas transacciones que no son de interés, y DEBERÍA (SHOULD) descargar todas las transacciones de cualquier bloque del cual se obtenga una sola transacción completa (sea de interés o no). DEBE (MUST) informar al usuario que obtener transacciones completas reducirá su privacidad.
