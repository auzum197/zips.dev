#Terminología

Las palabras clave "DEBE (MUST)", "NO DEBE (MUST NOT)" y "PUEDE (MAY)" de este documento deben interpretarse como se describe en BCP 14 [1] cuando, y solo cuando, aparecen en mayúsculas.

Los términos "rama de consenso", "actualización de red" y "cambio de regla de consenso" de este documento deben interpretarse como se describe en ZIP 200. [3]

El término "Overwinter" de este documento debe interpretarse como se describe en ZIP 201. [4]

#Resumen

Esta propuesta define un nuevo formato de transacción requerido para el mecanismo de actualización de red [3] y la expiración de transacciones [5].

#Motivación

Zcash se lanzó con soporte para transacciones versión 1 de Bitcoin upstream y definió un nuevo formato de transacción versión 2 que agregó los campos requeridos para transacciones blindadas.

Se requiere un nuevo formato de transacción para:

  • admitir actualizaciones de red seguras según lo especificado en Network Upgrade Mechanism [3];

  • proporcionar protección contra replay entre las ramas de consenso anteriores a Overwinter y las de Overwinter durante las actualizaciones;

  • proporcionar protección contra replay entre diferentes ramas de consenso posteriores a Overwinter;

  • permitir que una rama de consenso admita múltiples formatos de versión de transacción;

  • garantizar que los formatos de transacción se analicen de forma única entre ramas de consenso paralelas;

  • admitir la expiración de transacciones [5].

#Especificación

#Formato de transacción versión 3

Se introducirá un nuevo formato de transacción versión 3 para Overwinter.

El formato de la versión 3 difiere del formato de la versión 2 en los siguientes aspectos:

  • encabezado (primeros cuatro bytes, codificados en little-endian)

    • fOverwintered flag : bit 31, debe estar establecido

    • nVersion : bits 30-0, entero positivo

  • nVersionGroupId

  • nExpiryHeight

#Campo de encabezado

Los primeros cuatro bytes de las transacciones anteriores a Overwinter y de las de Overwinter están codificados en little-endian.

La transacción versión 1 (txid 5c6ba844e1ca1c8083cd53e29971bd82f1f9eea1f86c1763a22dd4ca183ae061)

  • comienza con la secuencia de bytes en little-endian [0x01, 0x00, 0x00, 0x00];

  • se deserializa como un entero con signo de 32 bits con valor decimal 1.

La transacción versión 2 (txid 4435bf8064e74f01262cb1725fd9b53e600fa285950163fd961bed3a64260d8b)

  • comienza con la secuencia de bytes en little-endian [0x02, 0x00, 0x00, 0x00];

  • se deserializa como un entero con signo de 32 bits con valor decimal 2.

Los analizadores de transacciones de las versiones de Zcash anteriores a Overwinter, y de la mayoría de los demás forks de Bitcoin, exigen que el número de versión de la transacción sea positivo.

Con el formato de transacción versión 3, los primeros cuatro bytes de una transacción serializada, el encabezado de 32 bits, están formados por dos campos como se muestra en la tabla anterior:

  • un flag fOverwintered de 1 bit, que debe estar establecido;

  • un entero sin signo de 31 bits para la versión.

Los analizadores anteriores a Overwinter deserializarán estos cuatro bytes como un entero con signo de 32 bits. En los enteros en complemento a dos, el bit más significativo indica si un entero es positivo o negativo. Con el flag de Overwinter establecido, la versión de la transacción será negativa, lo que hará que los analizadores anteriores a Overwinter rechacen la transacción como inválida. Esto proporciona protección contra la repetición de transacciones entre el software anterior a Overwinter y el de Overwinter.

Considérese el siguiente ejemplo de una transacción versión 3 serializada.

Analizador anterior a Overwinter:

  • los datos comienzan con la secuencia de bytes little-endian: [0x03, 0x00, 0x00, 0x80];

  • deserializado como un entero con signo de 32 bits.

    • con un valor hexadecimal de 0x80000003 (el bit más significativo está establecido);

    • valor decimal de -2147483645.

Los analizadores heredados esperarán que la versión sea un valor positivo, como 1 o 2, y por lo tanto rechazarán la transacción de Overwinter como inválida.

Analizador de Overwinter:

  • los datos comienzan con la secuencia de bytes little-endian: [0x03, 0x00, 0x00, 0x80];

  • deserializado como un entero sin signo de 32 bits

    • con un valor binario de 0b10000000000000000000000000000011;

  • los 32 bits se descomponen en dos campos:

    • bandera fOverwintered (bit 31) como booleano, se espera que esté establecido;

    • versión (bits 30 - bit 0) como entero sin signo, se espera que tenga un valor decimal de 3.

Los analizadores de Overwinter aceptarán la transacción como válida porque se ha establecido el bit más significativo del encabezado. Al enmascarar (desestablecer) el bit más significativo, el analizador puede recuperar el número de versión de la transacción:

0x80000003 & 0x7FFFFFFF = 0x00000003 = 3

#Identificador de grupo de versión

El identificador de grupo de versión es un identificador distinto de cero, aleatorio y único, de tipo uint32, asignado a una versión del formato de transacción, o a un grupo de versiones del formato de transacción compatibles mediante soft fork. El identificador de grupo de versión ayuda a los nodos a desambiguar entre ramas de consenso que usan el mismo número de versión.

Es decir, evita que un cliente en una rama de la red intente analizar transacciones destinadas a otra rama de consenso, en la situación en que las transacciones comparten el mismo número de versión de formato pero en realidad están especificadas de manera diferente. Por ejemplo, Zcash y un clon de Zcash podrían definir ambos sus propios formatos de transacción v3 personalizados, pero cada uno tendrá su propio identificador de grupo de versión único, de modo que puedan rechazar transacciones v3 con identificadores de grupo de versión desconocidos.

La combinación de la versión de la transacción y el identificador de grupo de versión, nVersion || nVersionGroupId, define de manera única el formato de la transacción, lo que permite a los analizadores rechazar transacciones provenientes de fuera de la cadena del cliente que no pueden analizarse.

Por convención, se espera que al introducir una nueva versión de transacción que requiera una actualización de red, se asigne un nuevo identificador de grupo de versión único a esa versión de transacción.

Sin embargo, si una nueva versión de transacción puede analizarse correctamente según el formato de una versión precedente (es decir, solo restringe el formato, o define campos que estaban previamente reservados y que los analizadores antiguos pueden ignorar de forma segura), entonces PUEDE (MAY) reutilizarse el mismo identificador de grupo de versión.

#Altura de expiración

El campo de altura de expiración, tal como se define en el ZIP de Expiración de Transacciones [5], almacena la altura de bloque después de la cual una transacción ya no puede ser minada.

#Validación de transacciones

Una transacción válida de Overwinter destinada a Zcash DEBE (MUST) tener:

  • número de versión 3; y

  • identificador de grupo de versión 0x03C48270; y

  • el indicador fOverwintered activado.

Los validadores de Overwinter DEBEN (MUST) rechazar transacciones por violar reglas de consenso si:

  • el indicador fOverwintered no está activado; o

  • el identificador de grupo de versión es desconocido; o

  • el número de versión es desconocido.

La validación de transacciones de versión 3 DEBE (MUST) usar el proceso de validación de firmas detallado en el ZIP de Validación de Firmas de Transacciones para Overwinter [2].

#Implementación

Los comentarios y ejemplos de código de esta sección aplican a la implementación de referencia en C++ de Zcash. Otras implementaciones pueden variar.

#Versión de transacción

La versión de transacción sigue siendo un valor positivo. La cadena principal de Zcash seguirá la convención y continuará ordenando las versiones de transacción en orden ascendente.

Las pruebas pueden seguir verificando la existencia de campos de transacción compatibles hacia adelante mediante la comparación de la versión de transacción usando operadores de comparación:

if (tx.nVersion >= 2) {
    for (int js = 0; js < joinsplits; js++) {
        ...
    }
}

Al (des)serializar transacciones v3, también se debe verificar el identificador de grupo de versión en caso de que la transacción esté destinada a una rama de consenso que tenga un formato diferente para su transacción de versión 3:

if (tx.nVersion == 3 && tx.nVersionGroupId == OVERWINTER_VERSION_GROUP_ID) {
    auto expiryHeight = tx.nExpiryHeight;
}

Las pruebas pueden seguir estableciendo la versión en cero como condición de error:

mtx.nVersion = 0

#Validación de Overwinter

Para probar si el formato de una transacción de Overwinter es v3 o no:

if (tx.fOverwintered && tx.nVersion == 3) {
    // Valid v3 format transaction
}

Esto solo prueba que el formato de la transacción coincide con la especificación v3 descrita anteriormente.

Para probar si el formato de una transacción de Overwinter es v3 y si la transacción misma está destinada a la cadena del cliente:

if (tx.fOverwintered &&
    tx.nVersionGroupId == OVERWINTER_VERSION_GROUP_ID) &&
    tx.nVersion == 3) {
    // Valid v3 format transaction intended for this client's chain
}

Se espera que esta prueba que involucra nVersionGroupId solo sea necesaria cuando se construye o deserializa una transacción, por ejemplo, cuando una transacción externa ingresa al sistema.

Sin embargo, es posible que un clon de Zcash esté usando el mismo identificador de grupo de versión y pase la condicional.

En última instancia, un cliente puede determinar si una transacción está realmente destinada a la cadena del cliente o no siguiendo el proceso de validación de firmas detallado en el ZIP de Transaction Signature Validation for Overwinter [2].

#Despliegue

Esta propuesta será desplegada con la actualización de red de Overwinter. La propuesta de altura de bloque de activación se encuentra en [4].

#Compatibilidad hacia atrás

Esta propuesta crea intencionalmente lo que se conoce como un "cambio de regla de consenso bilateral" [3] entre el software anterior a Overwinter y el software compatible con Overwinter. El uso de este nuevo formato de transacción requiere que todos los participantes de la red actualicen su software a una versión compatible dentro de la ventana de actualización. El software anterior a Overwinter tratará las transacciones de Overwinter como inválidas.

Una vez que Overwinter se haya activado, el software compatible con Overwinter rechazará las transacciones de versión 1 y versión 2, y solo aceptará transacciones basadas en números de versión de transacción soportados e identificadores de grupo de versión reconocidos.
